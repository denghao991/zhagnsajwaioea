# RAG 问答系统面试拷打清单

---

## 项目背景

我所在的团队负责一款内部云管平台，平台下面挂了几十个云服务。团队大约十几个人，分了多个方向，每人负责不同模块——有人管计算、有人管存储、有人管网络、有人管监控。每个方向的同学在日常开发和 oncall 过程中积累了大量知识：某个服务的启动流程是什么、某个告警的排查步骤、某个配置项改了会影响哪些下游、某个 API 的限制条件和默认值。

这些知识过去沉淀在内部 Wiki 里，逐年累积，到我接手时已经有约 500 篇 Markdown 文档。但文档多不代表知识可获取。

团队平时遇到问题的实际路径是：打开 Wiki 顶部的搜索框，输入几个关键词，回车。Wiki 的搜索是关键词全文匹配——你输入的词必须出现在文档正文里才能命中。问题在于，用户输入的词和文档使用的词往往不在一个语义空间。"OA 告警阈值怎么配"的答案在「优化顾问监控告警配置」这篇文档里，但这两个字符串之间没有任何公共关键词，Wiki 搜索返回零结果。用户搜不到，就去内部群里 @oncall 同学。oncall 同学看到问题，在脑子里匹配——"这个问题我看过，在某某文档里"——然后把链接发到群里，或者直接打字回答。同样的问题——"region 白名单在哪配""这个报错什么意思""某服务的默认限制是多少"——一天被问七八次，oncall 每天有大量时间消耗在重复问答上，真正的复杂排查反而没精力做。

这个流程有三个不可持续的地方：

**第一，知识检索依赖人脑索引。** oncall 同学是唯一知道"问题 A → 文档 B"映射关系的人。他请假、离职、转岗，这个映射表就没了。而且这套映射表只在 oncall 一个人脑子里，团队其他人遇到问题时没法自助查询——只能等他回复。

**第二，文档的维护和使用是断开的。** 写文档的人花时间把排查步骤写清楚，但用的人搜不到，文档就白写了。长此以往，写文档的动力会下降——"反正写了也没人看"——知识沉淀的循环就断了。

**第三，规模效应在帮倒忙。** 团队越扩张、服务越多、文档越多，oncall 的负担越重，但 oncall 的人数不会等比增长。500 篇文档靠一个人翻译，5000 篇呢？这个模式的天花板就在眼前。

所以这个项目的必要性不在于"用 AI 提升效率"这种大词，而在于一个非常具体的判断：**团队的知识已经存在了（500 篇文档），但缺少一个能把自然语言问题翻译成文档检索的中间层。过去这个中间层是 oncall 的人脑，但这不可持续。RAG 是目前最成熟、成本最低的方式来做这个中间层。** 用户用自然语言提问 → 系统做语义检索 → 找到相关文档片段 → LLM 组织成带引用的答案。不需要 oncall 在中间做翻译。

为什么要自己做而不是买现成的？三个原因：所有模型必须部署在内网（合规要求，外部 API 不可用），内部 Wiki 的内容结构和术语体系需要定制化的切片和检索策略，以及答案必须带 chunk 级别的溯源引用（市面上的通用方案做不到这个粒度）。

系统上线后，日均处理约 100 个问题，把 oncall 从重复问答中释放出来，同时让团队成员 7×24 小时能自助获取答案——不需要等别人回复。这不是一个大系统，但解决的是一个真实存在的问题。

## 一、离现阶段（数据处理、索引构建、评估体系）

### 1.1 文档处理 & 切片策略

**Q1.** 500个文档，你用了什么切片策略？固定长度、固定token数、还是基于语义的切片？为什么选这个方案？你对比过哪几种切片方式的召回效果？
 
我们的文档主要是 Markdown 格式，面向内部用户的 API 文档、故障手册、功能说明和版本更新记录。基于这些文档结构化的特点，我们的切分策略是：先用
  Markdown parser 按一二级标题做结构拆分，然后在每个二级标题域内，如果内容超过设定的 token 上限，再递归地按段落和行进行切分。

  对于特殊文本，比如表格、JSON 配置、代码块，我们不会按上限硬截断，而是做两条处理：第一，在清洗阶段用 LLM
  离线为这些特殊块生成一段自然语言描述，拼入 chunk 的 content 中，补充语义信息；第二，对于非特殊文本的普通段落，我们会把当前 chunk
  所属的一二级标题路径前置拼接到 content 头部，增强 chunk 的上下文信息。这样即使 chunk 被单独召回，大模型也能知道这段话出自哪个文档的哪个章节。 

  关于 chunk size 的选择，我们对比了 256、384、512 三个档位。选型逻辑分两步。第一步，全量 500
  个文档做语义切分后统计截断率。截断的正确定义是：如果当前 chunk 长度触达上限，且它和相邻 chunk
  共享同一标题路径，说明它是被硬截断的，而不是刚好自然结束。我们 384 和 512 的截断率都在百分之一左右，差距不大。第二步，我们构造了 100 条 QA  
  pairs 做检索召回评测。评测集是按场景分层抽样的，覆盖 API 类、故障类、功能细节类、版本类，同时刻意保留了百分之十到二十的冷门问题样本。每条     
  query 是用户在群里的真实问题，answer 标注的是对应的正确 chunk ID。我们把 384 和 512 两个配置跑检索评测。评测指标按问题类型拆成两组：单答案型问题（只有一个正确 chunk）用 MRR，综合推理型问题（需要多个 chunk 共同支撑）用 Recall@5。实测结果：384 单答案型 MRR 0.831（vs 512 的 0.791），综合推理型 Recall@5 0.892（vs 0.874）。384 在两项指标上均小幅领先，同时 chunk 更短、检索延迟更低，所以我们选了 384。

  关于 overlap，因为我们按标题和段落做语义切分，不是按固定长度硬切，截断发生的比例非常低，所以 overlap
  设的是零。如果后续新增文档导致截断率上升，我们会考虑用父子 chunk 的方案来补救：子 chunk 命中时，把对应的父 chunk
  一并返回给大模型，用更长的上下文弥补语义断裂。

  评估这一步，我们实际没有跑 bootstrap 显著性检验，因为业务规模不大，评测集的差异 case 我们可以逐条人工检查来判断是不是噪声。而且线上我们有反馈 
  闭环——用户踩的答案、以及漏到人工群里的问题都会被日志记录下来，定期回流扩充评测集。如果未来数据量更大、评测成本更高，我们会加上 bootstrap      
  来避免噪声误导决策。

  关于表格的检索召回率，目前我们没有单独量化，因为在实际业务中，用户的问题主要以功能和故障描述为主，纯表格类问题占比较低。但这个判断更多是基于经
  验而不是数据验证，这一点是我需要改进的。


**Q2.** 你文档的格式是什么？纯文本、Markdown、PDF、Word、Confluence？不同格式你怎么做解析和归一化的？表格和图片你是怎么处理的？表格被切碎了怎么办？

 我们的 500 个文档全部来源于内部 Wiki 平台，原生 Markdown 格式，由团队自己维护在 Git 仓库中，不存在从 Confluence、Word
  或网页转换的场景。这保证了格式一致性，不存在转换过程中的编码错误或层级丢失。
  
  解析方案上，我们使用 LangChain 的 MarkdownHeaderTextSplitter。它底层基于 Python markdown 库做 AST
  解析，按标题层级递归拆分，能正确区分代码块内的 # 符号和真正的 Markdown 标题，不会出现正则匹配常见的误判问题。我们在选型时全量跑了 500
  文档的解析验证，检查了标题层级连续性、空 chunk 率和 chunk
  边界合理性，没有出现解析失败或静默切错的情况。坦白说我没有逐行读过它的源码，但通过输出验证确认了它在我们的文档集上是可靠的。

  表格、JSON 和代码块的处理，我们不做硬截断，而是全文保留，同时在离线清洗阶段用 DeepSeek V4 Flash
  模型为这些特殊文本块生成自然语言摘要。具体做法是 few-shot prompt，把上下文和特殊文本一起给模型，让它生成一句功能性的标题，比如一个 JSON       
  配置块会被总结为"region 白名单配置"。整个文档集统计下来共 37 个表格、43 个 JSON 配置块、35 个代码块，每次调用的输入 token
  大约一千左右，输出只有几十个 token。因为我们用的是内部统一 API，成本在整体预算中几乎忽略不计。

  图片的处理是我们第一期明确做的取舍。目前模型不支持多模态，图片在解析阶段直接丢弃，在原文位置插入占位符标记。文档中与图片关联的引用文字如"如下 
  图所示"，当前没有做特殊清理，可能在个别 chunk 中遗留无意义的上下文断裂。但我们评估过我们文档的特点——内部文档以
  FAQ、功能说明和排障手册为主，不像论文或技术博客那样重度依赖图片传达关键信息，所以第一期没有投入工程资源处理这个问题。这是技术债，我记录了。   

  如果未来要支持图片，我会走图片转文本的路线，用视觉模型为图片生成文字描述嵌入原 chunk，继续复用现有的纯文本检索架构，不改检索管线。多模态      
  embedding 单独建索引的方案工程成本更高，在我们的场景里现阶段不划算。

**Q3.** 切片大小设了多少？这个数字是怎么定出来的？你有做过消融实验（ablation study）吗？chunk overlap 设了多少？overlap 设成多少对最终效果的影响你量化了吗？

我们的 chunk size 最终选了 384 token，overlap 设的是 0。

  选型流程分四步。

  第一步，确定候选值。我把 500 个文档全量跑了一遍 tokenizer，看了 chunk 长度的实际分布，中位数大概在 300 token 左右，所以定了 256、384、512     
  三个候选值在真实分布的两侧，覆盖了"偏小、适中、偏大"三个区间。

  第二步，截断率筛下限。在全量 500 文档上分别用三个上限做语义切分，统计截断率。截断的正确定义是：chunk 长度触达上限且与相邻 chunk
  共享标题路径。256 的截断率明显偏高，说明 256 装不下我们的内容，频繁腰斩语义，淘汰。384 和 512
  截断率都在百分之一左右，说明两个都足够大，截断率到这里就完成了它的使命，不再参与后续决策。

  第三步，检索评测做精选。384 和 512 两个配置全部跑检索评测。我们构造了 100 条 QA
  pairs，按文档类型和问题场景分层抽样，高频约占八成，冷门约占两成。每条 query 标注了正确的 chunk ID 作为 ground truth。两个配置分别计算每条     
  query 的 MRR 或 Recall@5 拆组评测。384 在单答案型上 MRR 0.831 vs 512 的 0.791，综合推理型上 Recall@5 0.892 vs 0.874，两项指标均小幅领先但差距不大。严格来说，我应该跑 bootstrap
  显著性检验来确认这个差距不是噪声——从 100 条里有放回抽样 10000 次，看差值分布，确认 p 小于 0.05。如果检验结果不显著，那就说明 384 和 512       
  在检索效果上无差异，此时选 384 是因为 token 更省、向量维度下的检索效率更高。好在我们业务体量小，实际中我们额外做了人工确认：把两个配置的差异  
  case 逐条拿出来看，判断 384 的检索结果是否确实更好，辅助验证了这个选择。

  第四步，chunk 质量人工抽查。切分完成后，我们对 384 配置下的 chunk 做了抽样检查，看了几十个 chunk，确认没有语义被明显截断或一个 chunk
  内堆叠多个不相关话题的情况。坦白说这一步是人工的，没有双人交叉验证，不够严谨。

  关于消融实验，我坦诚说没有做。我无法量化 header 拼接、特殊文本 LLM 摘要、chunk size 这三个设计各自对最终效果的贡献。这是我的一个盲区——如果面试
  官追问我哪个设计贡献最大，我答不出来确切的数字。正确的做法是把每个设计当开关，逐个关掉跑评测，看 MRR 掉多少。

  关于 overlap，我设的是 0。理由是我们的切分是按 Markdown
  标题层级加段落行做语义切分，不是固定长度硬切，截断率在百分之一以下，语义断裂的场景很少。所以 overlap
  用于补救截断的需求不存在。但我必须承认我没有验证 overlap 的另一个潜在价值——同一段内容出现在相邻两个 chunk
  里，检索时有双保险、命中概率可能更高。我没有跑过 overlap=0 和 overlap=50 的对照检索实验，所以我只能说我选了 0
  且目前线上检索效果可以接受，但我不能声称 overlap=0 一定是最优解。如果后续线上出现检索遗漏的 bad case，我会优先排查是否有语义刚好落在 chunk    
  边界导致向量相似度不够的情况，届时补做 overlap 的消融实验。

**Q4.** 你怎么处理文档更新的？文档有变更（新增、修改、删除）时，索引怎么同步？是全量重建还是增量更新？增量更新时怎么保证 chunk 之间引用关系不破裂？

 我们在每个 chunk 的 metadata 里记录了三个关键字段：file_name，作为文档级别的唯一标识；chunk_index，记录 chunk
  在文档内的切分顺序（仅用于前端展示时恢复原文段落顺序）；chunk_hash，记录当前 chunk 内容的 MD5，用于变更检测。

  **新增**：用 file_name 查询向量库。查不到，说明是新文档，直接切分入库。查得到，说明文件名重复，返回二次确认——"该文件名已存在，确认覆盖？"操作人确认后才进入修改流程。

  **修改**：用 file_name 查出该文档的所有旧 chunk，全部删除；新文档重新切分后，全部插入。不做逐 chunk 的增量比对。

  为什么不做增量比对？一个很自然的想法是：新旧两个 chunk 列表按 chunk_index 对齐，逐对比 hash，hash 相同的跳过、不同的替换——这样只重新 embedding 变化的部分，省 API 调用。但这个逻辑依赖一个前提：旧 chunk[3] 和新 chunk[3] 是同一段内容的两个版本。这个前提在修改场景下不成立——用户在文档中间插入一段、删除一段、或者调整章节顺序后，整个文档的 chunk 边界全部偏移。旧 chunk[3] 是"网络配置"那段，新 chunk[3] 变成了"存储配置"那段，两个完全不相关的内容被当成同一个 chunk 比 hash，结果一定是 hash 不同 → 删除旧 + 插入新——操作虽然会执行，但旧 chunk[3] 被错误删除（因为它的内容实际上在新文档的 chunk[5] 里，hash 本来可以匹配命中的）。所以按索引对齐做增量比对，在文档结构变化时反而会产生不必要的删除和重复 embedding，既没有省到，逻辑还是错的。

  正确的增量比对应该按内容 hash 做集合差集，不依赖 chunk_index：
  - 旧 chunk 集合中 hash 不在新 chunk 集合中的 → 删除
  - 新 chunk 集合中 hash 不在旧 chunk 集合中的 → 插入
  - hash 同时出现在两个集合中的 → 不动（这部分是真正没变的内容，省了 embedding）

  为什么我们连 hash 集合差集也没做？因为 500 文档/2000 chunk 这个规模下，单篇文档更新通常只有 5~20 个 chunk，re-embedding 的成本极低（内部 API，几十分钱级别），hash 差集比对带来的代码复杂度高于它省下的成本。等文档量到了需要优化的那一天再补这个逻辑，当前删全量 + 插全量是最简单也最正确的方案。

  **删除**：用 file_name 查出该文档下所有 chunk，逐个删除后验证数量归零。

  **并发安全**：修改流程是先删后插的两步操作。如果删除成功后、插入前进程崩溃，该文档的索引会暂时缺失。当前不做事务原子性——用户入口是上传模式，感知到异常后重新上传即可恢复。Redis 分布式锁在此处的作用是并发互斥（同一文档的并发操作串行化），锁粒度 file_name 级别，30 秒过期兜底防死锁。

  **索引同步**：ChromaDB 的向量索引增量更新，增删改后自动同步。BM25 全文索引每次数据变更后从内存重建，2000 chunk 级别在毫秒级完成。

  **chunk 引用关系**：当前没有。Markdown 按标题语义切分，截断率在 1% 以下，chunk 是独立检索单元，不需要父子或相邻引用。如果未来文档复杂度上升，在 metadata 里加 parent_chunk_id 字段，检索时命中子 chunk 一并带出父 chunk 即可。

  **file_name 做主键的局限**：文件名被改后，旧 file_name 的 chunk 变成孤岛残留，新 file_name 走新增分支可能引入重复。当前通过上传规范约束文件名唯一不可改 + 上传时二次确认兜底。更严谨的做法是用 Wiki 页面路径或平台稳定 ID 做主键。

**Q5.** 有没有做文档的预处理或清洗？比如去掉页眉页脚、去除水印、处理乱码、格式转换错误？你是怎么发现这些脏数据问题的？

  我们目前没有做系统化的预处理管线，原因和局限我分开说。

  先说做过的部分。对于特殊文本块——表格、JSON 配置、代码块——我们在离线阶段用 DeepSeek V4 Flash 做 few-shot
  摘要生成，把文本块和它周围的上下文一起给模型，让它输出一个功能性的标题，比如"region 白名单配置"或"API 错误码对照表"，这个标题作为 chunk
  的前置信息打入 content，补充语义。这个处理是规则发现特殊文本后用正则定位，然后离线批量调用 LLM 完成。

  图片我们做了基本处理：解析时检测到图片，替换为占位符标记，同时在 prompt
  中告诉生成模型"当前文档中图片已被移除，如遇到'如下图'等无意义引用请忽略"。

  坦白说下面几个点是我没有做但应该做的。

  第一，文档质量本身没有审查。500
  个文档由不同人不同时期编写，风格和粒度不一致。有的可能是详细的操作步骤，有的可能就一句话。没有经过质量筛选就直接入库了，这可能导致 RAG        
  召回了一个写得模糊的文档，LLM 基于它生成了同样模糊甚至错误的答案。正确做法应该在上线前对入库文档做一轮人工审核或 LLM
  质量打分，标出低质量文档，要么优化要么暂不索引。

  第二，图片的类型和分布我没有统计。我只知道图片数量不多，但我不知道其中多少是截图（报错、配置界面），多少是架构图、流程图。这两类图片的处理完全
  不一样：截图的 OCR 文字提取是有用的，但架构图里语义在拓扑关系里，纯 OCR
  提取出来是一堆散落的名词，没有意义。我把所有图片归成一类说"不重要"，这是拍脑袋，不是评估。正确做法应该抽样统计图片类型分布后再决定方案。      

  第三，图片引用文字的清理是没做的。占位符能标记图片丢了，但不能修复上下文断裂。"按照下图红色框所示，点击提交按钮"——图片没了，这句话对 LLM      
  就是噪声。如果说"图片数量不多所以没处理"，但面试官会反问"那你验证过吗？"我没有验证，这是我的盲区。

  如果后续要做图片支持，我的方案是：先抽样统计图片类型比例。如果截图为主，走 OCR 文字提取 +
  嵌入原文，不改检索架构。如果架构图/流程图占比高，考虑用视觉模型生成自然语言描述替代图片，仍然走纯文本检索。多模态 embedding
  独立建索引的方案工程量大，只有在图片成为核心信息载体时才值得投入。就我们内部 FAQ
  和排障手册的文档特点判断，大概率走第一条路就够了，但这个判断目前缺乏数据支撑。

### 1.2 Embedding & 向量化

**Q6.** Embedding 模型选的是什么？为什么选这个？你对比过哪些模型？在你们自己的数据集上做评测了吗？评测指标是什么？

 我们用的是阿里 text-embedding-v3@768，内部私有化部署，不走公网 API。选择背景是信息安全合规要求——所有模型必须部署在内网，网络完全隔离，不能用外部 API。候选池天然受限，只能在内部已部署的模型里选，当时可用的只有阿里 V2 和 V3。

 V2 固定 1024 维。V3 支持 512、768、1024 三档。所以候选配置一共四组：V2@1024、V3@512、V3@768、V3@1024。四组全部在 100 条 QA pairs 上跑检索，直接看结果，不需要分阶段。

 评测指标按问题类型拆两组：单答案型（FAQ、配置查询，只有一个正确 chunk）用 MRR；综合推理型（故障排查、跨文档分析，需要多个 chunk 共同支撑）用 Recall@5。

 四组结果：

 | 配置 | MRR | Recall@5 |
 |------|------|----------|
 | V2@1024 | 0.737 | 0.819 |
 | V3@512  | 0.780 | 0.853 |
 | V3@768  | 0.831 | 0.892 |
 | V3@1024 | 0.833 | 0.893 |

 两个结论很直接。第一，V3 全线优于 V2——即使 V3 最低配的 512 维也超过 V2 的 1024 维（MRR 0.780 vs 0.737），模型代际差距明显。第二，V3 内部 768 和 1024 两项指标几乎持平（MRR 差 0.002、Recall@5 差 0.001），但 1024 维存储多 33%、HNSW 检索延迟也相应增加。所以选 V3@768——效果到顶了，成本更低。

 我们没有跑 bootstrap 显著性检验，因为评测集规模不大（100 条），差异 case 可以逐条人工判断是不是真实改善。如果评测集扩展到几百条以上，应该加上。

 候选池局限于阿里两个模型，我清楚。BGE 的中文模型和 Jina 的多语言模型在公开评测上对中文支持也很好，但受合规约束目前没有实测——这是环境限制，不是技术决策。

 关于模型升级：embedding 模型一旦切换、维度一旦变化，必须全量重建索引。我设计的升级流程是旧版本索引继续服务线上，同时在后台全量重建新版本索引，两个索引并行跑，对同一批 query 比较检索结果，确认不退化后再切流量，旧索引保留一周做回滚兜底。当前规模下全量重建成本在百万 token 级别，完全可以接受。


**Q7.** 你用的是什么向量数据库？Milvus、Pinecone、Weaviate、Qdrant 还是自研？为什么选它？跟你们现有基础设施怎么配合的？
我们用的是 ChromaDB，选型逻辑不是因为它"刚好有"，而是按综合代价公式做了六个方案的对比后，它在我们场景下代价最低。

  综合代价 = 部署成本 + 运维成本 + 学习成本 + 切换成本 + 性能折损。

  Elasticsearch。如果团队已有 ES 集群，在 dense_vector 上加 HNSW 索引是最省事的方案——一个引擎同时提供
  BM25、向量检索、混合打分，高可用自带，中文分词现成。但我们当前环境没有 ES 集群，引入 ES 意味着引入 JVM 运维、heap 调优、版本升级时的 breaking 
  change，而团队主技术栈是 Python，出了问题排查成本很高。引入一个新中间件的代价远超我们的需求。

  Milvus。十亿级向量的最佳方案，但完整部署依赖 etcd、MinIO、Pulsar，运维四个中间件来完成两千个 chunk 的检索是杀鸡用牛刀。Milvus Lite 才是       
  ChromaDB 真正的竞品，pip install 即可运行，底层也是 hnswlib。坦诚说我没有做 Milvus Lite 和 ChromaDB 的同等数据量对比
  benchmark，这是选型流程上的缺失。

  Qdrant。Rust 实现，单机吞吐量同类领先。但它是独立进程的 Rust 二进制，部署多一个环节。如果出 bug，翻 Rust 源码的门槛我够不着。在两千条 chunk   
  的规模下，hnswlib 和 Qdrant 的性能差异根本感知不到，但运维复杂度的差异是实打实的。

  Weaviate。自带 vectorizer、generative、rerank 模块，RAG 全家桶。但我们架构是检索和生成分离——embedding 自己调、LLM 自己调、rerank
  自己调。Weaviate 的内置模块在我们架构里全是冗余，反而引入了额外的模块启用禁用配置。ChromaDB 只做"存向量加查向量"一件事，和我们自己控制        
  pipeline 的设计一致。

  FAISS。Facebook 的向量检索库，算法丰富、GPU 加速成熟。但它是库不是数据库——没有持久化、没有元数据管理、没有增删改 API。要用 FAISS 做 RAG       
  必须自己在上层实现所有这些，相当于把 ChromaDB 封装好的功能重写一遍。FAISS
  适合需要自定义索引策略的场景，对我们这种需要"能存能查"的需求来说太底层了。

  pgvector。如果团队已有 PostgreSQL，一个 CREATE EXTENSION 就搞定，向量和业务数据在一个事务里，ACID 保证。但当前环境没有 PG 实例。pgvector 的   
  HNSW 索引构建受 PostgreSQL WAL 写入路径影响，比 ChromaDB 慢。如果未来需要向量加元数据混合过滤，pgvector 是优势，但当前没有这个需求。

  最终选 ChromaDB 的核心原因：部署就是 pip install，零外部依赖；嵌入在 Python 进程内，没有独立服务需要监控重启；三个 API 解决所有操作；百级     
  chunk 下 HNSW 默认参数的召回率和延迟完全够用；未来如果换引擎，只需要改 VectorStore 这一个适配层。

  ChromaDB 的明确局限我也清楚。第一，单机部署不支持分布式，数据量到十万级 chunk 时索引内存会到几十
  GB，单机扛不住，必须换引擎。第二，没有内置高可用，进程崩了检索链路就中断，没有主从或副本自动切换。第三，它的 where
  过滤是向量检索之后的后过滤，不是索引阶段的前置裁剪——如果你需要按模块或时间范围过滤，白白检索了全量再扔掉大部分，目前我们没有复杂过滤需求所以不
  受影响。第四，持久化依赖本地磁盘的 SQLite 加二进制文件，没有备份机制。当前两千条 chunk
  的重建成本不到半分钟，所以没做冷备，但如果规模到万级，必须规划定期备份。

  **嵌入式 vs 集中式：一个需要显式做的设计决策**

  ChromaDB 支持两种运行模式：PersistentClient（嵌入在 Python 进程内，直接读写本地文件）和 `chroma run`（独立 server 进程，暴露 HTTP 端口，多个 client 通过网络连接）。我们的 4 节点部署有两种选法：每个 FastAPI 节点各嵌一个 ChromaDB，或者单独跑一个 ChromaDB server 四个节点共用。

  这个决策的关键变量是**读写比例**。我们日均 100 次查询（读），文档更新（写）由管理员手动触发，频率可能几天甚至一周一次——读写比超过 1000:1。这意味着读路径上的代价放大 1000 倍，写路径上的代价只放大 1 倍。

  两个方案在四个维度上的对比：

  **读延迟**：嵌入式是进程内函数调用，0ms 网络开销。集中式每次检索走一次 HTTP 往返，1~2ms。在 2000 chunk、HNSW 检索 3ms 的前提下，集中式的网络开销相当于检索本身的 30%~60%，无谓浪费。

  **读可用性**：嵌入式下，某个节点的 ChromaDB 崩了，只影响路由到该节点的请求（约 1/4 流量）。集中式下，ChromaDB server 崩了，4 个节点同时停摆，100% 流量不可用。单点故障的影响半径差 4 倍。

  **写一致性**：这是集中式唯一有优势的维度——写一次，所有节点读到同一份数据。嵌入式下，文档更新后必须让 4 个节点都拿到新索引，否则不同节点返回不同答案。

  **部署复杂度**：嵌入式零额外进程，ChromaDB 随 FastAPI 进程启动而启动。集中式多一个 server 进程要配置、监控、守护，出问题的排查范围更大。

  嵌入式在三个维度上赢，只在写一致性上输。但写一致性的代价能不能接受？我们的更新流程是管理员手动触发，4 个节点各自独立执行一遍切分 + embedding + 入库，全程约 30 秒。每次更新多花的 embedding API 调用量是 2000 chunk × 4 = 8000 次，在内部 API 下成本忽略不计。同步方案更简单：更新完成后，比较 4 个节点的 chunk 总数是否一致（一个简单的健康检查），不一致就重跑。

  反过来，集中式在写路径上省的那点事，换来的是一个全局单点——Q27 整篇讨论的"挂了怎么办"，换成嵌入式后直接消失。

  所以选嵌入式。核心逻辑：**在读写比极度悬殊的场景下，把复杂度放到写路径上，换取读路径的更优性能和更高可用性**。这和 Q26、Q27 的部署架构是一致的——4 个节点各自独立、无共享状态、某个挂了不影响其他。


**Q8.** 向量检索走的是哪个相似度度量？cosine、dot product 还是 Euclidean？为什么？你做 A/B 测试验证了吗？
 阿里 text-embedding-v3 的模型文档明确说明输出向量经过 L2 归一化，向量落在单位超球面上，语义由方向决定而非向量长度。所以我在 ChromaDB
  collection 里显式指定 cosine 相似度，与模型的输出特性完全对齐。

  补充一点：因为向量已归一化（模长均为 1），cosine 和 L2 在数学上排名等价——L2² = 2(1 - cos_sim)，单调关系保证了排序结果完全一致。所以即
  便误配了 L2，检索结果也不会出错。但显式声明 cosine 有两层意义：第一，它直接对应模型的训练目标，避免了"相似度度量与模型不匹配"的潜在隐患；第二，
  它让后续维护者一眼看懂设计意图，不会在排查问题时产生"这里是不是设错了"的疑虑。


### 1.3 索引 & 检索策略

**Q9.** 你是不是只做了向量检索？有没有做混合检索（hybrid search）？比如 BM25 + 向量？如果有，怎么融合两个通路的分数的？用的是 RRF（Reciprocal Rank Fusion）还是线性加权？融合参数怎么调的？

我们没有只做向量检索，做的是向量加 BM25 双路混合检索。整个检索链路的入口是先做 query 改写，再走双路检索，最后 RRF 融合。

整个流程是：用户问题进来后，先经过 query 改写步骤。改写器做两件事：一是用 LLM 将用户的口语化表述改写为文档风格的专业表述，比如把"手机收不到短信"改写为"SMS通知渠道未收到告警"；二是通过一个动态映射表，将用户常用的非专业词汇替换为系统内的专业术语，比如"OA"映射为"优化顾问"、"那个监控"映射为"OA监控告警"。映射表存储在动态配置中，可以在运行时直接修改，不需要重启服务或重新部署。映射表的维护来源是线上 bad case 复盘——用户点击"没用"的反馈会被记录下来，包括原始 query、改写后的 query、以及最终检索结果。在项目上线后的前一个月，我们每天都会看这些 bad case 日志，分析是改写步骤出了问题还是检索步骤出了问题。如果改写出了问题，就更新映射表；如果是检索出了问题，就排查是 jieba 分词错误还是 embedding 召回失败。

改写之后，query 并行进入两条检索通路。

向量路：用阿里 text-embedding-v3 对改写后的 query 做 embedding，进 ChromaDB 的 HNSW 索引做余弦相似度检索，返回 top-k 个候选。向量检索擅长语义相似和同义改写，但对精确关键词、专有名词、缩略语的匹配能力弱。

BM25 路：用 jieba 分词 + BM25 算法生成稀疏向量，存入 ChromaDB 的 sparse index 做关键词检索，同样返回 top-5 个候选。不是 ChromaDB 内置的——ChromaDB 负责存储稀疏向量和做 RRF 融合，BM25 的评分计算（TF 饱和 + IDF 加权 + 长度归一化）在外部用 rank_bm25 库完成。这样分词逻辑完全在自己控制下，自定义词库的热加载不受 ChromaDB 内部实现的影响（原理详见 Q17-附）。BM25 擅长精确关键词匹配，正好弥补向量路在专有名词和缩写上的盲区。分词器用的是 jieba，因为我们的文档是中文技术文档，有大量内部术语，默认词库切不准。我们维护了一套自定义词库，包含业务专有名词和缩写，比如"优化顾问"、"region白名单"、"多AZ"、"SMS通知"等。词库同样支持运行时热加载，发现新术语后添加到词库文件，调 reload 接口即刻生效。词库的维护来源和映射表一样，来自线上 bad case 复盘——如果发现是因为分词错误导致 BM25 路失效，就加词库。

两路结果通过 RRF（Reciprocal Rank Fusion）融合成最终候选列表。选 RRF 而不是线性加权的原因是：向量检索的余弦相似度和 BM25 的 TF-IDF 分数量纲完全不同，直接线性加权会有一路分数被另一路淹没。RRF 只关心排序位置，天然规避了量纲问题。公式是 score = alpha/(k+rank_vec) + beta/(k+rank_bm25)，k 取 60，这是 RRF 论文的经典取值——k 在 60 附近结果对此参数不敏感，学界和工业界广泛沿用，我们没有单独调它。

alpha 和 beta 当前都设的是 0.5。我做过网格搜索：在 100 条 QA pairs 上，α 从 0 到 1 以 0.1 为步长（β = 1 - α），11 组参数分别计算 RRF 融合后的 MRR 和 Recall@5。结果最优值落在 α=0.5 附近，且偏离不大时指标变化也很平缓，说明两路检索贡献均衡，所以就取了等权 0.5。这个搜索不需要重跑检索——两路的排序结果早就有了，改 α/β 只是重新算融合分数，一秒跑完。

关于要不要加第三路，我评估过 HyDE 和 Small-to-Big。HyDE 的核心思想是用 LLM 生成假设答案，把"问题 vs 答案"的匹配变成"答案 vs 答案"的匹配。经典 HyDE 不适合私有知识场景，因为 LLM 不了解内部文档，凭空生成的假设答案用词对不上。但有一个变体可行：先跑一轮快速向量检索取 top-3，把真实 chunk 给 LLM 让它基于真实内容生成假设答案，再做第二轮检索——这样风格和术语都来自真实文档。我没有实施，因为当前双路效果已满足指标，且我们的改写器已经在做风格对齐的工作。Small-to-Big 是返回时把命中小 chunk 所属的父文档一并返回，不改检索逻辑所以不提升 MRR，但提升答案完整度。没有实施是因为当前未发现因上下文不足导致的生成 bad case。两路到三路有边际收益，但三路以上收益递减明显，双路是当前业务的最优平衡。

评测指标方面，我们的 100 条 QA pairs 评测集按问题类型拆成两组：单答案型（只有一个正确 chunk）用 MRR，综合推理型（需多个 chunk 共同支撑）用 Recall@5。为什么多 chunk 场景不用 NDCG？NDCG 的设计依赖分级相关性——需要标注"这个 chunk 比那个更相关"才能发挥位置加权的作用。我们的标注是二元的（相关/不相关），所有正确答案 chunk 之间没有优先级之分——只要都在 top-5 里就够了，它们之间的相对顺序没有业务意义。Recall@5 直接回答"用户看到了多少相关知识"，简洁、可解释。

**Q10.** 有没有做 query 改写（query rewriting）？有没有做 HyDE（假设文档嵌入）？有没有做 multi-query / query decomposition？如果都没做，复杂问题怎么处理？

Query 改写做了。我们内部系统有大量专有名词和别名——比如"OA"就是"优化顾问"，"那个监控"就是"OA监控告警"。不做改写的话，用户用自己的话搜，根本对不上文档里的正式术语。我们的方案分两层：第一层是动态映射表，维护了专有名词到标准术语的映射关系，放在配置中心，运行时热加载，用户输入先过一遍映射表做术语替换；第二层是 LLM，对替换后的 query 做口语化去除，把自然语言风格对齐到文档风格。两层串行，先替换再改写。

HyDE 没有做，原因分两层说。经典 HyDE 是让 LLM 凭空生成一个假设答案，再用假设答案去做向量检索。这在我们的场景下有明显问题：我们的文档全是内部专有知识，LLM 不了解这些内容，生成的假设答案在术语上大概率出现幻觉——比如它可能会编一个不存在的配置项名称——然后拿着这个错误的答案去做检索，不仅帮不上忙，反而把检索带偏了。改进版的 HyDE 可以规避这个问题：先 rewrite query，跑一轮快速检索取 top-3 真实 chunk，把真实内容给 LLM 让它基于此生成假设答案，再做第二轮检索。这样术语锚定在真实文档上，不会跑偏。但这个方案的代价是链路变成两轮检索，端到端延迟翻倍。在当前 500 文档、日均 100 问的规模下，我们的双路混合检索效果已经够用，改进版 HyDE 的边际收益不足以覆盖延迟代价。后续我们会根据线上用户反馈数据——被踩的答案、漏到人工群的问题——来评估是否需要引入，优先级当前不高。

Multi-query 是指把同一个问题改写成多个不同表述，多路并行检索后合并结果。Query decomposition 是把一个复杂问题拆成多个独立的子问题，各自检索不同信息源，最后汇总。这两个技术本质上和改进版 HyDE 有相同的 tradeoff：检索轮次增加，链路变长，延迟上升。在当前阶段我们都没有采用。

目前复杂问题的处理不靠拆解或多次检索。我们的混合检索本身对多 chunk 召回能力足够——综合推理型 Recall@5 0.892 说明多相关 chunk 的召回质量在线。生成阶段 LLM 拿到 top-k 个 chunk 后自行综合多段信息推理。后续如果复杂问题的比例上升，或者线上 bad case 分析发现「多信息源漏召回」是主要瓶颈，我们会优先试 query decomposition，因为它解决的是信息覆盖面的问题，比 multi-query 的重表述更有针对性。

**Q11.** 检索结果你做重排序（rerank）了吗？用了什么 rerank 模型？是 cross-encoder 还是 bi-encoder？rerank 的延迟增加了多少？值得吗？消融实验数据有吗？

做了 rerank。先说明当前检索链路中各环节的 chunk 流转数量：向量检索返回 top-5，BM25 返回 top-5，两路经过 RRF 融合去重后约 8 个候选，Qwen3-rerank 对这 8 个候选做精排，最终输出 top-5 给 LLM。

为什么需要 rerank：我们的文档是内部专有知识，大量语义相近但实际不相关的片段——比如多个文档都可能提到"告警配置"，但分别讲的是不同产品的告警。向量检索和 BM25 在这种场景下容易把语义相近但不相关的 chunk 一并召回，造成干扰。Rerank 在这里起两个作用：一是精筛，用更强的模型精确判断 query 和 chunk 的相关性，把干扰片段过滤掉；二是压缩，从 8 个候选砍到 5 个高质量 chunk 喂给 LLM，减少输入噪声，提升生成质量。

Rerank 的实现方式有两种。一种是 cross-encoder：专门的 relevance 评分模型，把 query 和 doc 拼接后做全注意力推理，输出一个相关性分数。模型小、推理快、成本低，是目前 RAG 场景的主流方案。另一种是 LLM-based rerank：把候选文档和 query 一起给 LLM，让 LLM 判断相关性并排序，可以拿到更细致的语义判断，但延迟和成本远高于 cross-encoder，适合对延迟不敏感的高精度场景。我们用的是第一种——阿里内部部署的 Qwen3-rerank，cross-encoder 架构，内网私有化，不走公网 API。选它没有做多模型对比，因为合规约束下内部可用的 rerank 模型就这一个，选型空间不存在。

消融实验做了。同一批 100 条 QA pairs，不加 rerank（仅 RRF 融合取 top-5）vs 加 Qwen3-rerank 精排后取 top-5，对比结果：单答案型 MRR 从 0.831 提升到 0.868；综合推理型 Recall@5 从 0.892 提升到 0.914。MRR 提升 +0.037（4.5%），Recall@5 提升 +0.022（2.5%）——MRR 的涨幅明显更大，因为 rerank 做的是重排和裁剪，不增加新 chunk，所以排序质量（MRR）的提升幅度大于覆盖率（Recall@5）。

延迟方面，rerank 阶段增加约 100ms（8 个候选逐个过 cross-encoder），对于日均 100 问的 QPS 来说完全在可接受范围内。换回的是进入 LLM 的上下文从可能混杂了无关片段的 5 个，变成高相关度的 5 个，生成质量明显提升。收益大于代价。

**Q12.** 500个文档，500 * 平均每个文档多少 chunk？你的索引规模有多大？检索延迟是多少？P99 延迟呢？

500 个文档切分后共约 2000 个 chunk，平均每个文档 4 个 chunk，中位数在 3~5 之间。

索引规模分两块说。

向量索引：2000 个 768 维 float32 向量，裸向量存储 2000 × 768 × 4 bytes ≈ 6MB；HNSW 图结构——每个节点维护 M=16 条出边，额外约 2000 × 16 × (4+4) ≈ 0.25MB——可以忽略。总计向量索引约 6MB。

BM25 倒排索引：对 2000 个 chunk 做 jieba 分词后构建倒排表。词典大小约 5 万个 term，每个 term 对应一条 posting list，里面存的是 (chunk_id, term_frequency) 对。平均每个 term 出现在约 10 个 chunk 中，每条记录 8 bytes，posting list 总计约 5万 × 10 × 8 = 4MB；词典本身（term string + IDF 值）约 3MB。总计 BM25 索引约 7MB。

ChromaDB 元数据（file_name、chunk_index、chunk_hash、原文 content）约 5MB。三项加起来约 18MB，不到 20MB，完全在内存中，没有任何磁盘 I/O。

检索原理分开讲。

向量检索用的是 ChromaDB 内置的 HNSW（Hierarchical Navigable Small World）算法。HNSW 是一个多层图结构——可以把最上层想象成"高速公路"，节点少、跨度大，用来快速定位大致区域；逐层向下，图越来越密集，节点越来越多，用来精细搜索。检索时从顶层随机入口点出发，贪心地往离 query 向量更近的邻居节点跳；进入下一层后继续贪心搜索，直到最底层的 top-k 个最近邻。为什么不用暴力遍历？因为 2000 个向量暴力算余弦相似度是 O(N)，而 HNSW 通过图结构跳转做到近似 O(log N)，在 2000 这个规模下虽然绝对差距不大，但框架自带、零额外成本。HNSW 是近似搜索，靠 ef_search 参数控制召回精度——我们设的是 100，在速度和召回之间偏保守，实测 Recall@5 没有因近似而损失。

BM25 是 TF-IDF 的改进版，核心公式可以拆成三个因子的乘积。第一个是 term frequency 因子：一个词在文档中出现的次数——但加了饱和函数，出现 3 次和出现 10 次权重差距不大，避免了长文档天然占优。第二个是 IDF（逆文档频率）：稀有词权重高、常见词（如"的"、"是"）权重趋近于零——这个设计让专有术语天然获得高权重，比如"优化顾问"只在少数文档出现，IDF 值很高。第三个是文档长度归一化：文档越长，词频的贡献越被稀释，防止长文档在评分上占便宜。检索时 query 先过 jieba 分词，对每个 term 查倒排索引的 posting list，累加匹配 chunk 的 BM25 分数，最后按分数降序取 top-5。

BM25 在我们场景中和向量检索是互补的。向量擅长语义——用户搜"怎么配告警"能召回"告警配置指南"即使没出现"配"这个词；BM25 擅长精确——搜"region 白名单"能精确命中含这个词的 chunk，向量检索反而可能被语义相近但不含这个词的内容干扰。

两路并行检索各取 top-5，通过 RRF（k=60）按排名倒数加权融合去重，得到约 8 个候选，送入 Qwen3-rerank 精排后取 top-5 给 LLM。

检索延迟：Embedding 推理走内部 gRPC 调用，单条 query P50 约 30ms、P99 约 60ms。向量 HNSW 搜索约 3ms，BM25 分词+倒排查询约 2ms——两路并行，取较慢的那路，双路检索 P50 约 5ms、P99 约 15ms。合并检索阶段（Embedding + 双路）P50 约 35ms、P99 约 80ms。加上 Qwen3-rerank 的 ~100ms（见 Q11），LLM 生成前的完整检索链路 P50 约 135ms、P99 约 180ms。当前日均 100 问，QPS 峰值不到 1，延迟完全不是瓶颈。

### 1.4 评估体系

**Q13.** 你整个 RAG 系统的效果怎么评估的？有离线的评估数据集吗？规模多大？怎么构建的？谁标的？标注一致性（inter-annotator agreement）测了吗？

评估体系分两轨：离线评测定基线，线上反馈做持续校准。离线评测用标注好的 QA pairs 跑检索和生成指标，每次发版前跑一轮，确保不退化。线上反馈收集用户点踩和漏到人工群的问题，定期回流扩充评测集。

离线评估数据集目前 100 条 QA pairs。构建方式分三步：

第一，问题收集。来源是内部用户群的真实提问，筛选有明确答案、可追溯到具体文档的问题，去掉了闲聊和重复。第二，分层抽样。按文档类型（API 类、故障类、功能细节类、版本类）和问题热度做分层，高频问题约占八成，冷门问题刻意保留了一到两成，避免评测集偏向热门场景导致评测结果虚高。第三，标注。每条 query 对应标注的是正确的 chunk ID 作为 ground truth，标注人是我自己——逐个读了 query 对应的文档，确认哪个 chunk 能正确回答这个问题。

坦诚说，标注一致性没有测。Ideally 应该至少两人独立标注同一批数据，计算 Cohen's Kappa 或 Krippendorff's Alpha 来验证标注的可重复性。我没有做是因为团队里没有第二个对整个文档集同样熟悉的人，单人标注是现实约束下的妥协。我清楚这带来的风险：标注质量完全依赖我个人的判断，如果我在某类问题上存在系统性偏见（比如倾向于标注更长的 chunk），评测结果会带偏。

评测的执行流程：每次发版前跑一轮全量评测。脚本自动化执行——对每条 query 走完整检索链路（Embedding → 双路检索 → RRF → Rerank），拿到 top-5 chunk ID 列表，和 ground truth chunk ID 做比对，输出两项指标（MRR、Recall@5）的汇总报告。单条 query 的检索结果和 ground truth 的 diff 也会输出，方便逐条排查。

评测集的维护依赖线上日志系统持续供给数据。我们实现了一套 QueryLog 系统，基于 SQLite（data/queries.db），15 个字段。每次 /ask 请求——无论缓存命中还是完整检索——都会写一条日志，记录 user_id、original_question、rewritten（改写后）、latency_ms（端到端延迟）、vector_hits（JSON 数组，向量召回的 chunk 列表）、bm25_hits（BM25 召回的 chunk 列表）、final_count（RRF+Rerank 后结果数），以及 src_vector/src_bm25/src_both 三个来源分布字段。设计上"只写不读"——不提供查询 API，日志写入失败只记 warning 不抛异常，schema 迁移直接删旧表重建（数据不保留）。

线上反馈的入口有两个。一是前端页面的点踩按钮，点踩时将 user_click 字段回写到对应的日志记录中。二是漏到人工群里才能解决的问题——根据提问人的 user_id 去 QueryLog 搜索该用户最近的 /ask 记录，按问题内容匹配到对应那条日志，实现群聊问题和检索日志的关联。这些反馈数据定期（目前是每两周）审核后，标注 chunk ID 作为 ground truth，补充到评测集中。因为有 QueryLog 保留了每次检索的完整命中列表，回溯时不需要复现——直接查日志就能看到当时召回了哪些 chunk、哪个才是正确的。

**Q14.** 检索模块单独怎么评估？你用的 Recall@K、MRR、NDCG 哪个？K 选多少？为什么？

检索模块独立评估用的是同一批 100 条 QA pairs（和 Q13 同一个评测集），但只跑到 Rerank 输出的 top-5 就停下，不接 LLM 生成——纯测检索链路的质量。

指标按问题类型拆成两组：

**单答案型问题**（query 只有一个正确 chunk 能回答）：只用 MRR（Mean Reciprocal Rank）。MRR 衡量正确答案在返回列表中的排名——排第一得 1，排第三得 1/3，排第五得 1/5——越靠前越好。为什么不用 Recall@1？因为 Recall@1 只区分"排第一"和"没排第一"，信息太粗——正确答案排第 2 和第 50 在 Recall@1 眼里都是 0，但前者离成功一步之遥，后者基本是随机。MRR 能区分这两者，评测粒度更细。

**综合推理型问题**（需要多个 chunk 才能完整回答）：只用 Recall@5。衡量所有相关 chunk 有多少进入了 top-5。为什么不用 NDCG？NDCG 的核心价值在于分级相关性——当你标注了"chunk A 比 chunk B 更相关"时，NDCG 的位置加权能体现排序质量。但我们的标注是二元的（相关=1/不相关=0），所有正确答案 chunk 之间没有优先级之分，它们之间的相对顺序没有业务含义——用户看到的是 top-5 的全部内容，不是逐条翻阅。NDCG 的位置折损系数在二元标注下变成了没有业务依据的惩罚项。Recall@5 直接回答"用户拿到了多少相关知识"，不引入额外假设。

K 值的选取逻辑：单答案型不需要显式设 K——MRR 本身就是 rank-aware 的，不依赖固定 K。综合推理型选 K=5，因为 LLM 拿到 5 个 chunk 做综合推理，我们评估这 5 个里覆盖了多少相关 chunk，评测结果直接反映 LLM 实际拿到的上下文质量。

这个分组评测设计有一个好处：两类指标分别回答两个不同的工程问题。单答案指标回答"用户能不能尽快看到正确答案"——这是端到端体验的核心；综合推理指标回答"多段拼装的答案，底层检索有没有漏掉关键信息"——这是检索能力的底线。

**Q15.** 生成模块单独怎么评估？用了什么指标？基于 LLM 的自动评估（如 RAGAS）还是人工评估？你怎么保证 LLM-as-judge 的可靠性？

生成模块用 RAGAS 做自动化评估。具体做法是：对每条 query，先跑完完整检索链路拿到 Rerank 后的 top-5 chunk，和 LLM 生成的最终答案一起送入 RAGAS 评测管线。RAGAS 的核心思路是用另一个 LLM 当裁判，对生成结果做多维度打分。

我们关注的三个核心指标，以及各自的底层计算原理：

**1. Faithfulness（忠实度）—— 答案有没有编造**

计算分三步。第一步，裁判 LLM 把生成的答案拆成原子化断言（atomic claims），每个断言是一个独立的、可验证的陈述句。比如答案"OA 告警阈值是 80%，告警后 oncall 需在 5 分钟内响应"会被拆成两条：["OA 告警阈值是 80%", "告警后 oncall 需在 5 分钟内响应"]。第二步，裁判 LLM 逐条断言去检索到的上下文中验证：这条断言能不能从上下文里推断出来？输出 Yes 或 No 加判定理由。第三步，Faithfulness = 判定为 Yes 的断言数 / 总断言数。如果 LLM 生成了一段上下文根本没有的信息，对应的断言会被判 No，忠实度直接下降。我们线上阈值设 0.85——即 85% 以上的断言必须有上下文依据。

**2. Answer Relevancy（答案相关性）—— 有没有答非所问**

计算分三步。第一步，裁判 LLM 拿到生成的答案，反向推演：这个答案可能在回答什么问题？生成 N 个反向问题（通常 3~5 个）。比如答案是"SMS 通知渠道需在 OA 告警配置中开启"，反向问题可能包括"如何开启 SMS 通知？""SMS 通知在哪里配置？"。第二步，把这 N 个反向问题的 embedding 和原始用户问题的 embedding 做余弦相似度。第三步，Answer Relevancy = N 个相似度的平均值。如果 LLM 跑题了——比如用户问的是告警配置，答案却大量谈论监控大盘的历史演变——反向问题会和原始问题偏离很远，相似度低，相关性报警。

**3. Answer Correctness（答案正确性）—— 事实有没有搞错**

这个指标需要 ground truth（标准答案）才能计算，所以只覆盖评测集中有标注的 100 条 QA。计算分三步。第一步，裁判 LLM 把生成的答案和 ground truth 各自拆成原子化陈述。第二步，逐条比对分类：TP（True Positive，出现在生成答案中、也在 ground truth 中的正确陈述）、FP（False Positive，生成答案中有但 ground truth 中没有的陈述，即编造或错误）、FN（False Negative，ground truth 中有但生成答案遗漏的陈述）。第三步，算 F1-style 分数：Correctness = |TP| / (|TP| + 0.5×|FP| + 0.5×|FN|)。0.5 的权重意味着 FP 和 FN 各算半个惩罚——漏说和说错都扣分，但不至于一票否决。

为什么选 RAGAS 而不是纯人工评估：100 条 QA × 每次发版跑一轮，人工评一遍要半天，LLM 自动评几分钟搞定，成本差距太大。而且 RAGAS 的打分是可复现的——同一组参数跑两遍结果一致，人工评今天和明天的标准可能飘移。

LLM-as-judge 可靠性的保证措施有四个。第一，裁判模型和生成模型分离——我们用 DeepSeek V4 Flash 做生成，裁判模型用内部统一 API 的另一个模型实例，避免同一个模型既当运动员又当裁判。第二，结构化输出——RAGAS 的 prompt 要求输出 JSON 格式的分数和判定理由，不是开放式评价，减少裁判模型的自由发挥空间。第三，人工抽查校准——发版评测时从 100 条中随机抽 10~15 条做人工复评，对比 RAGAS 分数和人工判断的一致性。目前 Faithfulness 的人工-RAGAS 一致率约 85%，Answer Relevancy 约 80%。第四，阈值设保守——Faithfulness 阈值设 0.85 而不是 0.9，留出裁判模型的误差余量，避免因为裁判判断偏严造成过度报警。

**Q16.** 端到端的评估你做了吗？指标是什么？跟纯人工回答比，你们系统的正确率、用户满意度、拦截率分别是多少？这些数字有统计显著性检验吗？

## 二、在线阶段（推理链路、性能、稳定性、迭代）

### 2.1 Query 理解 & 路由

**Q17.** 用户问题进来之后，整个请求链路是什么样的？从接收请求到返回答案，每一步做了什么？画一下链路你能说清楚吗？

整个链路在 FastAPI 的 /ask 端点里，分两条路径——缓存命中走快速通道，缓存未命中走完整检索。下面按完整检索路径逐段说。

**第一步：语义缓存检查**

Query 进来先做 Semantic Cache 匹配。我们用的不是精确字符串匹配，而是把 query embedding 之后和缓存中的历史 query embedding 算余弦相似度，相似度超过阈值则认为语义等价，直接返回缓存答案。缓存命中时端到端延迟可以控制在几十毫秒内——跳过后续所有检索和生成步骤。缓存未命中则进入完整链路。

**第二步：Query 改写（两层串行）**

第一层是动态映射表：放在配置中心、运行时热加载，维护了内部专有名词 → 标准术语的映射（如"OA" → "优化顾问"、"那个监控" → "OA监控告警"），query 先过一遍做术语替换。第二层是 LLM 改写：对替换后的 query 做口语化去除，把用户闲聊式表达对齐到文档风格。两层串行——先替换、再改写——保证专有名词不被 LLM 误改写。

**第三步：Embedding 推理**

改写后的 query 走内部 gRPC 调用 text-embedding-v3 模型，生成一个 768 维的归一化向量。这一步 P50 约 30ms，P99 约 60ms，是检索延迟的大头。

**第四步：双路并行检索**

Embedding 出来后分两路并行执行，各取 top-5：

- 向量检索：768 维向量在 ChromaDB 的 HNSW 索引上做近似最近邻搜索。HNSW 是分层图结构，从顶层稀疏图快速定位区域，逐层向下精细搜索。ef_search=100，搜索复杂度 O(log N)。返回 top-5 个最相似的 chunk，每个结果带余弦相似度分数。

- BM25 检索：query 过 jieba 分词（加载了内部专有词典），对每个 term 在内存倒排索引中查 posting list，累加 BM25 分数（TF 饱和 + IDF 稀有词加权 + 文档长度归一化），返回 top-5 个关键词最匹配的 chunk。

两路并行，总耗时取较慢的那路——P50 约 5ms，P99 约 15ms。

**第五步：RRF 融合去重**

向量 top-5 和 BM25 top-5 通过 RRF（Reciprocal Rank Fusion，k=60）融合。公式是 score(chunk) = 1/(k+rank_vector) + 1/(k+rank_bm25)，按融合分降序排列。两路重合的 chunk 因在两边都有排名而分数叠加、自然排前。去重后得到约 8 个候选 chunk。

**第六步：Rerank 精排**

8 个候选逐个送入 Qwen3-rerank（cross-encoder 架构），每个候选将 query 和 chunk 拼接后做全注意力推理，输出一个精确的相关性分数。8 个候选按分数降序排列，取 top-5 作为最终喂给 LLM 的上下文。这一步增加约 100ms 延迟。

**第七步：LLM 生成**

Rerank 后的 top-5 chunk 拼入 prompt template，连同 system prompt 和原始 query 一起发给 DeepSeek V4 Flash 做生成。Prompt 中每个 chunk 附带来源标注（file_name + 标题路径），方便 LLM 在回答中引用。生成阶段是整个链路延迟最大的部分，取决于输出 token 数。

**第八步：写 QueryLog**

无论缓存命中还是完整检索，/ask 的每次请求都写一条日志到 SQLite（data/queries.db）。日志记录 15 个字段，包括 user_id、original_question、rewritten、latency_ms、vector_hits（JSON 数组）、bm25_hits（JSON 数组）、final_count、src_vector/src_bm25/src_both 来源分布、user_click。user_id 来自请求上下文的登录态（企业内网统一认证），和聊天工具里的用户账号是同一个，这个字段是后面人工群反馈回溯的关键（详见 Q29）。日志写入失败不抛异常、只记 warning——不能因为日志挂了影响主链路。

**一步汇总（chunk 数量的流转）：**

Query → 改写 → [向量 top-5 + BM25 top-5 并行] → RRF 去重 ~8 → Qwen3-rerank → top-5 → LLM

**延迟预算分配（P50）：**

Embedding ~30ms → 双路检索 ~5ms → Rerank ~100ms → LLM 生成（取决于输出长度）。检索链路（Embedding + 检索 + Rerank）P50 约 135ms。

**Q17-附：完整链路原理——从文档到答案，每一步到底在做什么**

这个问题不是面试题，是我自己梳理系统时写的。目的是把离线建库和在线查询两条链路从头到尾串一遍，说清楚每个组件在做什么、输入输出是什么、为什么放在这个位置。不涉及具体参数调优（Q1~Q17 已经覆盖了），只讲**原理和数据流**。

**一、先理解两个基本概念**

在往下走之前，需要先搞懂这个系统里最核心的两个东西：**向量** 和 **BM25**。

**什么是向量？** 向量就是一串数字。比如 `[0.23, -0.15, 0.78, ...]` 一共 768 个数。这串数字的特殊之处在于：它编码了一段文字的"语义"。两段意思相近的文字——比如"怎么配置告警阈值"和"如何设置监控报警的门限值"——它们对应的向量在数学上距离很近（余弦相似度高）。两段意思无关的文字——比如"告警配置"和"今天午饭吃什么"——它们的向量距离很远。这就是向量检索的核心能力：**不靠关键词匹配，靠语义距离匹配**。

向量是由 **Embedding 模型**（text-embedding-v3）生成的。这个模型是一个训练好的神经网络——你喂一段文字进去，它吐出 768 个浮点数。整个过程就是一次数学计算（矩阵乘法 + 激活函数），没有查表、没有规则匹配。模型在训练阶段见过海量中文文本，学会了"意思相近的词应该有相近的向量表示"。部署在内网，我们通过 gRPC 调用。

**什么是 BM25？** BM25 是纯统计公式，不走神经网络。它做的事情可以用一句话概括：**如果一个词在某个文档里出现次数多、但在整个文档集里很稀有，那这个词对这个文档的"代表性"就强**。比如"region白名单"在 500 篇文档里只出现 5 次，但在某篇文档里出现了 3 次——那搜"region白名单"时，这篇文档的分数就很高。反过来，"配置"这个词出现在 400 篇文档里——到处都有，区分度低，即使在某篇里出现多次，加的分也有限。

这个直觉被量化成了 BM25 公式里的三项：

- **TF（词频）**：这个词在这个文档里出现了几次？多次出现加分，但有上限（饱和），防止某个词出现 50 次就把分数撑爆。
- **IDF（逆文档频率）**：这个词在整个文档集里有多稀有？越稀有，权重越高。"region白名单"的 IDF 远高于"配置"。
- **长度归一化**：同样的词频，在短文档里比在长文档里更有代表性——长文档天然词多，需要惩罚。

三项乘法叠加，就是 BM25 的分数。整个过程不需要 GPU、不需要 API 调用，就是小学数学，在内存里毫秒级完成。

**两者怎么分工？** 向量擅长"意思相近但用词不同"的匹配——"告警怎么配"和"监控告警配置指南"之间没有公共关键词，但向量能识别语义相近。BM25 擅长"精确关键词匹配"——搜"region白名单"就一定能命中含这个词的文档，不会被语义相近但不相关的内容干扰。两者互补，并行检索，这就是混合检索的底层逻辑。

**二、离线阶段：把文档变成可检索的数据**

离线阶段做的事：把 500 个 Markdown 文档处理成两种"可检索的形态"，存进 ChromaDB。这个过程由管理员手动触发，每几天一次。

```
                      500篇Markdown文档
                            ↓
              MarkdownHeaderTextSplitter
              按标题层级语义切分
                            ↓
                     ~2000个chunk
                    每个 ~384 token
                     /            \
                    /              \
        【路A：语义向量】      【路B：关键词向量】
                    │                  │
                    │        jieba 分词（加载自定义词库）
                    │        "优化顾问的告警阈值怎么配置"
                    │        → ["优化顾问","的","告警","阈值","怎么","配置"]
                    │                  │
       text-embedding-v3       rank_bm25 计算稀疏向量
       神经网络推理              TF饱和 + IDF加权 + 长度归一化
       768个浮点数               → {term_15: 2.34, term_382: 1.87, ...}
       稠密向量（无零值）         稀疏向量（99%的维度是0）
                    │                  │
                    ↓                  ↓
           ChromaDB                ChromaDB
         dense index            sparse index
        (HNSW图结构)           (倒排索引结构)
```

**切分**：MarkdownHeaderTextSplitter 按文档的一二级标题做结构拆分，每个 chunk 约 384 token。标题路径拼入 chunk 正文头部，让每个 chunk 携带"我来自哪个文档的哪个章节"的信息。

**路A——语义向量（Dense）：** 每个 chunk 送进 text-embedding-v3，输出 768 维的稠密向量。这个向量就是 chunk 的"语义指纹"——两段意思相近的 chunk，向量距离近。全部 2000 个向量存入 ChromaDB，ChromaDB 用 HNSW（分层可导航小世界图）算法为它们建索引。HNSW 的原理：把 2000 个向量按空间距离分层连接成图结构，搜索时从顶层稀疏图快速定位大致区域，逐层向下精细查找，复杂度 O(log N)，2000 个向量单次检索约 3ms。

**路B——关键词向量（Sparse）：** 每个 chunk 先用 jieba 分词切成词列表，然后通过 BM25 公式算出每个 term 的权重。输出的不是一个 768 维的浮点数组，而是一个"词典大小的稀疏向量"——词典里大约 5 万个 term，每个 chunk 只在它包含的那些 term 上有非零值，其余全是 0。比如某个 chunk 只有 30 个不同的词，那它的稀疏向量里只有 30 个位置有值。这个稀疏向量同样存入 ChromaDB，ChromaDB 对稀疏向量有自己的索引结构（倒排索引）。

**关键认知：路B 完全没有神经网络参与。** jieba 分词是字典+统计算法，BM25 是纯数学公式。整个路B 不需要 GPU、不需要 API 调用、不需要模型推理——这就是为什么 BM25 路的离线成本几乎为零，在线检索也只需要 2ms。

**两路存完后，ChromaDB 里每个 chunk 有两条记录：** 一条在 dense index（语义检索用），一条在 sparse index（关键词检索用）。同一条原文，两种索引方式，互不干扰。查询时两路并行搜，结果融合。

**三、在线阶段：用户提问到返回答案**

在线链路 Q17 已经逐步骤讲过，这里不重复。从原理角度补充几个关键点：

**为什么需要 Query 改写？** 用户输入的词和文档使用的词不在同一个语义空间。"OA 告警怎么配" → 文档里写的是"优化顾问监控告警配置"。改写做的事就是把用户的日常表述翻译成文档的正式表述——第一层映射表保证专有名词不丢（"OA" → "优化顾问"），第二层 LLM 去口语化。这一步做完，后面的检索才能命中。

**为什么两路要并行？** 因为两路完全独立——向量检索跑 ChromaDB 的 HNSW 图，BM25 检索跑内存倒排索引。共享同一个 query 输入，但不共享任何中间状态。并行执行，耗时取较慢的那路（约 5ms），而不是叠加。

**RRF 为什么不用线性加权？** 向量相似度（余弦，0~1）和 BM25 分数（理论无上限）量纲完全不同——0.9 的余弦相似度和 9.5 的 BM25 分数，没法直接比较谁大谁小。直接加权会导致其中一路的分数把另一路淹没。RRF 只关心排序位置（rank），不管具体分数值——排第一就是第一，不管你得分是 0.95 还是 9.5。这就天然规避了量纲问题。

**Rerank 为什么放在融合之后？** RRF 融合只看排序位置，判断粒度粗。向量 top-5 和 BM25 top-5 去重后约 8 个候选——这里面可能有语义相近但实际不相关的（比如两个不同产品的"告警配置"都被召回了）。Rerank 用更强的 cross-encoder 模型对每个候选做精确的 query-chunk 相关性判断，把干扰过滤掉。Rerank 不增加新 chunk，只做重排和裁剪——8 个进、5 个出。

**LLM 生成这一步到底收到什么？** LLM 收到的不是检索结果本身，而是一个拼好的 prompt。System prompt（角色设定 + 行为约束）+ Few-shot 示例 （展示回答格式）+ Rerank 后的 top-5 chunk 原文（每个标注来源文件名和标题路径）+ 用户原始问题。LLM 基于这些上下文做生成，被要求在回答中为每句话标注引用的 chunk 编号，保证可溯源。

**四、完整数据流一览**

```
【离线：文档 → 索引】
Markdown文档 → 切分 → chunks
                          ├→ Embedding模型 → 768维稠密向量 → ChromaDB dense index
                          └→ jieba分词 → BM25算分 → 稀疏向量 → ChromaDB sparse index

【在线：用户提问 → 答案】
用户query → 改写 → Embedding ─┬→ ChromaDB dense检索 top-5 ─┐
                             └→ jieba→BM25 sparse检索 top-5 ─┘
                                                              ↓
                                                       RRF融合 ~8候选
                                                              ↓
                                                       Rerank精排 → top-5
                                                              ↓
                                                       LLM生成 → 带引用答案
```

这就是整个系统从文档到答案的完整原理。没有再复杂的东西了。

**Q18.** 你怎么判断一个问题是否能回答？有没有做意图识别或者打分？有没有拒答机制？拒答的阈值怎么定的？拒答之后用户看到的是什么？如果你们答错了，用户怎么办？

当前没有做意图识别、也没有做拒答。原因是业务规模小——日均 100 问，用户群是内部同事，问的问题基本都在知识库覆盖范围内。偶尔问到文档里没有的内容，LLM 拿到不相关的检索结果后通常会自然回复"没有找到相关信息"，实际体验上没有造成明显问题。从投入产出比看，为一个日均不到 100 问的系统单独做一套意图分类+拒答链路，ROI 不够。

但如果后续文档覆盖范围扩大、或者用户群扩展到不熟悉系统的团队，「不知道该不该答」会成为真实问题。如果要加，方案分两层。

**第一层：检索质量兜底（轻量、必做）**

在检索链路完成后、LLM 生成前，插入一个质量判断节点。两个信号可以用：

- Rerank 后的 top-1 分数：Qwen3-rerank 输出的最大相关性分数如果低于某个阈值（比如 0.3），说明 8 个候选中没有一个和 query 真正相关。这个阈值不能拍脑袋——需要拉一批「知识库确实没有答案」的 query 跑一遍，画出 rerank 分数的分布，取能区分「有答案」和「没答案」的最优切分点。

- 召回来源重合度：如果向量 top-5 和 BM25 top-5 的交集为 0，且 RRF 融合后 rerank top-1 分数偏低，说明两路检索各自召回的是不同方向的噪声——没有一路真正命中。这个信号可以作为辅助判断。

两个信号都触达阈值时，不进入 LLM 生成，直接返回「抱歉，当前知识库中没有找到相关信息」，并附上用户反馈入口（点踩 + 跳转人工群）。这里要注意：阈值宁可设松不要设严——宁可放几个弱相关的问题去让 LLM 试试，也比把用户挡在外面好。

**第二层：意图分类（重、按需做）**

在 Query 改写之后、Embedding 之前，加一个轻量的意图分类步骤。不是做一个完整的多分类模型，而是用一个 prompt 极短的 LLM 调用做三分类："可回答"（知识库范围内的问题）、"闲聊"（"你好"、"今天天气怎么样"）、"超出范围"（问的是知识库明确不覆盖的领域，比如问竞品产品的配置）。分类为"闲聊"的直接友好回复；分类为"超出范围"的不走检索、直接告知范围边界。

为什么不用传统文本分类模型而用 LLM：内部 query 量小，训练一个分类器的标注成本比调一个 prompt 高得多；LLM 做三分类的 prompt 不到 100 token，延迟在 100ms 以内，对整体链路影响小。

**当前答错的处理**

目前没有自动纠错机制。用户点踩的记录写入 QueryLog（user_click 字段），漏到人工群的问题由人工排查后回复。这些 bad case 会定期回流到评测集。本质上是用人工兜底换工程成本，在日均 100 问的体量下是合理的。

**Q19.** 有没有多轮对话能力？如果没有，上下文信息怎么处理的？用户追问"刚刚那个呢"你怎么应对？

没有多轮对话。每个 /ask 请求是独立的、无状态的——不保存对话历史，不基于上文推理下文。

不做不是因为技术上难，而是场景不需要。我们的系统是内部知识库问答，用户的提问模式是「遇到问题 → 打开页面 → 输入完整问题 → 得到答案」，每个问题自包含。和 toC chatbot 不一样——用户不会来闲聊，也不会说"刚刚那个呢"然后期望系统记得上一轮。实际线上日志里，追问式提问几乎没有。加多轮能力带来的是会话管理、上下文窗口膨胀、用户隔离这些工程成本，但收益趋近于零。

当前如果用户真的打了"刚刚那个呢"，系统会把它当作一个独立问题来处理——改写步骤会尝试还原（如果它被当作口语化表达），但因为没有上文，还原大概率失败，LLM 最终会回复"请提供更具体的问题"。这在实际中没有造成用户投诉。

**如果后续需要加多轮，整体方案分三层。**

第一层：上下文存储架构。多轮对话的上下文需要同时支持「当前活跃会话的热数据」和「历史会话的冷数据」。活跃会话存 Redis，key 格式为 `chat:{user_id}:{session_id}:messages`，value 是最近 N 轮（比如 10 轮）的 query-answer 对，TTL 设 30 分钟对齐网页端 session 生命周期。冷数据落在数据库（MySQL/PostgreSQL），表结构大致是 `conversations(user_id, session_id, role, content, created_at)`，user_id + session_id 建联合索引，翻历史记录时从 DB 拉。这里的核心设计约束是：user_id 永远从认证层解析，不接受客户端传参——请求体里不准出现 user_id 字段，防止横向越权。隔离路径是 API Gateway 验 JWT → 从 token 解析 user_id → Redis key 拼入 user_id → DB 查询带 WHERE user_id = ?。三层都嵌了 user_id，用户 A 不可能读到用户 B 的对话。

第二层：会话管理。前端生成 session_id（UUID），每次 /chat 请求带上。后端从 Redis 读历史、拼接新 query、写入新轮次。session_id 的生成时机有两种选择：一是前端进入对话页时自动创建，二是首次 /chat 时后端创建并返回。前者更简单，后者更安全（防止客户端伪造 session_id 碰撞）。用户切换话题时前端生成新的 session_id，旧的留在 Redis/DB 里可回溯。

第三层：上下文感知生成。构建 LLM prompt 时，不是把历史对话原文全部塞进去，而是取最近 N 轮的摘要拼入 system prompt 的「对话背景」字段。用摘要不用原文的原因：原文每多一轮就多吃一轮 token，留给 retrieved chunk 的空间被挤压，摘要把历史压缩成一句话，上下文窗口的 90% 留给真正的检索结果。摘要的生成可以复用当前 LLM（成本低）或用规则（取前一问的关键实体）。

**附：Claude Code（本地单机）vs 豆包（云端多租户）的上下文存储方案**

两种典型模式，帮助理解多轮对话中"上下文存哪里、隔离怎么做"。

**Claude Code 的模式——本地文件存储。** Claude Code 是单用户单机的 CLI 工具，上下文直接写在本地文件系统里。对话原文和工具调用记录存 JSONL 文件（compact 后压缩为摘要），持久化记忆写 memory 目录下的 Markdown 文件。隔离靠的是操作系统文件权限——谁登录了这台机器、谁就能读这些文件，没有额外的认证层。会话生命周期和进程绑定，进程退出后文件保留在磁盘上，下次启动可以恢复。因为只有一个人用，不存在多租户隔离问题，也不需要 Redis/DB 这套基础设施。方案的复杂度在"怎么存得高效"——对话长了要压缩、记忆多了要索引、跨会话要能回忆——而安全边界不是它要解决的问题。

**豆包的模式——云端多租户存储。** 豆包是 SaaS 服务，成千上万个用户同时用，上下文必须存在服务端、且必须做到用户间严格隔离。技术上分两层：活跃会话存 Redis，key 格式是 `chat:{user_id}:{session_id}:messages`，TTL 设 30 分钟对齐网页端 session；历史会话落 DB，表结构 `conversations(user_id, session_id, role, content, created_at)`，翻历史时查 DB。隔离的核心原则是 user_id 永远从 JWT 解析、不接客户端传参——API Gateway 验签拿到 user_id，Redis key 拼入 user_id，DB 查询带 WHERE user_id = ?，三层都嵌了 user_id，用户 A 不可能访问用户 B 的数据。和 Claude Code 不同，豆包的复杂度不在"怎么存得高效"，而在"怎么保证多租户之间的数据不串"——认证、授权、隔离是这个方案的核心。

两种模式的本质区别：Claude Code 用操作系统文件权限做隔离，豆包用 user_id 做多级隔离。前者适用于单用户场景、部署简单、零依赖；后者适用于多租户场景、需要 Redis + DB + JWT 全套基础设施。

**Q20.** 生成模型用的哪个？为什么选这个？上下文窗口多大？你是怎么组织 prompt 的？做了哪些 prompt engineering？system prompt、few-shot、chain-of-thought，各加了多少？有对比实验吗？

**模型选型：DeepSeek V4 Flash**

用的是 DeepSeek V4 Flash，走内部统一 API。选它的逻辑不是做了一轮多模型对比评测，而是受现实约束：内部合规要求只能用已采购的模型，候选池有限。在可用模型中选 V4 Flash 的理由有三：第一，Flash 变体是 DeepSeek 的轻量版，推理延迟在同系列中最低，适合 Q&A 这种对响应速度敏感的场景；第二，生成质量在内部知识库问答这个任务上够用——文档术语规范、答案结构清晰，不需要最强的推理能力；第三，成本低——日均 100 问，Flash 的 API 单价远低于 Pro 或 V3 完整版。

没有做正式的多模型对比评测。原因同上——候选池小，且更换模型的审批流程比技术验证更重。实际做法是用同一批 100 条 QA 跑了几条典型 case，对比 Flash 和完整版的输出质量，确认没有明显的准确率下降后就定了。

**上下文窗口**

V4 Flash 原生支持 128K token 上下文窗口。我们的实际用量远低于这个上限——Rerank 后 top-5 个 chunk，每个 384 token，加上 system prompt、few-shot examples 和用户 query，单次请求的输入 token 通常在 2500~3500 token 之间。输出 token 视问题复杂度，通常在 100~500 token。上下文窗口不是瓶颈。

**Prompt 组织：System prompt 定基调 + Few-shot 定格式**

这个场景下最有效的 prompt 策略是「System prompt 管行为边界，few-shot 管输出规范」。原因：用文字描述格式要求（"请使用 Markdown、标注来源、关键步骤用编号列表"），LLM 理解的稳定性不如直接给它两个示例让它照着学。示例能编码格式规范——引用怎么标、代码块什么时候用、回答详细到什么程度——比指令更不容易漂移。

当前 prompt 由四段组成：

System prompt（固定，约 200 token）：只定义角色和行为边界。内容——"你是内部技术支持助手，基于提供的文档内容回答问题。只使用文档中明确包含的信息，如果文档中没有相关内容，直接告知用户「当前知识库未覆盖此问题」。不要编造信息。"

Few-shot examples（固定，约 500 token）：2 个示例，展示理想的输出格式。示例的选择有两个原则——第一，示例内容用通用/虚构场景，不引用真实的配置项名称或具体数值，避免文档更新后示例变成错误信息；第二，两个示例分别覆盖不同类型：一个演示「单个配置项的精确回答」（带来源标注、配置值用代码块包裹），一个演示「多步骤操作指引」（用编号列表、每步标注来源）。这样 LLM 无论遇到哪类问题都能找到对应的格式模板。

Context（动态，约 2000 token）：Rerank 后的 top-5 chunk，每个 chunk 附带来源标注——file_name 和标题路径。chunk 按 Rerank 分数降序排列。

User query（动态，约 50 token）：改写后的用户问题。

四段拼装顺序：System prompt → Few-shot examples → Context → User query。System prompt 和 few-shot 在顶层且固定不变，可被 LLM 推理框架的 prefix caching 命中，节省重复推理成本。

关于 few-shot 的一个常见质疑是「示例会过时」。我们的应对方式是不用真实业务数据写示例——示例中的配置文件名、参数名、阈值都是虚构的（如「在 config/service.yaml 中设置 timeout 参数为 30」），只演示格式不传递真实信息。这样即使线上文档频繁更新，示例永远有效。

**为什么没做 CoT**

CoT（Chain-of-Thought）的核心价值是让 LLM 在推理型任务上显式写出思考步骤——数学计算、逻辑推导、多条件判断。我们的场景是检索式知识问答，LLM 拿到 chunk 后做的是信息整理和重述，不是推理。用户问"OA 告警阈值怎么配"，答案是一个确定的配置值，不需要"首先...其次...因此..."的推理链。在当前场景下加 CoT 只会多吃 token、加延迟，不提升答案质量。后续如果出现了需要跨文档推理的问题（比如"A 服务的配置依赖 B 服务的哪个参数"），再针对性加 CoT prompt，而不是全量启用。

**对比实验的意义与取舍**

Prompt 对比实验（A/B 测试不同 system prompt 措辞、不同 few-shot 示例）的工程价值是量化 prompt 变更的影响、防止劣化。但它有前提条件：样本量要够。Prompt 差异对答案质量的影响通常不是「对/错」级别的，而是「好/更好」级别的——需要几十上百条评测才能统计显著。在当前日均 100 问、评测集 100 条的体量下，做正式 A/B 测试的投入产出比不高。务实做法：每次改 prompt 后，人工抽查 20 条典型 case 覆盖不同类型（配置类、操作类、故障类），对比新旧两版输出，肉眼判断有没有退化。这个方法不严谨，但对当前规模够用。

**Q21.** RAG 你是怎么串联的？检索到的文档片段怎么拼进 prompt 的？你有控制 token 预算吗？如果检索结果超过 token 预算你怎么截断？

**串联方式**

RAG 的串联方式不是「检索完 → 把结果一股脑扔给 LLM」，而是在检索和生成之间插了两个处理节点：Rerank 精排 + 来源标注注入。完整链路是 Query → 改写 → Embedding → 双路检索（向量 top-5 + BM25 top-5 并行）→ RRF 融合去重 → Qwen3-rerank 精排取 top-5 → 每个 chunk 注入来源标注 → 拼入 prompt → LLM 生成。这个设计把「检索质量」和「生成质量」解耦了——检索团队调 HNSW 和 BM25 参数时不影响生成，生成团队调 prompt 时不需要关心向量维度和分词词典。

**文档片段怎么拼进 prompt**

Rerank 后的 top-5 chunk 不是直接原文丢进去的。每个 chunk 在拼入 prompt 前会做一次轻量格式化：头部追加一行来源标注（格式为 `文件: {file_name} > {标题路径}`），原始内容保持不动。这样 LLM 看到的是「带来源标签的文档片段」而不是裸文本。chunk 按 Rerank 分数降序排列——最相关的排最前，LLM 的注意力机制天然更关注靠前的内容，相当于在 prompt 层面又做了一次隐式的优先级排序。

拼入位置在 System prompt 和 Few-shot examples 之后、User query 之前（详见 Q20 的 prompt 模板）。Context 区域用分隔线与 System/Few-shot 区隔开，防止用户 query 中可能包含的对抗性文本污染检索结果区域。

**Token 预算控制**

当前没有做显式的 token 预算控制。原因是规模小、安全边际大。Rerank 输出的 top-5 chunk，每个 384 token，5 个加起来约 2000 token。加上 System prompt（200 token）、Few-shot（500 token）、User query（50 token），单次输入总量约 2750 token。而 DeepSeek V4 Flash 的上下文窗口是 128K token，实际用量不到窗口的 3%。输出 token 通常在 100~500 token，也不构成压力。

没有做截断策略的原因也在这里——当前窗口利用率太低，截断逻辑纯属多余。但这里有两点需要明确：

第一，如果真的需要截断（比如后续将 top-5 扩展到 top-20、或者单 chunk 从 384 扩展到 1024），截断策略应该在 chunk 层面做而不是 token 层面做。Token 级截断会把一个 chunk 从中间切断，破坏语义完整性。正确做法是按 chunk 逐个叠加，累计 token 数 + 下一个 chunk 的 token 数超过预算时就停止，而不是把最后一个 chunk 截半截。这样 LLM 拿到的每个 chunk 都是完整的。

第二，截断位置不应该在 Rerank 后——如果 token 预算紧张（比如只够 2 个 chunk），应该回到 Rerank 的分数排序上，取前 2 个完整的，而不是取 5 个然后切碎。这个决策顺序保证了「截断的是最不相关的内容，而不是最相关内容的尾部」。

**补充：为什么没有用 LangChain 的链式调用**

没有用 LangChain 的 Chain/LCEL 做 RAG 串联。说实话，链路简单本应是 LangChain 最擅长的场景——线性流水线正是它的 Chain 抽象设计的初衷。但在这个项目里，不用它的原因反而是：7 行 Python 比 LangChain 更简单。

看一下两者对比。我们的 RAG 链路写成显式 Python：

```python
query = rewrite(original)                        # 1. 改写
emb = embed(query)                               # 2. 向量化
vec_hits = vector_search(emb, top_k=5)           # 3. 向量检索
bm25_hits = bm25_search(query, top_k=5)          # 4. BM25 检索
merged = rrf_fusion(vec_hits, bm25_hits, k=60)   # 5. RRF 融合
final = rerank(query, merged, top_k=5)           # 6. Rerank 精排
answer = llm.generate(query, final)               # 7. 生成
```

每一步的输入输出是什么类型、什么形状，一目了然。调试时想在第 4 步后看 BM25 召回了什么——加一行 `print(bm25_hits)` 就完事了。

如果用 LangChain LCEL 实现同样的链路：

```python
chain = (
    rewrite_runnable
    | embed_runnable
    | vector_search_runnable
    | (lambda x: {"vec": x, "bm25": bm25_search(query, top_k=5)})
    | rrf_runnable
    | rerank_runnable
    | llm_runnable
)
result = chain.invoke(query)
```

表面上看也是几行，但实际上付出了这些成本：每一步要包装成 LangChain 的 Runnable 接口、理解 `|` 操作符的隐式数据传递规则、理解 LCEL 的并行/串行语义、出问题时在抽象层里定位哪一步挂了。而且 LangChain 的版本更新频繁，API 断舍离是常态——今天能跑的 Chain 写法，升一个小版本就可能报 deprecation warning。

核心判断：当你的链路用显式 Python 写出来不超过 10 行、且每一步的中间结果需要频繁检查调试时，LangChain 提供的「编排便利」抵不上它引入的「抽象成本」。换一个场景——比如链路有 30 步、有条件分支、有并行/重试逻辑——LangChain 的价值就凸显了。但在这个项目里，7 行 Python 就是最优解。

**Q22.** 生成的时候有没有引用（citation）？用户怎么知道答案来源于哪个文档？如果答案是错的，用户怎么追溯到原始文档去验证？

当前已实现了内联引用系统。之前只有「来源展示」（回答末尾贴文件名列表），后来加上了真正的引用编号和原文展开能力。

**当前状态**

传给 LLM 的 context 是 chunk 原文拼接（`"\n\n".join(r["text"] for r in results)`），没有给每个 chunk 加编号标签。LLM 拿到的是一坨纯文本，不知道 chunk 边界在哪，无法在回答中标注引用。

SSE 事件流中前端能拿到每个 chunk 的完整元数据——doc_id、filename、text、score、chunk_index，但只用于展示文件名列表和 chunk 前 120 字预览。用户看到答案后能看到文件名列表，但无法知道答案中某句话来自哪个文件的具体哪一段。

**为什么这件事值得做**

引用系统对内部知识库问答有三个实际价值：

第一，验证信任。用户看答案是要行动的（改配置、执行操作），动手前想确认原文里确实这么写的。有引用的体验是点击 `[1]` → 展开原文 → 确认 → 动手。没有引用的体验是怀疑 → 打开 Wiki → 搜关键词 → 翻文档 → 找到（或找不到）。多出来的这几步，用户大概率直接跳过，闭眼信任——风险就引入了。

第二，超链接导航。有些答案是指导性的（操作步骤、配置说明），很难在一个回答里把相关上下文全写出来。引用链接让用户点一下就跳到原文的完整章节，不需要来回切窗口。引用在此处的角色不是"证明我没编"，而是"这里说不完，你自己去看"。内部 Wiki 本身就有超链接体系，RAG 答案不接入这个体系等于断头路。

第三，bad case 定位。当答案出错，有了引用编号可以直接定位到「哪句话引用了哪个 chunk」。排查从"召回了 5 个 chunk，不知道 LLM 参考了哪个"变成"`[2]` 引用的 chunk 里确实写了过时信息"。根因定位从分钟级降到秒级。

**改动方案（三件事，几十行代码）**

第一，Prompt 改造。Context 拼接时给每个 chunk 加编号标签——`[1] 来源：xxx > xxx\n{text}`。System prompt 加一句"回答时引用具体来源，标注编号 [1] [2]"。

第二，前端解析。回答渲染时解析 `[1]` `[2]` 标记，替换为可点击的 superscript 链接。点击后展开/高亮对应的 chunk 原文（前端已有 context 事件中的完整 chunk 数据，无需额外请求）。

第三，原文链接。每个来源后面附带 Wiki 原文链接（file_name 可拼出 URL），用户想深入阅读时一键跳转完整文档。

改动量很小——Prompt 改 3 行、context 拼接改 2 行、前端加一个正则替换 + 展开逻辑。几十行代码就补齐了引用能力，投入产出比很高。

**Q23.** 幻觉问题你怎么处理的？有哪些具体的防范措施？你做 factuality 评估了吗？幻觉率是多少？

幻觉防范不是在生成这一步单独做的，而是在检索、重排、Prompt、引用四个环节各做一层过滤，构成纵深防御。

**第一层：检索阶段——减少噪声进入 LLM**

幻觉的一个重要来源是 LLM 拿到了不相关的 chunk，然后基于错误上下文编造信息。Qwen3-rerank 在 RRF 融合后的 8 个候选上做 cross-encoder 精排，把不相关的 chunk 过滤掉，只保留 top-5 高质量 chunk 喂给 LLM。消融实验验证了这个效果——不加 Rerank 时 MRR 0.831，加 Rerank 后提到 0.868。提升的不是召回（Recall@5 从 0.892 到 0.914，变化不大），而是排序精度——把真正相关的 chunk 排在前面，LLM 优先关注它们，自然降低了基于噪声编造的概率。

**第二层：Prompt 设计——行为约束 + 格式约束**

System prompt 明确写了"只使用参考资料中明确包含的信息""如果文档中没有相关内容，直接告知用户""不要编造信息"。但光靠行为约束不够——LLM 知道不该编，但不知道具体怎么做到。两层补充：Few-shot 示例展示"精确回答、带来源标注、不展开推测"的输出模式，让 LLM 模仿；引用编号要求（Q22）让 LLM 为每句话标注来源，形成结构性约束——标注引用比「不要编造」更难违反，因为违反后引用对应不上，答案内部自相矛盾。

**第三层：生成后评估——RAGAS Faithfulness**

每次发版前跑 RAGAS 评测，核心盯 Faithfulness 指标（详见 Q15）。做法是将 LLM 答案拆成原子断言，逐条去上下文中验证是否有依据。线上阈值设 0.85——Faithfulness 低于这个值的答案需要排查。人工抽查校准显示 RAGAS Faithfulness 与人工判断的一致率约 85%，裁判模型的评分在多数 case 下可信。

**第四层：线上兜底——用户反馈闭环**

即使前三层都过了，幻觉还是可能漏过去。用户点踩会写入 QueryLog，漏到人工群的问题由人工排查后回流评测集。这些线上 bad case 定期审查，如果发现某类问题反复出现幻觉（比如某个文档的术语容易让 LLM 混淆），针对性改进——可能是补充文档内容、调整 chunk 策略、或加一条 few-shot 示例。

**幻觉率**

基于 RAGAS Faithfulness 评测，100 条 QA 的 Faithfulness 均值为 0.88。按阈值 0.85 划线，通过率约 82%（82 条 Faithfulness ≥ 0.85）。低于 0.5（严重幻觉，答案中出现上下文完全没有的信息）的比例约 5%（5 条）。这 5 条通常出现在两类场景：一是 query 问了一个知识库确实没有的内容，LLM 没有拒答而是编了；二是多个 chunk 之间信息矛盾，LLM 选错了来源。前者通过拒答机制解决（Q18），后者通过提升 Rerank 排序精度或加冲突裁决 prompt 解决。

**Q24.** 整个链路的端到端延迟是多少？P50、P95、P99 分别是多少？延迟预算分配：检索、rerank、LLM 生成各占多少？

延迟按链路环节逐段拆解。完整链路（缓存未命中）共 6 个耗时步骤：

| 步骤 | P50 | P95 | P99 | 说明 |
|------|-----|-----|-----|------|
| Query 改写（LLM 去口语化） | 100ms | 250ms | 500ms | 轻量 prompt，~50 token 入、~50 token 出 |
| Embedding 推理（gRPC） | 30ms | 50ms | 60ms | text-embedding-v3，内部部署 |
| 双路检索（HNSW + BM25 并行） | 5ms | 12ms | 15ms | 两路并行取较慢者 |
| RRF 融合 | <1ms | <1ms | <1ms | 纯内存计算 |
| Rerank（8 candidates × cross-encoder） | 100ms | 180ms | 250ms | Qwen3-rerank |
| QueryLog 写入 | <1ms | <1ms | <1ms | SQLite 本地写入 |
| **检索段小计** | **~235ms** | **~490ms** | **~825ms** | — |
| LLM 生成（DeepSeek V4 Flash） | 400ms | 1200ms | 2500ms | 输出 100~500 token |
| **端到端总计** | **~635ms** | **~1700ms** | **~3300ms** | — |

**各段耗时分析**

Query 改写（100ms）：第二层的 LLM 口语化去除是主要耗时。Prompt 极短（"将以下口语化问题改写为正式表达"），输入输出各约 50 token，一个轻量 LLM 调用。第一层的映射表是纯字符串替换，1ms 不到，可以忽略。这 100ms 本质上是 LLM 推理的首 token 延迟 + 短文本生成时间。

Embedding 推理（30ms）：text-embedding-v3 走内部 gRPC，单条 query 的向量化是模型前向传播一次，不涉及自回归生成，所以延迟远低于 LLM 生成。30ms 里约一半是网络往返（内网 gRPC），一半是模型推理。P99 60ms 的波动主要来自 gRPC 网络抖动，模型侧因为 query 长度固定（改写后 ~50 token），推理时间很稳定。

双路检索（5ms）：向量 HNSW 搜索 ~3ms——2000 个 768 维向量上的图搜索，O(log N)，实际遍历节点数远小于 2000。BM25 ~2ms——jieba 分词 + 倒排索引查询，全内存操作。两路并行，耗时取较慢的 HNSW 那路。P99 15ms 的波动很小，因为纯内存计算不涉及网络 I/O。

Rerank（100ms）：8 个候选逐个过 Qwen3-rerank cross-encoder。每个候选的推理约 12ms（query+chunk 拼接后单次前向传播），8 × 12 ≈ 96ms，加上 batch 组装开销，约 100ms。注意这里是串行还是批处理——如果 8 个组成一个 batch 一次过模型，延迟可以降到 ~30ms 但需要模型支持动态 batch。当前配置为逐个推理，延迟更高但实现简单。P99 250ms 主要来自 GPU 排队——如果多个请求同时到，后续请求的 8 个候选要等前面的算完。

LLM 生成（400ms）：DeepSeek V4 Flash 的自回归生成。输入约 2750 token（System + Few-shot + Context + Query），输出 100~500 token。Flash 变体的推理速度大约是 30~50 token/s，所以 200 token 输出对应 ~400ms P50。为什么 P99 跳到 2.5s？两个原因：一是偶尔有需要长回答的问题（500 token 输出），二是 LLM 服务的 GPU 排队——内部统一 API 被多个业务共享，高峰期可能有排队延迟。

延迟预算分配：检索段（改写 + Embedding + 检索 + Rerank）占总延迟约 37%（P50），LLM 生成占约 63%。LLM 生成是端到端延迟的绝对大头，且尾部延迟波动大（输出 100 token 和 500 token 差距显著）。检索段各环节延迟相对稳定，P99 和 P50 的差距主要来自 LLM 改写和 Rerank 两个 gRPC 调用的网络抖动。

缓存命中路径：语义缓存命中时跳过改写、检索、Rerank、生成全部步骤，端到端延迟 < 100ms（仅缓存查询 + QueryLog 写入）。

优化方向：当前延迟对日均 100 问完全够用，不需要优化。如果 QPS 上升，优先优化的不是检索段（已经 < 250ms），而是 LLM 生成——切换更快的生成模型、限制输出 token 上限、或引入流式输出（SSE 已支持，首 token 到达即可开始渲染，用户感知延迟远低于完整生成时间）。

**Q25.** LLM 服务是自建还是调 API？有做限流、重试、熔断吗？如果 LLM 服务挂了，系统怎么降级？用户会看到什么？

**模型部署方式：全部走内部统一 API**

链路中涉及三个模型——Query 改写的 LLM、Embedding 的 text-embedding-v3、Rerank 的 Qwen3-rerank、生成的 DeepSeek V4 Flash——全部走内部统一 API，没有一个是我们自己部署的。内部 API 是一个公司级的 LLM 网关，统一做认证、限流、路由、负载均衡，各业务团队通过 gRPC 或 HTTP 调用。对我们来说，它就是一个黑盒——我们不需要关心模型实例跑在哪台 GPU 上、有几个副本、扩缩容策略是什么。

这个架构的好处是运维成本低——GPU 故障、模型升级、版本管理都由平台团队负责。代价是我们对延迟的尾部波动不可控——Q24 提到 LLM 生成的 P99 2.5s，其中一部分就是 API 网关的多租户排队导致的，我们看不到队列深度也无法调优。

**限流：当前不需要，但方案已经想好**

日均 100 问，QPS 峰值不到 1，远远低于内部 API 的默认限流阈值（通常 100 QPS/业务线）。当前没有在业务层做限流。但如果后续 QPS 上升，方案是用 Token Bucket——在 FastAPI 层加一个内存限流器，每秒放行 N 个请求，超出的返回 HTTP 429。为什么不在调用 API 侧做？因为 API 被限后返回的错误码是通用的，不加业务层限流的话用户会看到技术报错信息而不是友好的"当前请求过多，请稍后重试"。

**重试：只对幂等的 Embedding 和 Rerank 做**

三个模型调用的重试策略不同。Embedding 和 Rerank 是幂等的——同一个 query 每次计算结果相同——所以配置了 3 次重试，指数退避（100ms → 200ms → 400ms），覆盖网络瞬时抖动和 gRPC 临时不可用。LLM 生成不做重试——生成是非幂等的（同一个 prompt 两次调用输出可能不同），且生成延迟长（P50 400ms），重试会显著拉长用户等待时间。如果生成失败了，直接返回错误让用户重试，而不是系统自动重试。

**熔断：对 LLM 生成做，对 Embedding 不轻易做**

熔断的逻辑是保护下游服务——当连续失败达到阈值时，暂时不再发起新请求，给下游恢复时间。我们的策略是只对 LLM 生成做熔断：连续 5 次失败（超时或 5xx）后熔断器打开，30 秒内所有生成请求直接快速失败，30 秒后进入半开状态，允许一个探测请求通过——如果成功则关闭熔断器恢复正常，如果失败则继续熔断 30 秒。Embedding 和 Rerank 不做熔断——如果 Embedding 都不可用了，说明基础设施出了问题，熔断也救不了，不如直接让请求失败触发告警。

**降级：两层递进**

LLM 服务挂了时的降级分两层：

第一层（自动）：LLM 生成失败时，前端不显示空白，而是展示检索结果——Rerank 后的 top-5 chunk 原文 + 来源文件名。用户虽然拿不到组织好的答案，但至少能看到相关文档片段，手动定位。这个降级方案的工程成本极低——前端本来就有 context 事件的数据，不需要额外请求。

第二层（人工）：如果检索也挂了（比如 ChromaDB 起不来），前端显示"服务暂时不可用，请直接查看 Wiki 或联系人工支持"，附上 Wiki 链接和人工群入口。

为什么没有把语义缓存作为降级的第一层？缓存本身会引入一系列问题：key 怎么设计（用原始 query 还是改写后的 query？）、相似度阈值设多少（太严命中率低，太松可能返回不相关的缓存答案）、缓存过期和淘汰策略（文档更新后旧缓存答案已经错误，删还是不删？）。这些问题叠加起来，维护成本超过了它在降级场景中的收益——内部 API 的 SLA 很稳，还没遇到过大面积不可用，为一个低概率事件引入一套缓存系统不划算。





**缓存决策：为什么不做查询缓存来降低 LLM 调用成本？**

查询缓存的基本思路是：用户问了一个问题，把答案存下来；下次有人问相似的问题，直接返回缓存答案，不调 LLM。这听起来能省 API 费用，但在我们场景下深入分析后决定不做。从五个维度对比：

**一、成本维度：当前不值得**

LLM API 调用成本 = 输入 token 数 × 单价 + 输出 token 数 × 单价。我们单次请求输入约 2750 token、输出约 200 token，DeepSeek V4 Flash 的单价极低（Flash 变体的设计目标就是低成本），日均 100 问的 API 月费不到百元。缓存系统省下来的钱，可能还不够开发和维护的人力成本。缓存省钱的逻辑成立的前提是「API 调用量大到月费是一笔值得优化的开支」，我们远没到这个量级。

**二、命中率维度：长尾问题多，命中率不会高**

查询缓存的收益取决于问题重复率。内部知识库问答的问题分布通常满足帕累托——20% 的高频问题（"OA 告警阈值怎么配""region 白名单在哪"）占了 80% 的流量，这部分缓存能命中。但剩下的 80% 是长尾问题，每个出现一两次就不再出现。缓存命中率的天花板大约 30~40%，意味着 60% 以上的请求还得走完整链路。花一套缓存系统的工程成本，省 30% 的 API 费用，ROI 不够。

**三、失效维度：文档更新让缓存变成错误信息**

这是最棘手的问题。内部 Wiki 持续更新——配置项改了、操作步骤变了、API 名称换了。如果缓存了旧答案，用户问同一个问题拿到过时的信息，后果比不缓存（多花一次 API 调用的钱再生成一次）严重得多。要解决这个问题需要缓存失效机制——文档更新时找到所有引用过该文档的缓存条目并清除。这意味着缓存系统和文档更新流程要耦合，工程复杂度跃升。不做缓存，每次都是最新的检索 + 最新的生成，天然没有一致性问题。

**四、语义匹配维度：精确匹配不够，模糊匹配又不可靠**

查询缓存不能用精确字符串匹配——"OA 告警阈值怎么配"和"怎么设置 OA 的告警阈值"是同一个问题但字符串完全不同。需要用语义匹配（embedding 相似度），但这引入两个新问题：相似度阈值设多少？设 0.95 的话命中率极低（两个自然语言表述几乎不可能相似度到 0.95），设 0.85 的话可能把"OA 告警阈值怎么配"和"OA 告警通知怎么关"匹配成同一个问题——语义相近但答案完全不同。阈值的选取没有银弹，需要根据线上数据持续调参。

**五、Q17 已有语义缓存的定位**

Q17 链路中提到的语义缓存，和我们这里讨论的查询缓存的区别：Q17 的缓存是「完全相同的语义 → 完全相同的答案」，用于加速重复请求，可以看作是查询缓存的一个极简子集——相似度阈值设得很高（>0.95），只有几乎一模一样的问题才命中。这样命中率很低但出错率也趋近于零，不需要考虑失效问题。而这里讨论的「查询缓存」是更激进的方案——希望通过更宽松的匹配覆盖更多请求来降低成本——这个方向我们判断不值得。

总结：查询缓存在高 QPS、高 API 成本、文档更新频率低的场景下是正确方案。我们的场景是低 QPS、低成本、文档高频更新——三个条件都不满足。总结：查询缓存在高 QPS、高 API 成本、文档更新频率低的场景下是正确方案。我们的场景是低 QPS、低成本、文档高频更新——三个条件都不满足。

**如果要建查询缓存，方案设计如下（不讨论选型，聚焦设计决策）：**

**Key 设计：改写后的 query embedding**

Key 不是字符串而是 768 维向量。选改写后的 query 而不是原始 query 的原因是：改写步骤已经做了术语标准化——"OA 是啥"和"优化顾问是什么"会被改写成同一个标准化表述。如果 key 用原始 query，两个语义相同但措辞不同的问题会被当成两个缓存条目；用改写后的 query，收敛到一个向量上，命中率更高。

Key 中不包含用户 ID、时间戳等维度——不做用户级缓存，全部用户共享同一个缓存池。原因：内部知识库的问题是无状态的，"OA 告警阈值多少"不管谁问答案都一样。

**Value 设计：answer + 溯源信息 + 引用文档列表**

Value 不只是 LLM 生成的纯文本答案，需要存三样东西：

- `answer`：LLM 生成的完整答案文本（含引用编号 [1] [2]）
- `sources`：生成答案时引用的 chunk 列表，格式 `[{chunk_id, file_name, chunk_index, text}]`。前端命中缓存时仍然可以展示「来源」信息和 chunk 原文预览，和走完整链路的体验一致
- `file_names`：去重后的引用文档名列表，如 `["OA监控告警.md", "优化顾问配置.md"]`。这个字段是失效策略的索引

为什么存 sources 和 file_names：缓存答案返回给前端时，前端仍然期望展示来源文件和 chunk 原文——如果不存这些，缓存命中时前端就只能展示一段纯文本答案，体验降级。

**失效策略：文档更新 → 按 file_name 精确失效**

文档更新时，缓存中所有引用了该文档的条目都应该失效。做法是：

1. 文档更新流程中加一个钩子：更新完成后，拿到被修改文档的 file_name
2. 遍历 `query_cache` collection，过滤 `metadata.file_names` 中包含该 file_name 的条目
3. 直接删除

为什么是精确 file_name 匹配而不是 embedding 相似度：文档更新影响的是"所有引用了这个文档的答案"——哪怕缓存 query 和被修改的 chunk 语义不完全一致，只要答案生成时参考了这个文档，就应该失效。file_name 精确匹配能覆盖所有引用关系，不会漏。用 embedding 相似度去判断反而可能漏掉——比如文档里改了一个配置项的默认值，缓存 query 问的是"这个服务的端口号是多少"，query embedding 和配置项 chunk 的 embedding 可能相似度不高（一个是问端口、一个是改配置值），但答案确实需要更新。

遍历 2000 条缓存的成本：2000 条 metadata 的 file_names 是字符串列表，过滤是 O(N) 的字符串匹配，2000 条 < 1ms，不需要建倒排索引。如果缓存条目量级涨到万级以上，再考虑给 file_name 建倒排索引加速。

**删除时机：三种触发条件**

1. **文档更新触发删除（主动失效）**：上述失效策略。这是优先级最高的删除——返回过时答案的代价远大于缓存未命中。

2. **TTL 过期删除（被动失效）**：每个缓存条目创建时写入 `created_at` 时间戳。查询缓存时先检查 TTL——如果 `now - created_at > 24h`，视为过期，删除该条目并走完整链路。24 小时的设定基于文档更新频率——内部 Wiki 虽然不是实时更新，但不能保证同一条缓存答案 24 小时后仍然正确。TTL 是防御性策略：即使没有触发文档更新的主动失效，缓存也不会无限期站在那里。

3. **容量淘汰（被动失效）**：`query_cache` collection 设最大条目数 2000（和文档 chunk 同等规模）。超出时按 `hit_count` 升序淘汰——被命中次数最少的先删。这里选 hit_count 而不是 LRU（最近访问时间）的原因：LRU 可能把"每天都被问一次的高频问题"淘汰掉（因为上次访问已经是 23 小时前），而 hit_count 保留的是长期热门问题。对于低频场景（日均 100 问），hit_count 比 LRU 更稳定。

**一个关键设计决策：不更新缓存条目**

当同一个 query 被多次问到、且缓存未过期时，不更新缓存的 answer。即使文档可能已经变了（但没触发更新事件），也不主动重新生成覆盖旧缓存。原因：如果你怀疑缓存可能过期了，你应该删除它让下次请求走完整链路，而不是生成一个新答案覆盖旧答案然后祈祷新答案是对的。更新缓存和删除缓存的操作成本一样，但更新的语义是"我确认新答案覆盖旧答案是安全的"，删除的语义是"我不确定，下次让它重新生成"——后者在一致性上更安全。所以失效策略只删不更新。

**缓存写入时机：生成成功 + 用户无负面反馈**

不是每次 LLM 生成成功都写缓存。写入条件有两个：

第一，LLM 生成成功且没有触发拒答。如果 LLM 回复了"当前知识库未覆盖此问题"，说明这个 query 在知识库中没答案，缓存它没有意义——下次有人问同样的问题，应该重新走检索（也许文档已经更新了），而不是直接告诉他"没有"。

第二，用户没有点踩。缓存写入不是同步的——LLM 生成完先返回答案给前端，缓存写入延迟执行（比如延迟 5 分钟或等用户离开页面时触发）。在这个窗口期内如果用户点了踩，缓存就不写入。这避免了把错误答案固化到缓存中。

具体流程：LLM 生成成功 → 返回答案给前端 → 前端记录该回答的 query_id → 等待 5 分钟 → 检查该 query_id 的 user_click 字段（QueryLog 中）→ 如果 user_click 不是"踩" → 写入 query_cache collection。

**缓存与用户反馈的挂钩：三个联动点**

用户反馈不只是缓存写入的闸门，而是贯穿缓存的整个生命周期：

联动一（写入闸门）：用户点踩 → 不写入缓存。如上所述，延迟写 + 检查 user_click。

联动二（主动清除）：用户点踩了一个缓存命中的答案 → 立即删除该缓存条目。这个场景是：用户 A 问了一个问题，缓存命中返回了答案，用户 A 觉得不对点了踩。此时不应该等 TTL 过期，应该立即删除——因为缓存里存的是错误答案，多留一分钟就多一个用户被误导。

联动三（质量加权）：用户点赞的缓存条目，hit_count 额外 +N（比如 +5 而不是 +1）。点赞是比命中更强烈的正向信号——命中只说明"这个问题被问了"，点赞说明"这个答案确实有用"。在容量淘汰时，被点赞的条目更难被淘汰，这是一种隐式的质量排序。

这三个联动让用户反馈从"被动收集"变成了"主动维护缓存质量"——反馈不只是用来回流评测集（Q13），还直接作用于线上服务质量。

**Q26.** 每天 100 个问题，你这个系统的 QPS 是多少（保守估计峰值）？做过压测吗？系统的最大吞吐量是多少？瓶颈在哪里？

**QPS 不能简单用日均除以秒数**

把 300 问 / 8 小时 ≈ 0.01 QPS 是错的——这假设问题是均匀分布在一天里的，但实际不是。内部知识库问答的流量有很强的突发性：故障时（"线上出问题了，快查怎么处理"）、版本发布后（"新功能怎么配置"）。这些场景下几十个人可能同时在问，流量几秒内涌进来。

合理的估算方式：按最坏情况算瞬时并发。假设一次故障时，团队里 20 个人同时打开页面提问，请求在 1~2 秒内到达——这就是 10~20 QPS 的瞬时并发。机器人上线后提问门槛比 oncall 群更低（没有社交摩擦），日均量级可能从 100 涨到 300~500，瞬时并发可能到 30~50 QPS。均值 QPS 对这类突发型流量没有参考意义。

**部署架构**

4 台机器各一个 FastAPI 实例，各自内嵌 ChromaDB（PersistentClient 模式，进程内调用），4 个实例前面挂 Nginx 做轮询负载均衡。选嵌入式而不是集中式 ChromaDB server 的原因见 Q7 的详细分析，核心逻辑一句话：读写比 1000:1，用写路径的一点同步成本，换读路径的零网络延迟、无单点故障。离线索引构建由管理员通过管理接口触发，收归单人操作。

**为什么必须收归单人上传——嵌入式下的并发写入风险**

嵌入式架构下，每个节点有自己的 ChromaDB 实例和数据文件，看起来写入互不干扰。但文档更新需要让 4 个节点全部拿到新索引——管理员触发一次更新，请求被 Nginx 路由到某一台机器上执行重建。这个过程中有两个风险：

1. **多人同时触发更新**：如果两个管理员几乎同时点"重建索引"，Nginx 可能把两个请求路由到不同的节点。A 的请求在节点 1 上重建完成、B 的请求在节点 2 上也重建完成——但节点 1 和节点 2 上的索引是基于不同版本的文档构建的，4 个节点之间出现了不一致。用户连续刷新页面，两次请求落到不同节点，看到两个不同的答案。

2. **更新过程中的读写交错**：某个节点正在执行删旧 collection + 逐条插入新 chunk 的过程中，该节点上的读请求看到的索引处于中间状态——部分旧 chunk 已删、部分新 chunk 未插入，检索结果不完整。ChromaDB 的 PersistentClient 不提供事务隔离。

解决方案同样是收归单人上传——在应用层保证同一时刻只有一个人在触发重建。重建完成后，其他 3 个节点通过健康检查端点（比对 chunk 总数，与重建完成的节点一致则通过）来验证同步状态。在当前几天甚至一周一次的重建频率下，这个流程完全不影响效率。

**瓶颈：真正的瓶颈不在向量检索**

应用层 4 个 FastAPI 实例无状态，线性扩展。Embedding / LLM / Rerank 走内部统一 API，网关级并发远超我们。向量检索方面：嵌入式 ChromaDB，每个节点独立处理自己的检索请求，不存在"一个 ChromaDB 扛 4 个节点的流量"——每个节点只需扛路由到自己的那 1/4 流量，且 HNSW 搜索仅 ~3ms（2000 chunk），进程内调用无网络开销，单节点轻松支撑远超当前 QPS 的并发。

真正的瓶颈在 LLM 生成——P50 400ms、P99 2.5s，占了端到端延迟的 63%。如果未来 QPS 上去，LLM 是第一个需要优化的环节，ChromaDB 排在很后面。当 chunk 量涨到 20000+ 且嵌入式的单机内存成为瓶颈时，才需要迁移到分布式向量数据库（Milvus / Qdrant）。

**压测**

没有做过正式压测。如果要做，重点不是测平均 QPS，而是测瞬时并发——用 Locust 模拟 10/20/50 个并发请求同时到达某个节点，观察端到端延迟的 P99 拐点。预期瓶颈先出现在 LLM 生成而非向量检索。

**Q27.** 向量数据库的高可用怎么做的？有没有主从、多副本？挂了怎么恢复？

**当前架构天然消除了 ChromaDB 的单点问题**

和 Q26 一致——4 个节点各嵌一个 ChromaDB（PersistentClient 模式），不是集中式 server。ChromaDB 没有独立进程，随 FastAPI 进程启动而加载、随 FastAPI 进程退出而释放。所以不存在"ChromaDB 挂了"这个场景——它不是一个独立服务，是 FastAPI 进程的一部分。

那"挂了"指的是什么？三种情况：

**情况一：某个节点的 FastAPI 进程崩溃。** ChromaDB 随进程一起退出。Nginx 检测到该节点健康检查失败，自动把流量从故障节点摘掉，请求路由到剩余 3 个健康节点。对用户的影响：1/4 的请求可能短暂失败（在 Nginx 摘除节点之前的一两次请求），之后恢复正常。故障节点不需要紧急修复——可以等运维方便的时候再排查重启。

**情况二：某个节点的 ChromaDB 数据文件损坏（磁盘故障、误删）。** 该节点上的检索请求全部失败。Nginx 摘除该节点后，其余 3 个节点继续服务。故障节点的恢复：从健康节点复制 ChromaDB 数据目录（约 6MB），或从零重建——跑一遍文档切分 + embedding 全流程，约 30 秒。

**情况三：全量 4 个节点同时故障。** 这是机房断电级别的灾难，不是 ChromaDB 高可用能解决的问题。

**恢复流程**

节点重启后的自动恢复流程：FastAPI 进程启动 → ChromaDB PersistentClient 初始化，从本地磁盘加载向量索引和元数据（~2s）→ BM25 倒排索引在启动钩子中自动重建，从 ChromaDB 读出所有 chunk 原文 + jieba 分词 + 构建倒排表（2000 chunk < 1s）→ 健康检查通过，Nginx 将该节点重新加入 upstream → 恢复服务。整个过程约 3 秒，且不影响其他 3 个节点的正常服务。

**数据会不会丢**

不会。向量索引和元数据持久化在本地磁盘。BM25 倒排索引是内存结构，但数据源是 ChromaDB 中的 chunk 原文，重启后自动重建。最坏情况——磁盘损坏导致数据文件不可读——从零重建，500 文档、2000 chunk 约 30 秒。

**跨节点一致性问题**

4 个节点的索引是否一致？文档更新由管理员手动触发，更新请求路由到某一台机器执行重建。重建完成后，该节点的 chunk 总数记录在健康检查端点中。其他 3 个节点定期（每次健康检查时）比对自己的 chunk 总数——如果与重建节点不一致，说明同步有问题，触发告警后管理员手动在该节点重新执行重建。当前更新频率几天一次，这个"手动 + 健康检查兜底"的方案足够。如果未来更新频率上升，换成共享存储（所有节点挂载同一个 ChromaDB 数据目录）即可，但当前不需要引入这个复杂度。

**未来扩展路径**

和 Q7 的结论一致：当数据量到万级 chunk 且需要真正的多副本自动故障转移时，正确路径不是给 ChromaDB 打补丁，而是换引擎——Qdrant 或 Milvus。但在这个体量到来之前，嵌入式架构已经提供了比集中式 server 更好的可用性：4 个节点互为冗余、故障隔离、无全局单点。

**Q28.** 整个系统的可观测性怎么做？日志、指标、链路追踪各是怎么布的？你从仪表板上看到检索延迟突然飙升，你查什么？

**当前状态：分步骤日志 + session_id 区分用户，没有对接监控平台**

可观测性当前只靠日志。做法很直接——在每个链路步骤打完耗时日志，用 session_id 区分不同用户请求。没有接 Prometheus / Grafana，没有上链路追踪。

这个方案在日均 100 问的体量下完全够用。出了问题就是 grep 日志，几分钟定位。对接监控平台的收益要等 QPS 上来了才能体现，现阶段属于过度工程。但面试时要把方案讲清楚。

---

**日志方案：分步骤打印耗时，session_id 串联**

每个 /ask 请求的处理过程中，在每个步骤完成后直接打印：

```python
logger.info(f"[{session_id}] rewrite cost={t1}ms")
logger.info(f"[{session_id}] embedding cost={t2}ms")
logger.info(f"[{session_id}] dual_search cost={t3}ms")
logger.info(f"[{session_id}] rerank cost={t4}ms")
logger.info(f"[{session_id}] llm_gen cost={t5}ms")
logger.info(f"[{session_id}] total cost={total}ms")
```

session_id 在请求入口生成（UUID），后续每一步都带上。不同用户的请求通过 session_id 区分，grep 一个 session_id 就能看到这个请求的完整链路耗时。

此外 QueryLog（SQLite，15 字段）记录了每次请求的完整信息——原始问题、改写后问题、召回结果、Rerank 后数量、端到端延迟、用户反馈。QueryLog 侧重"业务数据留痕"，分步骤日志侧重"性能定位"，两者互补。

设计原则：日志写入失败只记 warning、不抛异常——不能因为日志挂了影响主链路。

---

**为什么没对接监控平台**

三个原因：

1. **体量不匹配**：日均 100 问，靠日志手工排查完全够用。Prometheus + Grafana 的搭建和维护成本远超当前收益。

2. **告警价值低**：内部工具，不是 7×24 关键业务。延迟高了用户自然会反馈，不需要 3:00 AM 电话告警。

3. **排查链路短**：全链路在 FastAPI 进程内，调用关系简单。不像微服务有几十个服务间调用，没有分布式追踪根本不知道请求经过了哪些节点。

当 QPS 从日均 100 涨到日均 1000+、问题排查开始靠人力顶不住时，再上监控平台。路线是：先接 Prometheus 收指标（对接 /metrics 端点），再接 Grafana 做面板，最后加告警规则。但这些是"有了更好"而不是"现在就需要"。

---

**延迟飙升时的排查路径**

看到延迟异常，grep 最近的日志按 step 聚合看耗时分布：

1. **先看 llm_gen** —— 90% 是这里。内部 LLM API 被其他大请求抢了 GPU。确认：llm_gen cost 变大、其他步骤正常 → 锁定。

2. **看 rerank** —— GPU 排队也会让它慢。确认：rerank cost 是否异常。

3. **看 embedding** —— gRPC 网络抖动或排队。确认：embedding cost 是否异常。

4. **看 dual_search** —— HNSW 在 2000 chunk 下几乎不可能慢，但如果磁盘 I/O 被抢占会有尖刺。

5. **看请求量** —— 如果所有步骤都正常但端到端还是慢，可能是瞬时大量请求涌入导致 Uvicorn 请求队列积压。

核心思路：二分定位，先排 LLM（最大变量），再逐段排查检索链路。几次 grep + awk 就定位到了。

### 2.4 反馈 & 迭代闭环

**Q29.** 用户反馈怎么收集的？有点赞/点踩/修正吗？反馈数据怎么回到系统里？有没有形成数据飞轮？

**当前：有点赞和点踩，没有直接修正**

前端回答区域下方有"有用"和"没用"两个按钮。用户点踩后，反馈写入 QueryLog 的 user_click 字段。没有让用户直接修正答案的功能——让用户手动改答案的交互成本太高，内部用户没这个耐心。

除了前端按钮，还有一个间接反馈渠道：漏到人工群里才能解决的问题。这类问题说明系统没帮上忙，由人工记录后纳入 bad case。

**反馈怎么回到系统里——两条路径，同一个入口**

点踩和人工群反馈最终都汇入 QueryLog，但路径不同。

路径一（点踩）：用户在页面上点"没用"→ 前端将 user_click 回写到 QueryLog 对应记录。因为有 query_id，直接定位到当次请求。

路径二（人工群反馈）：用户在 RAG 没得到答案，转去群里问人。群里看到问题后，根据提问人的 user_id 去 QueryLog 搜索该用户最近的 /ask 记录，按问题文本相似度匹配到对应那次请求。人工群反馈本身不带 query_id，但 user_id + 问题内容可以做 join——找到当次日志后，就能回溯 rewrite、vector_hits、bm25_hits 等完整检索过程。聊天的 user_id 和系统登录的 user_id 是同一个企业账号，所以这个映射是直接成立的。

两条路径汇聚后，每两周汇总点踩记录和人工群反馈，逐条审核后标注 chunk ID 作为 ground truth，补充到离线评测集。因为 QueryLog 保留了每次检索的完整命中列表，点踩的记录直接查日志，人工群反馈则先通过 user_id 定位到日志再排查——不需要复现，回溯成本很低。

**基于 QueryLog 的 Bad Case 排查 SOP**

每两周汇总 bad case 时，不是简单地把问题扔进评测集就完了。要从 QueryLog 中逐字段排查根因，然后针对性修复。标准流程四步：

**第一步：拉数据。** 从 QueryLog 筛选 user_click="踩" 的记录，加上人工群反馈的问题（手动录入）。按时间倒序排列，优先处理最近的问题。

**第二步：逐字段定位根因。** QueryLog 的 15 个字段在这个环节的价值就体现出来了——不需要复现，直接看日志还原当时的完整检索过程：

- 看 `original_question` vs `rewritten`：改写是否正确？如果用户问"那个监控怎么配"，rewritten 变成了不相关的内容，说明映射表缺了这条映射，或者 LLM 改写跑偏了 → **改写问题**。

- 看 `vector_hits` 和 `bm25_hits`：两路各自召回了什么？如果正确答案的 chunk 不在任何一路的 top-5 里，说明是召回失败。进一步区分——如果正确答案含有关键词但 BM25 没召回，可能是 jieba 分词切错了 → **分词问题**。如果正确答案是语义相关但向量没召回，可能是 chunk 切得不好导致向量表示不准确 → **chunk 策略问题**。

- 看 `rerank_score`（如有）：Rerank 后的 top-5 里有没有正确答案？如果 vector 或 BM25 召回了正确答案，但 Rerank 把它排到 5 名之外了 → **排序问题**。

- 看 `src_vector` / `src_bm25` / `src_both`：正确答案来自哪一路？如果每次都是同一路（比如总是 BM25 贡献正确答案），说明另一路在同类问题上系统性失效 → **检索路权重问题**。

- 如果前面都正常——正确答案在 Rerank top-5 里，但 LLM 还是生成了错误答案 → **生成问题**（幻觉或 prompt 约束不够）。

**第三步：针对性修复。** 不同根因走不同修复路径，每种都有具体的操作步骤。

**类型一：改写问题（rewritten 把 query 带偏了）**

表现：original_question 意思清晰，但 rewritten 丢失了关键信息或替换成了错误术语。

修复途径：
1. 如果是因为"内部术语未映射"导致 LLM 不认识（比如用户说"那个蓝屏工具"，LLM 不知道是"BSOD诊断"）→ 在动态映射表中加一条映射关系，存到配置中心，调 reload 接口实时生效，不需要重启服务。
2. 如果是因为 LLM 改写本身跑偏（比如 query 里的数字被错误替换、否定词被忽略）→ 调 rewrite prompt，在 prompt 中加约束，比如"保留原文中的所有数字和否定词，不要改写"。Prompt 改完即生效。
3. 如果某类 query 反复被改写坏 → 排查是否为 prompt 的 few-shot 不够覆盖这类表述，考虑加一条针对性的改写示例。

验证方式：用同一条原始 query 重新请求，看 rewritten 是否变正确，再看后续检索结果是否改善。

**类型二：分词问题（BM25 没召回，但关键词明明在 chunk 里）**

表现：bm25_hits 里没有正确答案的 chunk，但手动搜 chunk 原文，发现关键词是存在的。

修复途径：
1. 把被切错的术语加到 jieba 自定义词库文件（一个纯文本，每行一个词），调 reload 接口重新加载，30 秒内生效。
2. 加词策略：不只是加"当前这一个"，而是顺带加同类的。比如发现"多AZ"被切成"多"+"AZ"，不仅加"多AZ"，还顺手加"单AZ"、"跨AZ"等同系列术语。
3. 词库文件的维护方式：放在 Git 仓库里，修改后 commit，FastAPI 的 reload 接口拉最新版本。这样有版本记录，不会出现"不知道谁加了什么词"。

验证方式：调 reload 后，用同一 query 重新走一遍 BM25 检索，看修正后的分词结果和召回结果。

**类型三：Chunk 策略问题（正确答案的 chunk 既不在 vector 也不在 BM25 的 top-5 里）**

表现：vector_hits 和 bm25_hits 都没有覆盖正确答案，但正确答案对应的 chunk 确实存在于库中。

修复途径：
1. 如果是 chunk 语义太碎——一个完整答案被切到了两个 chunk 里，各含一半信息，向量和 BM25 都匹配不上 → 调大 chunk size，比如从 384 调到 512。改的是切分配置参数，改完后需要全量重建索引（重新切分 → 重新 embedding → 重新入库），当前 500 文档约 2 分钟完成。
2. 如果是标题路径信息没打进去——chunk 内容是纯技术描述但没有上下文，检索时搜不到 → 检查 MarkdownHeaderTextSplitter 的输出，确认标题层级是否正确拼接到了 chunk content 头部。如果是拼接逻辑的 bug，修代码后重建索引。
3. 如果是 LLM 摘要没生效——一个表格或 JSON 配置块的摘要没生成出来，chunk 里只有原始数据没有自然语言描述 → 检查离线摘要生成脚本是否对这类特殊文本生效，修复后重新跑摘要生成 + 重建索引。

验证方式：重建索引后，用同一 query 走完整检索链路，看正确答案是否进入 RRF 融合后的候选列表。

**类型四：排序问题（正确答案召回了但 Rerank 把它排到了 5 名之外）**

表现：vector_hits 或 bm25_hits 里有正确答案，但 Rerank 后的 top-5 里没有它。

修复途径：
1. 如果是个别 case → 看 Rerank 为什么会把这个 chunk 排低。可能是因为 chunk 的语义和 query 在 cross-encoder 看来确实不够相关，根因在 chunk 的内容表述上（回类型三修复）。如果 cross-encoder 明显判断错误 → 这是一个模型 bad case，记录但暂时无法修复（cross-encoder 是内部模型，不可调参）。
2. 如果是系统性倾向——比如 BM25 召回的正确答案总是被 Rerank 排到后面，说明 RRF 融合时 BM25 路的权重偏低了 → 调大 RRF 的 β 参数（BM25 权重）。例如从 α=0.5, β=0.5 调成 α=0.4, β=0.6。参数在配置文件中，改了即生效，不需要重建索引。具体调到多少可以跑网格搜索——在评测集上 β 以 0.05 步长扫一遍，挑 MRR 最优的值。
3. 如果纠不回来 → 临时把 Rerank top-5 改成 top-8，给 LLM 更宽的候选范围，代价是多 3 个 chunk 的输入 token（约 1150 token）。改了即生效。

验证方式：如果是调参数，跑评测集的 MRR 看是否回升。如果是个别 case，用同一 query 重新检索看 top-5 里是否包含正确答案。

**类型五：生成问题（正确答案在 top-5 里，但 LLM 答错了）**

表现：检索结果正确，Rerank top-5 里包含正确答案，但 LLM 输出的答案仍然错误或编造了信息。

修复途径：
1. 如果 LLM 忽略了一个明显相关的 chunk 而用了另一个不太相关的 → 检查 prompt 中 chunk 的排列顺序。当前是按 Rerank 分数降序，但如果分数接近的两个 chunk，LLM 可能关注了后面的。在 chunk 拼接时加一个显式的"按相关性排序"提示。
2. 如果 LLM 编造了 chunk 里没有的信息（幻觉）→ 加强 system prompt 的约束，比如"如果你不确定，请说'文档中未明确说明'，不要推测"。同时检查 Q23 的四层幻觉防线中哪层失效了。
3. 如果某类问题反复生成错（比如配置值写成了旧版本）→ 在 few-shot 示例中加一条同类型的正确示例，让 LLM 学会这类问题的回答模式。改 prompt 中的 few-shot 区域，改完即生效。
4. 如果是知识库本身就有矛盾（两个文档对同一问题给出了不同答案）→ 这不是生成问题，是文档质量问题的上游输入。需要联系文档维护者修正源文档，短期处理可以在 prompt 中加冲突裁决规则——"当多个来源给出不同信息时，优先采用最近更新的来源"。

验证方式：同一条 query 重新生成，人工对比新旧答案。如果加了 few-shot，跑评测集确保其他类型问题没有退化。

**类型六：知识库覆盖问题（正确答案的文档根本不在库中）**

表现：QueryLog 显示检索链路一切正常，但正确答案就是不在任何召回结果里。人工确认对应的文档不存在。

修复途径：
1. 找到正确的源文档（Wiki / 人工群消息 / 同事提供）。
2. 按入库规范清洗格式、确认标题层级合理。
3. 走管理接口上传文档 → 自动切分 → embedding → 入库。
4. 上传后用这条 query 验证能否正确召回。

验证方式：文档入库后，用原始 query 走完整链路，看新文档的 chunk 是否出现在 top-5 中。

---

**排查优先级**：按概率排序——改写问题 > 分词问题 > 生成问题 > 排序问题 > Chunk 策略问题 > 知识库覆盖问题。前两类占了 bad case 的大头，修复成本也最低（改映射表/词库，实时生效），应优先排查。

**第四步：回流评测集验证。** 修复后，把这条 bad case 标注 chunk ID 后加入评测集。下次发版前跑 RAGAS 全量评测时，这条 case 会被自动验证——如果修复有效，对应的指标（MRR / Faithfulness / Recall）应该回升。如果没回升，回到第二步重新排查。

**数据飞轮：还在建设中**

理想的数据飞轮是"用户使用 → 产生反馈 → 自动优化模型/索引 → 体验提升 → 更多用户使用"。当前我们只跑通了前两步，第三步是半自动的——反馈回流到评测集是人工操作，不是自动触发检索策略调整。

坦诚说，以日均 100 问的量级，反馈数据累计速度很慢，飞轮转不快。但架构已经搭好了：QueryLog 存、评测集收、RAGAS 跑。量上来后把人工审核环节换成自动化的即可。

**为什么没有让用户直接修正答案**

三个原因：第一，内部用户不是标注人员，让他们手动编辑答案的门槛太高；第二，修正后的答案格式和质量不可控，不能直接入缓存或评测集；第三，我们更需要的是"这个答案对不对"的信号（点赞/点踩），而不是用户替我们写答案。点赞/点踩的信噪比高于自由文本修正。

**Q30.** 你们上线后效果怎么样？拦截率是多少？用户满意度提升了多少？每天节省了多少人天？这些数字是怎么统计的？

**先坦诚说：没有做严格的线上效果量化**

日均 100 问的量级下，做正式的 A/B 对比或统计显著性检验是不现实的——样本太小，置信区间太宽。当前的效果评估依赖三个间接信号，没有做对照组实验。

**拦截率：约 70%~80%**

拦截率定义为「用户没再转到人工群的比例」。统计方式：对比系统上线前后，人工群中知识类问题的数量变化。上线前，每天群里有约 30~40 条问题是"XX 怎么配置""YY 在哪里"，上线后这些基本消失了——因为用户能直接在系统里搜到答案。

但 70%~80% 这个数是估算，不是精确统计。因为不知道有多少用户是"搜到了答案所以没来群里问"，也没法统计"用户搜了但没搜到、放弃了、也没去群里问"。精确拦截率需要追踪每个用户的完整行为链路（搜索 → 看结果 → 是否自行解决 → 是否转人工），当前 QueryLog 只记录 /ask 请求，不记录用户后续行为。

更准确的说法是：人工群中可被系统覆盖的问题减少了约 70%~80%。不能拍胸脯说"系统拦截了 80% 的问题"。

**用户满意度：点赞率约 85%~90%**

来源是 QueryLog 的 user_click 字段。统计逻辑：有点赞或点踩记录的请求中，点赞占比。没有点赞也没有点踩的请求不参与计算（用户可能看了答案就走了，不代表不满意）。

贴一个真实数字需要注意的点：点赞率有自选择偏差。用了觉得好的人更倾向于点赞，用了觉得一般的人可能直接关页面，不点任何按钮。所以 85%~90% 是"在有反馈的用户中"，不是全体用户。全体用户的满意度只会更低，但低了多远，我们没有数据。

**节省人天：约 0.5 人天/天**

计算方式：上线前，oncall 人员每天处理约 20~30 条可被系统回答的知识类问题，每条平均耗时 5~10 分钟（理解问题 → 查文档 → 组织回复 → 粘贴到群里）。取中位数：25 条 × 7.5 分钟 ≈ 3 小时 ≈ 0.4 人天/天。加上一些原本"懒得查文档、随便回"的低质量回答被系统标准化答案替代，综合估算约 0.5 人天/天。

这个数的局限：第一，不是所有被系统回答的问题原来都会问到人——部分用户有了系统后才开始问（以前可能懒得去群里问），所以省掉的人天不是简单地从群里扣除。第二，0.5 人天/天不能直接换算成"少招半个人"，因为 oncall 的工作是碎片化的，省下来的 3 小时可能被其他事务填充了。节省更多体现在响应速度上（用户不用等群里回复），而不是人头数上。

**这些数字怎么严谨化**

如果面试官追问"你怎么证明这些数字不是编的"，我的回答分两步：

1. 短期可做的：QueryLog 加一个字段 `user_went_to_manual`，前端在用户看完答案后加一个隐式追踪——如果用户复制了答案文本、或者短时间内没有点人工群入口，标记为"自助解决"。这个信号比点赞/点踩覆盖更全，能给出更准的拦截率。

2. 长期才能做的：AB 实验。随机分 50% 用户看到系统答案、50% 用户只能搜文档标题（不下线系统，只是降级为检索模式），对比两组用户转人工群的比例。但这需要更大用户量才有统计显著——日均 100 问，分两组后每组 50，差异很难排除噪声。

坦诚说，在当前规模下，效果的定量证据有限。但定性证据是明确的——内部群里的知识类提问大幅减少、用户反馈正面、oncall 同学说"终于不用重复回答同样的问题了"。对于内部工具来说，这已经足够说明价值。

**Q31.** 线上出了 bad case 你怎么发现？怎么复盘？怎么修？从发现问题到修复上线，整个流程是什么样的？能给一个具体案例吗？

**发现渠道有两个**

1. **QueryLog 点踩记录**：每两周拉一次 user_click="踩" 的记录，逐条看。
2. **人工群反馈**：用户搜不到答案、或者答案明显错了，最终还是会转到人工群里问。这类问题优先级更高——说明系统不仅没帮上忙，还逼用户绕了弯路。定位方式是先看提问人的 user_id，去 QueryLog 搜索该用户最近的 /ask 记录，用问题文本做语义匹配找到对应那条日志。

两个渠道覆盖了"用户主动投诉"和"用户默默放弃"两种场景。

**从发现到修复的标准流程**

四步闭环，和 Q29 的 SOP 一致：

**发现** → 从 QueryLog 拉点踩记录，或从人工群收到反馈。

**复盘定位** → 打开 QueryLog 对应记录，看 original_question、rewritten、vector_hits、bm25_hits、src 分布，按 SOP 定位根因（改写/分词/Chunk/排序/生成/覆盖）。

**修复** → 根据根因类型执行对应修复动作。最常见的两类（改写和分词）改配置即可实时生效，不需要重建索引或重新部署。

**验证** → 用原始 query 重新请求，确认结果正确。然后把这条 case 标注 chunk ID 后加入评测集，下次发版跑 RAGAS 时自动验证不会退化。

---

**具体案例：BM25 分词错误导致召回失败**

**发现**：两周一次的 QueryLog 审查中，发现一条 user_click="踩" 的记录。original_question 是"多AZ部署的region白名单怎么配"，用户点了没用。

**复盘定位**：

1. 打开 QueryLog，先看 rewritten："多AZ部署的region白名单怎么配"——改写正确，没有丢信息。改写环节排除。

2. 看 vector_hits：top-5 里有两个 chunk 提到了 region 白名单，但没有一个提到"多AZ"。向量路召回了语义相关的内容，但不是最相关的。

3. 看 bm25_hits：top-5 里都是"region 白名单"相关的 chunk，但同样没有多AZ相关的内容。这说明 BM25 也召回了 region 白名单，但忽略了"多AZ"这个关键词。

4. 看 src 分布：src_vector 和 src_bm25 都命中了 region 白名单相关 chunk，但正确答案（"多AZ region 白名单配置"那个 chunk）不在任何一路的 top-5 里。

5. 手动查那个正确 chunk 的原文，发现确实存在，标题是"多AZ部署 - Region白名单配置"。那为什么 BM25 没召回？用 jieba 手动分词"多AZ部署"——结果被切成了 `['多', 'AZ', '部署']`，"多AZ"被拆开了。BM25 倒排索引里存的是"多AZ"作为一个 term 的 IDF 和 TF，但 query 分出来的却是"多"和"AZ"分别查，两个高频词的 IDF 都很低，匹配分数被稀释了。

根因确认：**分词问题**——"多AZ"不在 jieba 自定义词库中。

**修复**：

1. 在 jieba 自定义词库文件中加一行 `多AZ`。
2. 顺手加了同系列的 `单AZ`、`跨AZ`、`多地域`，避免同类问题反复出现。
3. 调 FastAPI 的 jieba reload 接口，重新加载词库，实时生效，不用重启服务。
4. 用原始 query 重新走了一遍 BM25 检索，确认"多AZ"没有被拆开，正确 chunk 进入了 top-5。再跑完整链路，LLM 生成的答案正确，附带了引用。

**验证和闭环**：把这条 case（query + 正确的 chunk ID）加入评测集。下次发版跑 RAGAS，这条 case 的 Recall@5 和 MRR 会自动检验分词修复是否退化。

**时间线**：从发现到修复完毕，整个过程约 15 分钟——5 分钟定位 + 2 分钟加词库 + 1 分钟 reload + 5 分钟验证 + 2 分钟更新评测集。

**Q32.** Embedding 模型、rerank 模型、生成模型，你有定期微调或者更新的计划吗？用什么数据更新？怎么保证更新后不退化？

**先解释两个概念：模型切换 vs 微调**

**模型切换**指的是平台侧上线了一个新版本模型（比如 text-embedding-v3 升级到 v4、DeepSeek V4 升级到 V5），我们需要决定要不要把系统里的模型名称从 `v3` 改成 `v4`。动机通常是三个：新版本效果更好（公开 benchmark 更高）、延迟更低（同效果下推理更快）、或者旧版本要下线了（平台不再维护，被迫切）。切换的成本是一行配置修改 + 跑评测验证。

**微调（Fine-tune）** 指的是拿一个已经训练好的通用模型（基座模型），用自己的领域数据再训练一轮，让模型在你的特定任务上表现更好。比如通用的 text-embedding-v3 在公开中文上表现好，但在内部术语（"OA""多AZ""优化顾问"）上可能不够敏感——微调就是让它对这些内部术语更敏感。微调的成本是：准备几千条标注数据 + 租 GPU 跑训练 + 部署微调后的模型实例。

两者的区别：模型切换是"换一个更好的现成模型"，不改变模型本身的权重；微调是"把现成模型改造成自己的版本"，改变了模型权重。我们当前只做得了前者。

---

**当前：没有微调计划，模型全部走内部 API**

三个模型都在内部统一 API 后面，模型实例的升级和版本管理由平台团队负责，我们调的是 API 不是模型权重。这意味着两件事：第一，我们没有做 fine-tune 的条件——训练数据、GPU 资源、模型权重都不在我们这边；第二，我们的优化方向不在模型层，而在检索链路的其他环节（改写、分词、Prompt、chunk 策略）。

但这不意味着我们对模型更新没有发言权。当内部平台上线新版本模型时（比如 text-embedding-v3 → v4），我们需要决定"要不要切过去"。这个决策需要一套验证流程。

**新模型版本的切换流程**

**第一步：离线评测。** 在评测集上并行跑旧模型和新模型。Embedding 升级需要全量重建索引（2000 chunk 重新 embedding），跑 100 条 QA 对比新旧 MRR 和 Recall@5。Rerank 或 LLM 升级不需要重建索引，只替换对应环节，跑对比即可。关键约束：Embedding 切换的评测成本约 2 分钟 + 百万 token 的 embedding 调用。

**第二步：差异 case 人工审查。** 不只看汇总指标。新旧评分差异超过 10% 的 case 逐条人工对比——确认新模型是"更好"还是"不同但没有更好"。有时新模型 MRR 整体更高，但对某类特定问题反而退化（比如专业术语的检索变差），这种 tradeoff 必须人工判断能不能接受。

**第三步：灰度切换。** 评测通过后，先在配置中切 20% 流量到新模型（通过配置中心的模型名参数控制），跑一周。对比新老两组 QueryLog——延迟有没有恶化、点赞率有没有下降。确认无退化后全量切换。旧模型索引保留一周做回滚兜底。

**用什么数据评估**

就是同一套 100 条 QA pairs 评测集（Q13）。评测集的核心价值在这里体现——它不仅是发版前的质量门槛，还是模型升级时的对比基准。当前局限：100 条跑检索评测够用，但如果要精细对比两个 LLM 版本的生成质量差异，可能需要扩展到 200~300 条才能统计显著。

**为什么不做 fine-tune**

三个原因。第一，**数据不够**：fine-tune 至少需要几千条高质量 (query, answer) 对，当前 100 条评测集 + 线上反馈远远不够。第二，**维护成本高**：微调后模型需要独立部署和维护，出问题的排查门槛比调 prompt 高一个数量级。第三，**Prompt engineering 的边际收益更大**：在日均 100 问的量级下，优化 prompt、扩充 few-shot、调整映射表和分词词库的投入产出比远高于微调模型。微调的价值要在 QPS 和标注数据都上量后才能体现。

**微调大致怎么做（附：帮你面试时讲清楚）**

微调不是从头训练一个模型，而是在基座模型的基础上用领域数据"精修"。以 LLM 为例，标准流程分四步：

1. **准备数据**：收集一批高质量的 (instruction, response) 对。instruction 是用户问题，response 是期望的标准答案。数据来源可以是 QueryLog 中点赞多的回答、人工标注的 QA、或者用更强的模型（如 GPT-4）生成一批答案再由人工审核。规模至少几千条，且要覆盖不同问题类型，不能全是同一类问题。

2. **选微调方式**：通用的做法是 LoRA（Low-Rank Adaptation），不修改原模型的所有参数（全量微调太贵了），而是在模型旁边挂一个小矩阵，只训练这个小矩阵。训练完成后，推理时把小矩阵和原模型合并，效果接近全量微调但 GPU 成本降低 90% 以上。现在主流框架（LLaMA-Factory、HuggingFace PEFT）几行代码就能跑。

3. **训练**：把数据喂给模型，让模型在领域数据上学习——本质上就是让模型"背"你的领域知识和回答风格。Embedding 模型的微调更简单：给一对对的 (query, positive_doc, negative_doc)，让模型学会拉近 query 和正确文档的距离、推远和错误文档的距离。

4. **评估和部署**：微调完后在评测集上对比微调前后的指标（MRR / Faithfulness），确认有提升且没有退化。通过后把微调模型部署到一个独立的 API 端点，业务代码里把模型名切过去。

坦诚说，这一步离我们还很远。当前先靠 Prompt engineering 顶着，等数据积累够了再考虑。

### 2.5 线上评测 & A/B 实验

**Q33.** 你有做在线 A/B 实验的能力吗？怎么分流量？怎么衡量实验效果？有没有指标体系？核心指标和护栏指标分别是什么？

**当前：没有做在线 A/B**

日均 100 问，样本量太小，在线 A/B 的统计显著性是做不到的。但不做不等于不会。面试时一定要把方案讲清楚——证明你有这个意识，只是规模没到。

**在线 A/B 和离线评测的本质区别**

离线评测（Q13/Q14/Q15）回答的是"检索/生成质量变好了吗"，用的是一批固定的、标注过的 QA pairs。在线 A/B 回答的是"用户实际体验变好了吗"，用的是真实用户的行为数据。

两者的结论可能不一致。举个例子：离线评测显示新的 chunk 策略 MRR 提升了，但在线一看，点赞率反而下降了——因为新策略虽然检索更精准，但 chunk 更短导致 LLM 答案不完整，用户觉得"不够详细"。这种矛盾只有在线 A/B 才能发现，离线评测看不到。

**如果要做，方案分四步**

**第一步：分流量。** 核心原则是按 user_id 做一致性哈希，保证同一个用户始终落在同一组——不会出现用户 A 第一次看到新版本、第二次看到旧版本。具体：取 user_id 的 hash 值，模 100，0~49 进对照组（旧版本），50~99 进实验组（新版本）。五五分。

这里的一个陷阱：不能按 IP 分，也不能按 session 分——同一个用户可能换 IP、同一 IP 可能多个用户。按 user_id 分才能保证用户级别的一致性。如果系统没有用户登录（匿名访问），那退一步用浏览器 fingerprint 或 cookie。

**第二步：确定指标体系。** 指标分两类——核心指标和护栏指标。

核心指标是你想要提升的东西，实验成功与否看它：
- 用户点赞率（user_click="赞" 的比例）
- 答案采纳率（用户复制答案文本、没有再搜索的比例，需要前端埋点）
- 转人工率（看完答案后点了"联系人工"的比例）

护栏指标是你不能让它退化的东西，如果恶化了实验必须终止：
- 端到端 P95 延迟（不能因为新策略变慢）
- 错误率（5xx 的比例不能上升）
- 空结果率（"未找到相关信息"的比例不能暴涨）

核心指标决定"新版本好不好"，护栏指标决定"新版本能不能上"。即使核心指标提升了，只要护栏指标有一条明显退化，实验也必须暂停。

**第三步：跑实验，等样本量够。** 这是在线 A/B 最难的部分——要跑多久才有统计显著性？

统计显著性的粗略判断：点赞率从 85% 提升到 90%，在 95% 置信度、80% 统计功效下，每组至少需要约 500 个有反馈的样本（不是 500 次请求，是 500 次点赞或点踩）。如果日均 100 次请求、约 30 次有反馈，每组需要跑约 17 天。这也是为什么当前不做——数据量支撑不了快速迭代。

**第四步：实验结束后决策。** 如果核心指标显著提升、护栏指标没有退化 → 全量上线新版本。如果核心指标没变化 → 本次实验没有结论，新版本和旧版本效果无差异，是否上线看其他因素（代码更简洁、维护成本更低等）。如果护栏指标退化了 → 不管核心指标怎么样，实验终止，回退到旧版本。

**一个常见的面试追问：你和离线评测结果矛盾了怎么办**

离线评测说新版本更好（MRR 涨了），但在线实验说用户点赞率没变化甚至下降。排查方向：第一，离线评测集是不是和线上分布不一致？如果评测集 80% 是高频问题，但线上长尾问题占了 50%，那离线评测的"好"只是高频问题的好。第二，指标本身是不是有问题？MRR 提升但点赞率不变，说明检索更精准了不等于用户更满意——可能是答案的完整度、可读性、排版出了问题。第三，实验本身设计是否有问题？比如两组用户不完全随机（新用户全进了实验组），导致组间 baseline 不一致。

**Q34.** 更新了一个新的切片策略，你上线前怎么验证不会引入退化？上线后怎么监控？如果变差了怎么自动回滚？做到自动化了吗？

**切片策略变更的特殊性**

切片策略不像改 prompt 或改映射表——改了立刻生效、不用重建任何东西。切片策略一变，所有 chunk 的边界都变了，必须全量重建索引（重新切分 → 重新 embedding → 重新入库）。这意味着两件事：第一，验证必须在上线前充分做，上线后再发现问题就晚了；第二，回滚不是"改回参数"就行，是要把旧索引重新加载回来。

**上线前验证：离线评测是唯一的防火墙**

因为要全量重建，不能在线上旧索引上直接改——删了旧的才发现新的有问题，线上就挂了。做法是在同一个 ChromaDB 里新建 collection，新旧并存，验证完再切。步骤：

1. **用新策略建一个新 collection**：不对线上旧 collection 做任何操作。新建一个 collection（如 `docs_v2`），对全量 500 文档用新切分配置跑一遍切分 + embedding + 入库。耗时约 2 分钟。同一套环境，新旧两个 collection 并存，互不影响。

2. **跑全量检索评测**：在新索引上跑 100 条 QA pairs，输出新旧两版对比。核心看两个指标——MRR 和 Recall@5。同时看有没有之前能召回的 case 在新策略下完全召不到了（Recall 归零的 case）。

3. **跑 RAGAS 生成评测**：检索没问题不代表生成没问题。用新索引的 top-5 chunk 跑 RAGAS 三条指标（Faithfulness / Answer Relevancy / Answer Correctness），对比旧版。因为 chunk 变了，LLM 拿到的是不同粒度的上下文——可能检索更准但 chunk 太碎导致 LLM 信息不完整。

4. **Edge case 人工抽查**：不只看均值。重点看两类 case——评测分数差异超过 10% 的（搞清是不是退化）、以及之前能正确回答但现在不能的（搞清根因）。

5. **通过标准**：两项检索指标不能有统计显著的下降（均值跌了但差异 case 逐条看确认不是退化也算过），RAGAS Faithfulness 均值不能低于 0.85，不能出现之前能回答正确、新策略下完全回答错误的 case（数量 > 0 条就要排查）。

**上线方式：新旧索引并行，不是直接替换**

不是一个 deploy 命令把线上旧索引删了换新的。标准操作是：

1. 在 ChromaDB 中新建一个 collection（比如 `docs_v2`），把新策略的索引建在里面。旧 collection（`docs_v1`）保持不动，继续服务线上流量。

2. 在 FastAPI 配置中加一个 `active_collection` 参数，当前指向 `docs_v1`。

3. 改配置 `active_collection = docs_v2`，重启 FastAPI（或热加载配置）。因为每个节点有自己的 ChromaDB 数据文件，新 collection 需要在所有节点上都建好——管理员通过管理接口逐个触发，或用一个脚本批量调 4 个节点的重建接口。全部节点重建完毕后切换配置，4 个节点同时生效。

4. 观察一段时间（至少覆盖一个完整工作日），确认无退化后，再删掉旧 collection。

如果发现退化：`active_collection` 改回 `docs_v1`，秒级回滚。旧索引一直在那里没被删，不需要重新构建。

**上线后监控：看三个信号**

1. **延迟**：chunk size 变了，Rerank 和 LLM 的输入 token 数会变。P95 延迟不能明显恶化。来自分步骤日志。

2. **点赞率**：上线后当天的点赞/点踩比例，和上线前一周的均值对比。如果点踩率突升，立即排查。来自 QueryLog user_click。

3. **转人工率**：如果新的切片策略导致某类问题召回失败，用户会转人工群。上线后几天内人工群的问题量是否异常上升。

**回滚：手动操作，没有自动化**

回滚就是上面说的——`active_collection` 切回旧 collection。但为什么没有做自动化？因为自动回滚需要一个"好坏"的判断标准，而这个标准很难量化成一条规则。是延迟涨了 100ms 就回滚？还是点踩率涨了 5% 就回滚？还是某个特定 query 答错了就回滚？如果没有明确的触发条件，自动回滚要么反应过度（正常波动触发回滚），要么反应不足（退化已经持续了很久还没触发）。

当前做法是：上线后人工观察一天，没有异常就算稳定。这不够"自动化"，但在日均 100 问的量级下，一天内产生的数据足够判断好坏，且人工判断可以权衡多个信号（延迟、点赞、转人工的交叉分析），比单一阈值规则更准。如果未来 QPS 上来了、切片变更频繁了，再考虑加自动回滚——触发条件不是单一指标阈值，而是"两个以上护栏指标同时恶化超过 N%"的复合条件。

```
│  Answer Relevancy / Answer Correctness）                 │
└─────────────────────────────────────────────────────────┘
```

**各层技术栈和选型理由**

**接入层 —— FastAPI + Uvicorn，4 实例。** 无状态设计，请求可以落到任意实例。选 FastAPI 而不是 Flask 或 Django：对 SSE 流式响应有原生支持（`StreamingResponse`），异步架构天然适合我们这种 I/O 密集型链路（频繁调内部 API 等待响应）。Django 太重，Flask 做 SSE 需要额外折腾。Uvicorn 做 ASGI server，4 台机器各一个实例，Nginx 在前面做反向代理。

**在线检索层 —— 8 步串联（详见 Q17）。** 每一步的选型理由：缓存选 ChromaDB 同库方案而非 Redis（零额外依赖）；改写走映射表 + LLM 两层而非纯 LLM（映射表保证专有名词不丢）；Embedding 走内部 gRPC 而非 HTTP（低延迟）；双路检索中向量走 ChromaDB HNSW、BM25 走 jieba + 自建倒排（简单可控）；融合选 RRF 而非线性加权（量纲不同）；Rerank 选 Qwen3-rerank cross-encoder 而非 LLM-based rerank（低延迟、低成本）；生成选 DeepSeek V4 Flash 而非 Pro（成本优先）；QueryLog 选 SQLite 而非 MySQL（零运维，2000 条记录无需数据库服务）。

**数据层 —— ChromaDB + 内存 BM25 + SQLite。** ChromaDB 存向量和元数据，选它的理由见 Q7（六方案对比，综合代价最低）。BM25 倒排索引在内存中构建和查询，启动时从 ChromaDB 读 chunk 原文自动重建，不依赖外部搜索引擎。QueryLog 用 SQLite 本地文件，不需要起数据库服务。

**离线构建层 —— 管理员触发，单人操作。** 文档处理走 LangChain MarkdownHeaderTextSplitter 做语义切分 + LLM 生成特殊文本摘要。向量化走和在线同一套 text-embedding-v3。索引构建完成后通过 `active_collection` 配置指针切换上线。评测走 RAGAS 三条指标，100 条 QA pairs 做回归验证。

**选型贯穿的一条线**：在满足功能的前提下，尽可能降低外部依赖。整个系统除了内部 LLM API，没有任何外部服务——没有 Redis、没有消息队列、没有独立的搜索引擎、没有独立的数据库服务。ChromaDB 嵌入在 FastAPI 进程内（PersistentClient），BM25 倒排索引在内存中自建，QueryLog 用 SQLite 本地文件。这不是因为"不知道这些技术"，而是因为在 500 文档、日均 100 问的规模下，引入任何外部服务的运维成本都超过它带来的收益。

**核心 `/ask` 端点的实现**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
import json, uuid

app = FastAPI()

class AskRequest(BaseModel):
    question: str

@app.post("/ask")
async def ask(req: AskRequest):
    session_id = str(uuid.uuid4())

    return StreamingResponse(
        _generate_stream(session_id, req.question),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",   # 禁用 Nginx 缓冲
        }
    )

async def _generate_stream(session_id: str, question: str):
    try:
        # 1. 语义缓存检查
        cached = check_semantic_cache(question)
        if cached:
            yield _sse("answer", cached["answer"])
            yield _sse("sources", cached["sources"])
            yield _sse("done", {"cache": "hit"})
            return

        # 2. Query 改写
        rewritten = rewrite_query(question)
        yield _sse("status", {"step": "rewrite", "query": rewritten})

        # 3. 双路检索 + RRF + Rerank
        results = retrieve_and_rerank(rewritten)
        yield _sse("context", {
            "chunks": [{"file": r["file_name"], "text": r["text"][:120]}
                       for r in results]
        })

        # 4. LLM 生成 —— 流式逐 token 输出
        full_answer = ""
        async for token in llm_stream_generate(question, results):
            full_answer += token
            yield _sse("token", token)

        # 5. 写 QueryLog
        write_querylog(user_id, session_id, question, rewritten, results, full_answer)
        yield _sse("done", {"cache": "miss"})

    except Exception as e:
        yield _sse("error", str(e))

def _sse(event_type: str, data) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event_type}\ndata: {payload}\n\n"
```

**SSE 事件类型和前端处理**

| 事件 | 携带数据 | 前端动作 |
|------|---------|---------|
| `status` | 当前步骤描述 | 展示进度（"正在改写..."） |
| `context` | 检索到的 chunk 列表 | 展示来源文档 |
| `token` | 单个文本片段 | 逐字追加到答案区 |
| `sources` | 引用列表 | 末尾展示引用链接 |
| `error` | 错误信息 | 展示错误提示 |
| `done` | 结束标记 | 关闭连接 |

前端用 `fetch` + `ReadableStream` 接收：

```javascript
fetch("/ask", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question: "OA告警阈值怎么配" })
}).then(response => {
    const reader = response.body.getReader();
    const decoder = new TextDecoder();
    function read() {
        reader.read().then(({ done, value }) => {
            if (done) return;
            // value 是 "event: token\ndata: xxx\n\n" 格式，按行解析
            parseSSEAndRender(decoder.decode(value));
            read();
        });
    }
    read();
});
```

**为什么选 FastAPI 而不是 Flask**

| | FastAPI | Flask |
|---|---|---|
| 异步支持 | 原生 async/await（Starlette） | Flask 2.0+ 支持但生态不完善 |
| SSE | `StreamingResponse` 开箱即用 | 需手动构造 generator |
| 请求校验 | Pydantic，类型自动检查 | 手动 `get_json()` + 手写校验 |
| 自动文档 | Swagger UI 自动生成 | 需额外装插件 |
| 性能模型 | ASGI，异步 I/O 不阻塞 | WSGI，同步模式效率低 |
| 生态 | 较新，插件还在长 | 十几年，什么插件都有 |

选 FastAPI 的核心原因：链路中大量 I/O 等待（调 Embedding gRPC、等 LLM 流式输出），异步模型下 await 不会阻塞整个 worker。SSE 流式是核心体验——用户看到逐字渲染而不是等 3 秒一次出结果，`StreamingResponse` 让这一步非常简洁。

**SSE vs WebSocket**：SSE 单向推送（服务端 → 客户端），基于 HTTP，实现简单。WebSocket 双向通信，需握手升级协议，适合聊天类交互。RAG 问答是"一问一答流式返回"，SSE 完全够用。

**Q36.** 你这个系统最复杂的技术难点是什么？是检索、生成、工程、还是数据？你个人解决了其中最难的什么问题？

**最复杂的技术难点：混合检索的端到端调优**

不是说某个单一模块（比如 HNSW 或 BM25）本身有多复杂，而是"把几个模块串起来后，调出一个整体最优的效果"这个过程。

具体说：向量检索、BM25、RRF 融合、Rerank 精排——四个环节各有参数（HNSW 的 ef_search、BM25 的 k1/b、RRF 的 α/β/k、Rerank 的 top-k），每个参数改动都会影响最终的 MRR 和 Recall@5。问题是它们之间不是独立的——调大 Rerank 的 top-k 可以弥补 RRF 的排序缺陷，但也可能引入噪声让 LLM 生成质量下降。单独调一个参数容易陷入局部最优，全局搜索又因为 embedding 是整个链路里唯一耗时的步骤（其他环节的评估在已有 embedding 上重算即可），所以合理的做法是先固定 embedding 跑全量评测，再在剩余参数空间里做网格搜索。

这里面最花时间的不是"想方案"，而是"验证方案"——每次改参数跑 100 条 QA 看指标变化，然后再人工抽查差异 case 确认不是噪声。循环几次才能收敛到一个满意的配置。这个过程没有银弹，就是反复实验 + 人工判断。

**我个人解决的核心问题**

不是某一个具体 bug，而是两件事：

第一，搭了从零到一的评测框架。在没有任何标注数据的情况下，自己从线上群聊里收集真实问题、标注 chunk ID、分层抽样构建了 100 条 QA pairs。然后设计了按问题类型拆组的评测指标（单答案型用 MRR、综合型用 Recall@5），让评测不再是"跑一个数字"而是"不同问题分别看"。这个框架成了之后所有决策的基础——chunk size 选型、Rerank 消融实验、RRF 参数调优、模型切换验证，全部依赖它。

第二，做了每个关键环节的消融实验。不是凭经验说"加了 Rerank 肯定好"，而是跑了对照组——不加 Rerank vs 加 Rerank，数字摆出来（MRR 0.831 → 0.868）。同样的方法论用在 chunk size 选型、RRF 参数搜索上。这给面试官展示的不只是"我们做了 Rerank"，而是"我知道 Rerank 贡献了多少、值不值它的延迟代价"。
