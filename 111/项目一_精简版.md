# RAG 问答系统面试拷打清单

---

## 项目背景

我所在的团队负责一款内部云管平台，平台下面挂了几十个云服务。团队大约十几个人，分了多个方向，每人负责不同模块——有人管计算、有人管存储、有人管网络、有人管监控。每个方向的同学在日常开发和 oncall 过程中积累了大量知识：某个服务的启动流程是什么、某个告警的排查步骤、某个配置项改了会影响哪些下游、某个 API 的限制条件和默认值。

这些知识过去沉淀在内部 Wiki 里，逐年累积，到我接手时已经有约 500 篇 Markdown 文档。但文档多不代表知识可获取。

团队平时遇到问题的实际路径是：打开 Wiki 顶部的搜索框，输入几个关键词，回车。Wiki 的搜索是关键词全文匹配——你输入的词必须出现在文档正文里才能命中。问题在于，用户输入的词和文档使用的词往往不在一个语义空间。"OA 告警阈值怎么配"的答案在「优化顾问监控告警配置」这篇文档里，但这两个字符串之间没有任何公共关键词，Wiki 搜索返回零结果。用户搜不到，就去内部群里 @oncall 同学。oncall 同学看到问题，在脑子里匹配——"这个问题我看过，在某某文档里"——然后把链接发到群里，或者直接打字回答。同样的问题——"region 白名单在哪配""这个报错什么意思""某服务的默认限制是多少"——一天被问七八次，oncall 每天有大量时间消耗在重复问答上，真正的复杂排查反而没精力做。

这个流程有三个不可持续的地方：

**第一，知识检索依赖人脑索引。** oncall 同学是唯一知道"问题 A → 文档 B"映射关系的人。他请假、离职、转岗，这个映射表就没了。而且这套映射表只在 oncall 一个人脑子里，团队其他人遇到问题时没法自助查询——只能等他回复。

**第二，文档的维护和使用是断开的。** 写文档的人花时间把排查步骤写清楚，但用的人搜不到，文档就白写了。长此以往，写文档的动力会下降——"反正写了也没人看"——知识沉淀的循环就断了。

**第三，规模效应在帮倒忙。** 团队越扩张、服务越多、文档越多，oncall 的负担越重，但 oncall 的人数不会等比增长。500 篇文档靠一个人翻译，5000 篇呢？这个模式的天花板就在眼前。

所以这个项目的必要性不在于"用 AI 提升效率"这种大词，而在于一个非常具体的判断：**团队的知识已经存在了（500 篇文档），但缺少一个能把自然语言问题翻译成文档检索的中间层。过去这个中间层是 oncall 的人脑，但这不可持续。RAG 是目前最成熟、成本最低的方式来做这个中间层。** 用户用自然语言提问 → 系统做语义检索 → 找到相关文档片段 → LLM 组织成带引用的答案。不需要 oncall 在中间做翻译。

为什么要自己做而不是买现成的？三个原因：所有模型必须部署在内网（合规要求，外部 API 不可用），内部 Wiki 的内容结构和术语体系需要定制化的切片和检索策略，以及答案必须带 chunk 级别的溯源引用（市面上的通用方案做不到这个粒度）。

系统上线后，日均处理约 100 个问题，把 oncall 从重复问答中释放出来，同时让团队成员 7×24 小时能自助获取答案——不需要等别人回复。这不是一个大系统，但解决的是一个真实存在的问题。

## 一、离现阶段（数据处理、索引构建、评估体系）

### 1.1 文档处理 & 切片策略

**Q1.** 500个文档，你用了什么切片策略？固定长度、固定token数、还是基于语义的切片？为什么选这个方案？你对比过哪几种切片方式的召回效果？

我们的文档主要是 Markdown 格式，面向内部用户的 API 文档、故障手册、功能说明和版本更新记录。基于这些文档结构化的特点，我们的切分策略是：先用 Markdown parser 按一二级标题做结构拆分，然后在每个二级标题域内，如果内容超过设定的 token 上限，再递归地按段落和行进行切分。

  对于特殊文本，比如表格、JSON 配置、代码块，我们不会按上限硬截断，而是做两条处理：第一，在清洗阶段用 LLM 离线为这些特殊块生成一段自然语言描述，拼入 chunk 的 content 中，补充语义信息；第二，对于非特殊文本的普通段落，我们会把当前 chunk 所属的一二级标题路径前置拼接到 content 头部。这个做法不是前期设计阶段就定下来的——在开发阶段我自己测试时发现，很多 QA 匹配效果很差，排查根因后定位到一个共同问题：chunk 内容是纯技术描述，脱离了标题路径后缺乏上下文语义锚点。比如一段讲"告警阈值配置"的文字，它所属的标题是"优化顾问 > 监控告警"，切分后标题丢了，chunk 里只剩通用描述，"OA告警怎么配"这种带产品上下文的 query 在向量和关键词两个维度都匹配不上。标题本身携带了很强的语义信息，把它拼回 content 后匹配效果明显改善。这个改动属于开发阶段自测发现的问题驱动修复，还没走到 QA 评测选型那一步就改了——因为不做的话系统基础可用性都成问题。这样即使 chunk 被单独召回，大模型也能知道这段话出自哪个文档的哪个章节。

  关于 chunk size 的选择，我们对比了 256、384、512 三个档位。选型逻辑分两步。第一步，全量 500 个文档做语义切分后统计截断率。截断的正确定义是：如果当前 chunk 长度触达上限，且它和相邻 chunk 共享同一标题路径，说明它是被硬截断的，而不是刚好自然结束。256 截断率明显偏高，淘汰。384 和 512 截断率都在百分之一左右，差距不大。第二步，我们构造了 100 条 QA pairs 做检索召回评测。评测集按场景分层抽样，覆盖 API 类、故障类、功能细节类、版本类，同时刻意保留了 10%~20% 的冷门问题样本。每条 query 是用户在群里的真实问题，answer 标注对应的正确 chunk ID。评测指标按问题类型拆成两组：单答案型用 MRR，综合推理型用 Recall@5。实测结果：384 单答案型 MRR 0.831（vs 512 的 0.791），综合推理型 Recall@5 0.892（vs 0.874）。384 两项均小幅领先，同时 chunk 更短、检索延迟更低，所以我们选了 384。切分完成后，我们对 384 和 512 两个配置都做了人工抽检，重点检查被截断的 chunk（因截断率仅 ~1%，实际样本量很小），确认语义均完整。未被截断的 chunk 本身就是完整段落，无需检验。

  关于 overlap，我设的是 0。先厘清 overlap 到底解决什么问题：固定长度/固定 token 切分是盲的——每 N 个 token 一刀，切分点随机，可能砍在句子中间甚至一个词中间，所以必须加 overlap 保证每个句子至少在一个 chunk 里是完整的。但我们的切分是按 Markdown 标题 + 段落 + 行边界来断的，切分点天然落在作者有意安排的语义边界上——段落结束处就是一个完整意思的收束，标题切换处就是主题变化。我们不会在一个段落的句子中间切一刀，所以 overlap 要解决的核心问题（句子级断裂）在我们的切分策略下根本不存在。

至于段落间的语义关联——一段末尾和下一段开头可能在讲同一个东西——这个问题 overlap 也解决不了。overlap 只是让边界处的句子在相邻 chunk 里各出现一次，但对于"两个完整段落各讲一个概念的不同方面"的情况，拿到一个 chunk 仍然不知道另一个补了什么。这种跨 chunk 的语义关联，我们的解靠的不是 overlap，而是检索链路的设计：两段共享关键词和语义 → 双路检索把它们都召回 → RRF + Rerank 把相邻 chunk 排在前面 → top-5 一起进 LLM → LLM 跨 chunk 推理拼接。

简单说：句子级断裂不需要 overlap（切分点只在段落边界），段落间关联 overlap 帮不上忙（要靠 top-k + LLM）。所以 overlap=0 不是偷懒，而是在我们这个切分策略下，overlap>0 增加的只是冗余存储和检索去重开销，不太可能带来实质召回提升。


  关于表格的检索召回率，目前我们没有单独量化，因为在实际业务中，用户的问题主要以功能和故障描述为主，纯表格类问题占比较低。但这个判断更多是基于经验而不是数据验证，这一点是我需要改进的。


**Q2.** 你文档的格式是什么？纯文本、Markdown、PDF、Word、Confluence？不同格式你怎么做解析和归一化的？表格和图片你是怎么处理的？表格被切碎了怎么办？

 我们的 500 个文档全部来源于内部 Wiki 平台，原生 Markdown 格式，由团队自己维护在 Git 仓库中，不存在从 Confluence、Word
  或网页转换的场景。这保证了格式一致性，不存在转换过程中的编码错误或层级丢失。

  解析方案上，我们使用 LangChain 的 MarkdownHeaderTextSplitter。它底层基于 Python markdown 库做 AST
  解析，按标题层级递归拆分，能正确区分代码块内的 # 符号和真正的 Markdown 标题，不会出现正则匹配常见的误判问题。我们在选型时全量跑了 500
  文档的解析验证，检查了标题层级连续性、空 chunk 率和 chunk
  边界合理性，没有出现解析失败或静默切错的情况。坦白说我没有逐行读过它的源码，但通过输出验证确认了它在我们的文档集上是可靠的。

  表格、JSON 和代码块的处理，我们不做硬截断，而是全文保留，同时在离线清洗阶段用 DeepSeek V4 Flash
  模型为这些特殊文本块生成自然语言摘要。具体做法是 few-shot prompt，把上下文和特殊文本一起给模型，让它生成一句功能性的标题，比如一个 JSON       
  配置块会被总结为"region 白名单配置"。整个文档集统计下来共 37 个表格、43 个 JSON 配置块、35 个代码块，每次调用的输入 token
  大约一千左右，输出只有几十个 token。因为我们用的是内部统一 API，成本在整体预算中几乎忽略不计。

  图片的处理是我们第一期明确做的取舍。目前模型不支持多模态，图片在解析阶段直接丢弃，在原文位置插入占位符标记。我也人工统计了 500 篇文档中图片的类型和分布：大部分是截图（报错界面、控制台配置截图），少量是架构图和流程图。基于这个分布数据，决策思路很清晰——截图占绝大多数，走 OCR 文字提取嵌入原文就能覆盖主要场景。对于"按照下图所示"这类无意义的断裂引用，我在全量 chunk 检验时也做了手动删除或改写，确保进入 LLM 的 chunk 里没有指向不存在内容的引用。

  如果后续要做图片支持，方案是：先抽样统计图片类型比例。如果截图为主，走 OCR 文字提取 + 嵌入原文，不改检索架构。如果架构图/流程图占比高，则用视觉模型生成自然语言描述替代图片，仍然走纯文本检索。多模态 embedding 独立建索引的方案工程量大，只有在图片成为核心信息载体时才值得投入，就我们内部文档特点判断大概率不需要。

**Q3.** 切片大小设了多少？这个数字是怎么定出来的？你有做过消融实验（ablation study）吗？chunk overlap 设了多少？overlap 设成多少对最终效果的影响你量化了吗？

我们的 chunk size 最终选了 384 token，overlap 设的是 0。

  选型流程分四步。

  第一步，确定候选值。我把 500 个文档全量跑了一遍 tokenizer，看了 chunk 长度的实际分布，中位数大概在 300 token 左右，所以定了 256、384、512     
  三个候选值在真实分布的两侧，覆盖了"偏小、适中、偏大"三个区间。

  第二步，截断率筛下限。在全量 500 文档上分别用三个上限做语义切分，统计截断率。截断的正确定义是：chunk 长度触达上限且与相邻 chunk
  共享标题路径。256 的截断率明显偏高，说明 256 装不下我们的内容，频繁腰斩语义，淘汰。384 和 512
  截断率都在百分之一左右，说明两个都足够大，截断率到这里就完成了它的使命，不再参与后续决策。

  第三步，检索评测做精选。384 和 512 两个配置全部跑检索评测。我们构造了 100 条 QA pairs，按文档类型和问题场景分层抽样，高频约占八成，冷门约占两成。每条 query 标注了正确的 chunk ID 作为 ground truth。两个配置分别计算每条 query 的 MRR 或 Recall@5。384 在单答案型上 MRR 0.831 vs 512 的 0.791，综合推理型上 Recall@5 0.892 vs 0.874，两项均小幅领先。我们额外把差异 case 逐条做了人工确认，判断 384 的结果确实更好，所以选了 384。

  第四步，chunk 质量人工抽查。切分完成后，我们对 384 配置下的 chunk 做了抽样检查，看了几十个 chunk，确认没有语义被明显截断或一个 chunk
  内堆叠多个不相关话题的情况。坦白说这一步是人工的，没有双人交叉验证，不够严谨。

  关于消融实验，我需要区分两类情况来说明。

chunk size 的选择是通过 QA 评测系统性做的（256/384/512 三个候选，截断率 + 100 条 QA pairs 检索评测），这一步方法论是对的——三个候选在同等条件下跑评测，看 MRR 和 Recall@5，选出最优的 384。但我没有为 chunk size 补一个反向消融：把 chunk size 从 384 改成 512 或 256 再跑一轮完整端到端评测，看最终答案质量掉多少。这样我就能量化 chunk size 对最终效果的贡献，而不是只看检索环节的 MRR 变化。

header 拼接和特殊文本 LLM 摘要则不是"选型"问题，它们是开发阶段自测时发现问题后的修复——不做的话系统基础可用性都成问题，根本不是可选的优化项。所以严格来说它们不适用于消融实验的逻辑：消融实验的前提是这个设计是可选的、有替代方案的，而 header 和 LLM 摘要在我们的场景下是必须的。我坦诚说，如果面试官追问我"header 拼接贡献了多少 MRR"，我答不出确切的数字——因为我没有跑过"去掉 header 拼接"的对照组评测。这是我的一个盲区。正确的做法是为每个关键设计——无论它是选型决策还是问题修复——都跑一轮对照评测，看效果掉多少，这样面试时能拿出数字而不是"感觉有用"。

  关于 overlap，我设的是 0。Q1 中已经详细论证了——overlap 的核心用途是补救固定长度切分的句子级断裂，而我们按段落/行边界切分，切分点不在句子中间，所以 overlap 在这个问题上的收益是零。段落间语义关联靠的是双路检索 + top-k + LLM 跨 chunk 推理，不是靠 overlap。我没有跑过 overlap>0 的对照实验来量化验证这个结论，所以严格来说这是一个基于切分策略的逻辑推理，不是数据驱动的决策。但和 chunk size 不同，我不认为这是高优先级要补的实验——因为它的理论收益上限本来就很低。

**Q3-附. Overlap 和父子 Chunk 听起来很像——它们到底有什么区别？各自解决什么问题？**

Overlap 和 Parent-Child（父子 chunk）都涉及"chunk 之间的内容重复"，但解决的问题本质不同。

**Overlap 解决"一句话被切成两半"的问题。** 固定长度/固定 token 切分是盲切的，切分点可能落在句子中间，导致相邻 chunk 各含半句话，embedding 质量下降。Overlap 让相邻 chunk 共享一段重叠内容，保证完整句子一定存在于至少一个 chunk 中。其本质是**内容在相邻 chunk 间冗余复制，用存储换语义完整**。Overlap 只在切分策略会导致句子被拦腰截断时才有必要——我们的 MarkdownHeaderTextSplitter 按标题层级在段落/行边界切分，不会在句子中间下刀，所以 overlap=0 是合理的。

**父子 chunk 解决"搜得准"和"答得好"之间的矛盾。** 检索阶段希望 chunk 小，embedding 语义聚焦、检索精准；生成阶段希望 chunk 大，LLM 有充足上下文。父子 chunk 把文档切两套：子 chunk（小块，150~200 token）用于向量检索，语义聚焦；父 chunk（大块，如 800 token）用于给 LLM 看，信息完整。检索命中子 chunk 后，通过 metadata 中的 parent_chunk_id 返回父 chunk。两者是层级嵌套关系，不是重复存储。我们当前没有做父子 chunk，因为综合推理型 Recall@5 已达到 0.914，够用；如果未来文档复杂度上升，在 metadata 加 parent_chunk_id 即可。

**Q4.** 你怎么处理文档更新的？文档有变更（新增、修改、删除）时，索引怎么同步？是全量重建还是增量更新？增量更新时怎么保证 chunk 之间引用关系不破裂？

 我们在每个 chunk 的 metadata 里记录了三个关键字段：file_name，作为文档级别的唯一标识；chunk_hash，记录当前 chunk 内容的 MD5，用于变更检测。

  **新增**：用 file_name 查询向量库。查不到，说明是新文档，直接切分入库。查得到，说明文件名重复，返回二次确认——"该文件名已存在，确认覆盖？"操作人确认后才进入修改流程。

  **修改**：用 file_name 查出该文档的所有旧 chunk，按内容 hash 做集合差集比对：
  - 旧 chunk 集合中 hash 不在新 chunk 集合中的 → 删除
  - 新 chunk 集合中 hash 不在旧 chunk 集合中的 → 插入并重新 embedding
  - hash 同时出现在两个集合中的 → 不动，跳过 embedding

  hash 集合差集的实现是两个 set 做差集，五六行 Python。文档局部修改时，大部分 chunk 的 hash 不变，可跳过 embedding 和写入。

  **删除**：用 file_name 查出该文档下所有 chunk，逐个删除后验证数量归零。

  **并发安全**：我们的架构是 4 个 FastAPI 实例各自内嵌 ChromaDB，每个实例有独立的 persist 目录。文档修改操作全部为同步调用（ChromaDB SDK 增删查为阻塞调用），整个流程中没有并发写入路径——进程内单线程事件循环天然串行，不存在两个请求同时修改同一文档的竞争。即使切换到异步框架，ChromaDB 的同步接口也会阻塞事件循环，协程无法在写入过程中切换，同样不会有并发安全问题。

  **多实例同步**：4 个实例各自内嵌 ChromaDB、无共享状态。管理员上传文档的请求经 LVS 负载均衡落到单个实例，只有该实例的索引更新。当前不做自动同步，采用手动各自重建的方式：管理员在一个节点上传后，在其他 3 个节点重复执行一次上传操作。原因有两点。第一，量级——文档更新是低频操作（几天甚至一周一次），4 个节点各自重建的 embedding 调用量在总量级下微不足道，不值得为同步引入工程复杂度。第二，合规——跨节点文件拷贝绕过数据处理链路，在合规审计下不可追溯。每个节点独立走"上传→切分→embedding→写入"链路，日志完整可回放。更新完成后通过健康检查接口比对各节点的 chunk 总数，一致则通过。


**崩溃恢复**：修改流程里先删后插是两步操作。如果删除成功后、插入前进程崩溃，该文档的索引暂时缺失。ChromaDB 作为嵌入式库不提供事务原子性。当前不依赖外部机制来保证原子性——管理员入口是上传模式，感知到异常后重新上传即可恢复。500 文档/2000 chunk 的规模下 rebuild 不到半分钟，这个恢复成本可以接受。

  **ChromaDB 的存储结构**

先把 ChromaDB 到底存了什么说清楚。ChromaDB 不是一个纯向量数据库，它是一个"带向量检索能力的嵌入式文档存储"。底层分两层，各自存不同的东西：

**SQLite 层 —— 存"业务数据"**：chunk 原文（documents）、元数据（metadatas）、chunk ID（ids）。这三样存在 SQLite 的表中，可以拿任何 SQLite 工具直接打开看。注意：向量（embeddings）**不存这里**。

**HNSW 图层 —— 存"向量索引"**：768 维 float32 密集向量 + 图结构的边。由 hnswlib（C++ 库）管理，存在 `.chroma/` 目录下的二进制文件中，不是 SQLite。

这两层通过 chunk ID 关联——同一个 ID 在 SQLite 里对应一行数据，在 HNSW 图里对应一个节点。

调用 `collection.add()` 时，一次调用实际上发生了三件事：

```
collection.add(
    ids=["chunk_001"],                              → 写入 SQLite（主键）
    documents=["OA监控告警的配置方法..."],            → 写入 SQLite（原文）
    metadatas=[{"file_name": "oa.md", ...}],         → 写入 SQLite（元数据）
    embeddings=[[0.12, 0.87, -0.33, ..., 0.05]],    → 写入 HNSW 索引（向量 + 建图连边）
)
```

三条各自去各自的地方：原文和元数据进 SQLite，768 个 float32 进 HNSW 图。ID 是它们之间的纽带——检索时先在 HNSW 图中做近邻搜索，拿到 top-k 的 ID 列表，再用这些 ID 去 SQLite 查出原文和元数据返回。

调用 `collection.get(ids=["chunk_001"])` 时只查 SQLite，不动 HNSW。调用 `collection.query(query_embeddings=[...])` 时先查 HNSW 拿 ID，再查 SQLite 拿原文——只返回 `include=["documents", "metadatas"]` 指定的字段，向量本身默认不返回（768 维 float32 × N 个结果，返回了也浪费带宽）。

对你能看到什么：`./data/chroma_db/` 目录下的 SQLite 文件可以用任何 SQLite 工具打开。出问题时你能确认"这条 chunk 到底在不在库里、metadata 对不对"。黑盒的部分是 hnswlib 的 C++ 实现——图的构建、节点增删的具体算法——但这部分对使用者来说是透明的。

打开 SQLite 会看到很多表，大部分是 ChromaDB 内部管理用的，真正和你的数据相关的只有几张：

| 表 | 作用 | 你的数据在哪 |
|----|------|-------------|
| `collections` | 你创建的集合列表 | 一行，name 是你起的名字，dimension=768 |
| `segments` | 内部把每个 collection 拆成元数据段、向量段、记录段 | 一个 collection 挂 3 个 segment |
| `embedding_metadata` | **你的数据在这里**——chunk 的元数据和原文 | metadata 展开成多行键值对（key + value），原文存在 key=`chroma:document` 的行里 |
| `embedding_records` | embedding_id → segment_id 的映射（极薄，不存向量值） | embedding_id 关联到上表的记录 |
| `databases` / `tenants` | 多租户隔离层级，单机部署各只有一条默认记录 | 和你无关 |
| `migrations` | 版本升级时的表结构变更记录 | 和你无关 |

关键认知：向量值不在任何 SQLite 表里，在旁边的 HNSW 二进制文件中。
  
索引更新路径：文档修改时，先 `collection.delete(ids=[...])` 删旧 chunk，再 `collection.add(...)` 插新 chunk。delete 同时从 SQLite 删记录 + 从 HNSW 图移除节点；add 先调 embedding function 生成向量，再同时写入 SQLite + 插入 HNSW 图。全程同步执行，调用返回时数据已在磁盘上。

**BM25 关键词检索 —— rank_bm25 纯内存方案**

BM25 关键词检索不走 ChromaDB。我们用的是 rank_bm25 库，在 Python 内存里构建索引。ChromaDB 只存密集向量，不存稀疏向量。BM25 索引的数据源是 ChromaDB——启动时从 ChromaDB 读出所有 chunk 原文来做分词和建索引。

这里先纠正一个容易搞混的概念。rank_bm25 既不是纯倒排索引，也不是纯正向索引——它在两个方向上各做了一半。

一个完整的**倒排索引**（inverted index）由两部分组成：词典（term → IDF/DF）+ posting list（term → 包含该 term 的 chunk 列表及 tf）。检索时，拿到 query term 直接查 posting list，只遍历命中 chunk，跳过无关 chunk——这是倒排索引的核心优势。

rank_bm25 做了词典那半（`idf` dict：term → IDF 值），但**没有构建 posting list**。那检索时怎么知道每个 term 在哪些 chunk 里？靠的是 `doc_freqs`——一个按 chunk 方向组织的数据结构：每个 chunk 存一个 Counter，记录"我这个 chunk 里有哪些 term 及各出现几次"。这就是正向索引的方向（chunk → term）。检索时遍历全部 2000 个 chunk，对每个 chunk 用 Counter.get(query_term) 查有没有命中。

所以准确说：**词典是倒排的（term → IDF），检索是靠正向扫描的（遍历 doc_freqs）。** 这样设计在小规模（2000 chunk）下完全合理——少了 posting list 的构建和维护成本，查询性能也完全够用（1 万次 dict 查找 ≈ 1ms）。下面说清楚 rank_bm25 内存里到底长了 4 个什么样的数据结构。

**启动时构建**

BM25 索引不在离线阶段预构建，而是在服务启动时从 ChromaDB 读出全量 chunk 原文后实时构建。流程：从 ChromaDB 读出全量 chunk 原文 → jieba 逐条分词（走自定义词库）→ 构建词典和 doc_freqs 数据结构 → 返回 BM25Okapi 对象。

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 等待 embedding 模型服务就绪 | 几十秒 | 独立服务，启动最慢 |
| ChromaDB 加载向量索引进内存 | ~2s | hnswlib 加载 HNSW 图结构 |
| jieba 分词（~50 万字符，2000 chunk） | 3~8s | 标准 jieba 精确模式，单 batch 瓶颈 |
| 词典 + doc_freqs 构建（~4000 term） | 100~200ms | CPython dict 插入 + Counter 创建 |
| BM25Okapi 实例化 | ~100ms | 纯 Python 循环计算 IDF |
| **总计启动耗时** | **~3~9s** | 非启动路径瓶颈 |

**数据结构 —— 4 个 Python 对象，全部在内存中**

假设 3 个 chunk 的小例子来展示真实的内存形态：

```python
# 原始语料（jieba 分词后）
corpus = [
    ["OA", "监控", "告警", "的", "配置", "方法"],           # chunk_0，6个token
    ["告警", "阈值", "的", "设置", "与", "调整"],           # chunk_1，6个token
    ["MySQL", "数据库", "备份", "与", "恢复"],              # chunk_2，5个token
]

# ① bm25.idf: dict[str, float]  —— 每个term的稀有度
#     约4000个key，key是中文词，value是float
#     查 "OA" 得 0.85，查 "告警" 得 0.47（"告警"出现在2个chunk，不如"OA"稀有）
idf = {"OA": 0.85, "监控": 0.85, "告警": 0.47, "的": 0.47,
       "配置": 0.85, "方法": 0.85, "阈值": 0.85, "设置": 0.85,
       "与": 0.47, "调整": 0.85, "MySQL": 0.85, "数据库": 0.85,
       "备份": 0.85, "恢复": 0.85}

# ② bm25.doc_len: list[int]  —— 每个chunk分词后的token数，2000个int
doc_len = [6, 6, 5]

# ③ bm25.avgdl: float  —— 平均长度，一个数
avgdl = 5.67

# ④ bm25.doc_freqs: list[Counter]  —— 这是关键！正向索引
#     2000个Counter，每个Counter记录"我这个chunk里各词出现了几次"
#     查询时遍历这2000个Counter，对每个Counter做 .get(query_term)
doc_freqs = [
    Counter({"OA": 1, "监控": 1, "告警": 1, "的": 1, "配置": 1, "方法": 1}),  # chunk_0
    Counter({"告警": 1, "阈值": 1, "的": 1, "设置": 1, "与": 1, "调整": 1}),    # chunk_1
    Counter({"MySQL": 1, "数据库": 1, "备份": 1, "与": 1, "恢复": 1}),          # chunk_2
]
```

**在线检索 —— 确实遍历全部 2000 个 chunk**

这是 rank_bm25 的 `get_scores()` 核心逻辑（简化版）：

```python
def get_scores(self, query_tokens):
    score = np.zeros(2000)                    # 2000个0，每个chunk一个槽位
    for token in query_tokens:                # 遍历query的每个词，比如5个词
        # ↓↓↓ 这一行遍历全部2000个chunk ↓↓↓
        q_freq = np.array([doc.get(token, 0) for doc in self.doc_freqs])
        #  ↑ 2000次Counter.get()，token不存在则返回0
        score += self.idf[token] * tf_part(q_freq, ...)  # numpy向量化浮点运算
    return score                               # 返回2000个分数
```

**拿上面 3 个 chunk 跑一遍真实查询，看清每一步：**

用户输入 `"告警 阈值"`，jieba 分词 → `["告警", "阈值"]`。现在要算这 3 个 chunk 各自的 BM25 分数。

```
═══════════════════════════════════════════════════════════
Step 1: 处理 query term "告警"
═══════════════════════════════════════════════════════════

先查词典：idf["告警"] = 0.47（"告警"出现在 2 个 chunk 里，不算稀有，IDF 偏低）

然后扫描 doc_freqs，看 3 个 chunk 各自有没有"告警"：

  chunk_0: Counter{"OA":1, "监控":1, "告警":1, "的":1, "配置":1, "方法":1}
            doc.get("告警") → 1  ← 命中！tf=1

  chunk_1: Counter{"告警":1, "阈值":1, "的":1, "设置":1, "与":1, "调整":1}
            doc.get("告警") → 1  ← 命中！tf=1

  chunk_2: Counter{"MySQL":1, "数据库":1, "备份":1, "与":1, "恢复":1}
            doc.get("告警") → 0  ← 没命中，这个词不在这个chunk里

"告警"对 3 个 chunk 的 tf 贡献：[1, 1, 0]
× IDF(0.47) → 临时分 = [0.47, 0.47, 0]

═══════════════════════════════════════════════════════════
Step 2: 处理 query term "阈值"
═══════════════════════════════════════════════════════════

查词典：idf["阈值"] = 0.85（"阈值"只出现在 1 个 chunk，稀有词，IDF 高）

扫描 doc_freqs：

  chunk_0: doc.get("阈值") → 0  ← 没命中
  chunk_1: doc.get("阈值") → 1  ← 命中！tf=1
  chunk_2: doc.get("阈值") → 0  ← 没命中

"阈值"对 3 个 chunk 的 tf 贡献：[0, 1, 0]
× IDF(0.85) → 临时分 = [0, 0.85, 0]

═══════════════════════════════════════════════════════════
Step 3: 累加总分
═══════════════════════════════════════════════════════════

           "告警"    "阈值"    总分
chunk_0:   0.47  +   0     = 0.47
chunk_1:   0.47  +   0.85  = 1.32  ← 最高！
chunk_2:   0     +   0     = 0     ← 完全不相关

排序取 top-2 → [chunk_1 (1.32), chunk_0 (0.47)]
```

关键观察：
- chunk_1 两个词都命中，且命中了稀有的"阈值"（IDF 高），得分远超 chunk_0
- chunk_2 两个词都不沾边，直接 0 分
- "告警"虽然也命中了 chunk_0，但 IDF 低（常见词），贡献有限——光靠常见词撑不起分数

**这就是正向扫描**：没有 posting list 告诉你"阈值在 chunk_1"，你得把 3 个 chunk 都问一遍才知道。3 个 chunk 当然无所谓，2000 个也是同样的逻辑——只是循环 2000 次。

是的——query 有 5 个词，就执行 5 × 2000 = **1 万次 `Counter.get()`**。没有跳表、没有剪枝、没有跳过不相关 chunk。那为什么耗时只有 2ms？

拆开看 2ms 是怎么来的：

| 操作 | 次数 | 每次耗时 | 小计 |
|------|------|---------|------|
| `Counter.get(token, 0)` | 10000 次 | ~100ns（C 层哈希查找） | ~1ms |
| numpy 向量化 `tf_part()` | 5 次 | ~100μs（C 层 SIMD） | ~0.5ms |
| `np.argsort()` 取 top-5 | 1 次 | ~200μs | ~0.2ms |
| jieba 分词 + 其他开销 | — | — | ~0.3ms |
| **总计** | | | **~2ms** |

关键在第一步：`Counter.get()` 是 CPython C 层的哈希表查找，一次约 50~150ns。1 万次加起来也就 1ms 左右。而"2000 个 chunk"对 CPU 来说太小了——现代 CPU 的 L3 缓存有 8~32MB，2000 个 Counter 对象加起来才几百 KB，全部在缓存里，没有内存延迟。

**为什么不用真正的倒排索引？**

倒排索引的查询逻辑是：只遍历 posting list 里的 chunk。如果 query 中 5 个 term 的 posting list 加起来只有 50 条，那就只算 50 次——理论上比 1 万次快 200 倍。

但实际上，在当前 2000 chunk 的规模下，引入倒排索引并不会更快。原因：
- 1 万次 dict.get() 只要 1ms，优化空间已到纳秒级
- 倒排索引需要额外维护 posting list 数据结构（term → [(chunk_id, tf), ...]），内存和构建时间翻倍
- jieba 分词已经占了 2ms 的大头（0.3ms），再优化 dict 查找没有意义

rank_bm25 选择正向索引是合理的工程决策——在小规模下，正向索引的代码简单、构建快、内存小，查询性能完全够用。如果未来文档量从 500 涨到 5 万、chunk 从 2000 涨到 20 万，那时正向索引的 O(N) 遍历才会成为瓶颈，需要切换成倒排索引。但那时整个架构都需要升级，BM25 只是其中一环。


**为什么必须全量重建**：BM25 的 IDF 是全局统计量——IDF(t) = log((N-df+0.5)/(df+0.5))。你改了一个文档，N（文档总数）变了，某些 term 的 df（文档频率）也变了，所有 term 的 IDF 都要重新算，avgdl 也要重新算。这不像是向量索引——新向量插入 HNSW 图只影响局部连接，不改变已有向量。所以 BM25 在数据变更后全量重建不是偷懒，是算法天然要求。2000 chunk 规模下全量重建只要 50-100ms，完全可接受。

**为什么 BM25 不自己持久化**：数据源（ChromaDB）本身已经持久化了原文，全量重建又快。如果 BM25 也把倒排索引持久化到磁盘，就多了一个需要和 ChromaDB 保持一致的副本。设计原则是 ChromaDB 是唯一持久化层，BM25 是无状态计算层，随时可销毁重建。

**为什么选 rank_bm25 内存方案而不是 ChromaDB sparse index**

这里需要解释一个我曾认真考虑过但放弃了的方案对比。ChromaDB 从 0.5.x 版本开始支持 sparse vector（稀疏向量），可以把 `{term_id: weight}` 格式的稀疏向量存入 ChromaDB，在 ChromaDB 内部做稀疏向量点积检索。表面上看，两路索引统一在 ChromaDB 里管理，架构更整洁。但经过分析后我选择了 rank_bm25 纯内存方案，理由如下：

1. **term→id 映射是额外负担**。ChromaDB sparse 方案要求把 jieba 分出的词转成整数 ID。为什么？因为 ChromaDB 的稀疏向量接口不认识中文，只接受 `{15: 2.34, 382: 1.87}` 这种格式——key 必须是整数（term_id），value 是对应的权重。你需要自己维护一个 `{词 → 编号}` 的全局映射表。这个映射表需要持久化（ChromaDB 不会帮你存），每次文档更新引入新词时要同步更新，查询时要和写入时用的是同一份映射。

    具体举例说明这个映射链路有多脆弱。假设你用 ChromaDB sparse 方案，离线阶段要做的事：

    ```
    第1步：对500篇文档分词，收集所有出现过的词 → 词典里有约4000个词
    第2步：给每个词编一个固定ID → {"OA": 15, "监控告警": 382, "阈值": 1203, "配置": 42, ...}
    第3步：对每个 chunk，把它的词转成 {term_id: bm25_weight} 格式
           chunk "OA 监控告警阈值配置" 分词后是 ["OA","监控告警","阈值","配置"]
           查映射表 → term_id: [15, 382, 1203, 42]
           计算 BM25 文档侧权重（TF分量） → {15: 2.34, 382: 1.87, 1203: 1.52, 42: 0.98}
           把这个 {15: 2.34, 382: 1.87, ...} 写入 ChromaDB sparse collection
    第4步：把这个 {"OA": 15, "监控告警": 382, ...} 的映射表持久化到磁盘（json/db）
    ```

    在线查询阶段：

    ```
    用户问"OA告警" → jieba分词 → ["OA", "告警"] → 查映射表 → [15, 687]
    → 计算query侧BM25权重（IDF分量）→ {15: 3.2, 687: 2.8}
    → 把 {15: 3.2, 687: 2.8} 发给 ChromaDB sparse collection.query()
    → ChromaDB 内部做稀疏向量点积：{15: 3.2, 687: 2.8} · chunk_sparse_vector
       （ChromaDB 内部遍历倒排，找出包含 term 15 或 687 的 chunk，分别算点积）
    → 返回排序结果
    ```

    这个链路的问题在哪里？第一，词表会变化。你新增一篇文档，里面出现了新词"多AZ"——之前词典里没有这个词。你必须给"多AZ"分配一个新 ID（比如 52431），然后更新映射表、持久化映射表、对所有包含"多AZ"的 chunk 重新生成稀疏向量。如果映射表的版本没同步好——比如查询时用的是旧映射表，把"多AZ"映射成了 52000（一个被占用的旧 ID），检索结果就会错位。

    第二，你完全失去了中间环节的可控性。ChromaDB 内部做稀疏向量点积检索的时候，你只能拿到最终排序结果。哪个 chunk 被哪个 term 命中、点积的计算过程对不对、新词有没有被正确编入映射——这些全都看不到。

    对比 rank_bm25：没有映射表、没有编号转换、没有写入/查询两侧的版本同步问题。jieba 切出来 "OA" 就是字符串 "OA"，`bm25.idf["OA"]` 直接能查到 IDF。新词出现后 `jieba.lcut("多AZ")` → `["多AZ"]`，BM25Okapi 自动把它加入词典，不需要你维护任何映射。代码量少一个数量级，出错环节少一个数量级。

2. **可观测性**。rank_bm25 所有中间数据都在 Python 内存里，出问题时可以逐层排查：`jieba.lcut(text)` 看分词对不对 → `bm25.idf["OA"]` 看某个词的 IDF 是否合理 → `bm25.get_scores(tokens)` 看每个 chunk 得了多少分。ChromaDB sparse 方案下，你把向量丢给 ChromaDB 后只能拿到排序结果，中间过程（怎么做的点积、命中了哪些文档、每个文档的权重是多少）全不可见。

3. **数学正确性**。rank_bm25 内部就是标准 BM25 公式（TF 饱和 + IDF 加权 + 长度归一化），学术界验证了二十多年。ChromaDB sparse 方案需要你自己把 BM25 公式拆成文档侧（存 TF 分量）和查询侧（乘 IDF），公式拆分如果不对就会引入偏差。rank_bm25 不需要你做这个拆分。

4. **实现复杂度**。rank_bm25 方案：`pip install rank_bm25`，10 行代码构建索引，5 行代码检索。ChromaDB sparse 方案：需要维护 term→id 映射表的持久化和同步、处理新词扩展时的映射一致性、正确拆分 BM25 公式、处理 avgdl 变化时的全量重算。代码量从 15 行变成 100+ 行，且引入了多个容易出错的环节。

5. **规模足够小，全量重建无感**。ChromaDB sparse 方案的最大优势是增量更新（只更新变化的 chunk，不重建全量索引）和持久化免重建。但 2000 chunk 的规模下，rank_bm25 全量重建只要 50-100ms——persistent 的优势体现不出来。反而是为了拿到增量更新而引入的额外复杂度（term→id 映射管理、公式拆分）是实打实的。如果 chunk 到了 5 万、10 万级别，全量重建会变成秒级，那时 ChromaDB sparse 的增量更新优势才会超过它的成本。

**启动时的自动恢复**

节点重启后的完整流程：FastAPI 进程启动 → ChromaDB PersistentClient 初始化，从本地磁盘加载向量索引和元数据进内存（~2s）→ BM25 索引在启动钩子中自动重建：从 ChromaDB 读出全量 chunk 原文 → jieba 分词 → 构建 BM25Okapi 对象（50-100ms）→ 健康检查通过 → 恢复服务。整个过程约 3 秒。如果磁盘损坏数据文件不可读，从零重建——重新切分 500 文档 → embedding → 写入 ChromaDB → BM25 重建，约 2 分钟。

  **chunk 引用关系**：当前没有做显式的父子或相邻 chunk 引用追踪。先厘清引用关系和 overlap 是两回事——overlap 解决的是同一个语义单元被切分边界拦腰截断的问题，引用关系解决的是不同 chunk 之间语义相关、互为补充的问题（比如连续三个段落讲同一个配置的不同方面，命中一个后需要把相邻的也带出来）。

不做显式引用追踪，依赖的是三个机制叠加：第一，相邻 chunk 共享标题路径，content 里打了相同的 header，向量 embedding 天然接近；第二，相邻 chunk 共享关键词，BM25 路两边都有分词命中；第三，RRF 融合时如果同一个 chunk 在两路都有排名，融合分叠加，更容易排到前面。这三个机制保证了同主题的相邻 chunk 被一起召回的概率。

更重要的是有数据支撑：综合推理型问题（需要多个 chunk 共同支撑答案）的 Recall@5 达到 0.914，说明 91% 的情况下所有需要的 chunk 都在 top-5 里。同时我们 Rerank 前有 8 个候选，Rerank 后取 5 个给 LLM，而实际答案平均依赖 3-4 个 chunk——top-5 留了余量，覆盖了大多数多 chunk 场景。所以当前不做显式引用追踪，不是偷懒，而是在现有评测数据下，相邻 chunk 的自然召回能力已经够用。如果未来文档复杂度上升导致 Recall@5 明显下降，在 metadata 里加 parent_chunk_id 字段，检索时命中子 chunk 一并带出父 chunk 即可。

  **file_name 做主键的局限**：文件名被改后，旧 file_name 的 chunk 变成孤岛残留，新 file_name 走新增分支可能引入重复。当前通过上传规范约束文件名唯一不可改 + 上传时二次确认兜底。更严谨的做法是用 Wiki 页面路径或平台稳定 ID 做主键。

### 1.2 Embedding & 向量化

**Q6.** Embedding 模型选的是什么？为什么选这个？你对比过哪些模型？在你们自己的数据集上做评测了吗？评测指标是什么？

 我们用的是阿里 text-embedding-v3@768，内部私有化部署，不走公网 API。选择背景是信息安全合规要求——所有模型必须部署在内网，网络完全隔离，不能用外部 API。候选池天然受限，只能在内部已部署的模型里选，当时可用的只有阿里 V2 和 V3。

 V2 固定 1024 维。V3 支持 512、768、1024 三档。所以候选配置一共四组：V2@1024、V3@512、V3@768、V3@1024。四组全部在 100 条 QA pairs 上跑检索，直接看结果，不需要分阶段。

 评测指标按问题类型拆两组：单答案型（FAQ、配置查询，只有一个正确 chunk）用 MRR；综合推理型（故障排查、跨文档分析，需要多个 chunk 共同支撑）用 Recall@5。

 四组结果：

 | 配置 | MRR | Recall@5 |
 |------|------|----------|
 | V2@1024 | 0.737 | 0.819 |
 | V3@512  | 0.780 | 0.853 |
 | V3@768  | 0.831 | 0.892 |
 | V3@1024 | 0.833 | 0.893 |

 两个结论很直接。第一，V3 全线优于 V2——即使 V3 最低配的 512 维也超过 V2 的 1024 维（MRR 0.780 vs 0.737），模型代际差距明显。第二，V3 内部 768 和 1024 两项指标几乎持平（MRR 差 0.002、Recall@5 差 0.001），但 1024 维存储多 33%、HNSW 检索延迟也相应增加。所以选 V3@768——效果到顶了，成本更低。

 候选池局限于阿里两个模型，我清楚。BGE 的中文模型和 Jina 的多语言模型在公开评测上对中文支持也很好，但受合规约束目前没有实测——这是环境限制，不是技术决策。

 关于模型升级：MRR/Recall@5 只是第一轮快速筛选。完整的升级流程分五步：第一步，全量 100 条 QA pairs 跑 MRR/Recall@5 快速筛选，有回归 case 直接打回；第二步，全量跑 RAGAS Faithfulness 相对比较，检查忠实度是否退化；第三步，前两步通过后，30 条分层抽样做人工端到端验证，直接看答案质量；第四步，影子部署——新旧两路并行跑线上真实 query，新路只记录不返回，对比答案不一致率，不一致率飙高（> 20%）则排查；第五步，切流量，观察一周线上指标。


**Q7.** 你用的是什么向量数据库？Milvus、Pinecone、Weaviate、Qdrant 还是自研？为什么选它？跟你们现有基础设施怎么配合的？

  我们用的是 ChromaDB（/ˈkroʊmə/，嵌入式向量数据库）。选型逻辑不是因为它"刚好有"，而是筛完候选后，它在我们的场景下综合代价最低。

  **先排除三个生产级系统——对我们太重了。**

  **Milvus**（/ˈmɪlvəs/ 米尔沃斯）——十亿级向量标杆，但完整部署依赖 etcd+MinIO+Pulsar 四个组件，2000 chunk 杀鸡用牛刀。

  **Elasticsearch**（/iːˈlæstɪk/ 伊拉斯提克）——全文检索出身，后加向量能力。如果有现成 ES 集群最省事，但我们没有，引入要搭 JVM 运维，团队主栈 Python 排查成本高。

  **Qdrant**（/ˈkjuːdrənt/ 库德兰特）——Rust 实现性能强，但独立二进制进程，出 bug 翻 Rust 源码门槛够不着。

  **ChromaDB 刚好匹配我们的量级。**

  pip install 完事，嵌入在 Python 进程内运行，数据存本地文件（SQLite + HNSW），不需要单独部署 server、不需要配端口。三个 API 覆盖全部操作，2000 个 768 维向量检索一次约 3ms。从扩展性看：ChromaDB 单机可支撑约百万级向量（768 维下约 3GB 内存），对于我们 2000 chunk 的当前规模和可预见的增长都绰绰有余。如果未来文档量涨到十万级，ChromaDB 的内存和性能仍可承受；如果到百万级以上再考虑迁移到 Milvus 或 ES，架构上只需改 VectorStore 一个适配层。

  **嵌入式 vs 集中式：选嵌入式**

  ChromaDB 支持嵌入式和独立 server 两种模式。我们选了嵌入式——4 个 FastAPI 节点各嵌一个实例，不单独跑 server。原因是：我们日均 100 次查询、文档更新几天一次，读远多于写。嵌入式没有网络开销、不引入单点故障、零额外运维。写一致性的代价是文档更新后 4 个节点各自跑一遍 embedding，每次多花 8000 次 API 调用，但在内部 API 成本下忽略不计。核心逻辑：**读写差距极大的场景下，把复杂度放在写路径上，换读路径的更低延迟和更高可用性**。


**Q8.** 向量检索走的是哪个相似度度量？cosine、dot product 还是 Euclidean？为什么？你做 A/B 测试验证了吗？

  先理清这三个度量之间的关系。

  点积（dot product）是对应维度相乘再求和，结果受方向和向量长度共同影响——一个很长的向量方向不太对，点积也可能大于方向精准但很短的向量。cosine 是点积除以两个向量模长的乘积，它剥离了长度，只看方向。L2 距离算的是空间中的直线距离，同样受长度影响。所以**没归一化时，这三个东西各算各的，不等价**——方向相同但长度不同的两个向量，cosine 给 1，L2 距离不为 0，点积也不是 1。

  但它们在一个前提下等价——向量经过 L2 归一化之后。L2 归一化就是把每个向量的模长拉到 1，所有向量落在单位球面上。此时 |A| = |B| = 1，点积 = cosine（分母为 1），L2 距离也退化为只和点积单调负相关（L2 越小即 cosine 越大）——因为长度信息被归一化去掉了，三者排序完全一致。所以归一化后你用 L2、cosine 还是点积检索，结果顺序一模一样。ChromaDB 默认走 L2，我们的 text-embedding-v3 输出向量模长就是 1，所以实际跑的是和 cosine 等价的排序，不存在兼容问题。

  那真正需要注意的是什么？不是度量选哪个，而是 embedding 模型的训练目标和检索度量是否在同一个坐标系里说话。

  模型吐出向量的时候，向量的"含义"是由训练方式决定的。text-embedding-v3 在对比学习框架下训，目标是让语义相似的 query 和 chunk 方向靠近、不相似的远离——所以它学的是方向，长度没意义，天然适合 cosine 坐标系。但如果换一个模型，它的训练目标可能不是纯方向导向的，比如某些模型在训的时候没做 L2 归一化约束，输出向量的长度本身也承载了语义信息（比如"置信度"或"相关性强度"）。这时候你把它的向量塞进 L2 度量里检索，就会出现错位——模型觉得 A 和 B 语义相近（因为方向对），但 L2 因为长度差异把它们判远了。这不是度量不兼容，是模型的语义空间和检索度量不在同一套坐标系下。

  所以问题的本质是：**模型训练时在什么坐标系里定义语义，检索时就在什么坐标系里比较**。归一化之后 L2/cosine/点积等价，这是数学事实，不需要 A/B 测试验证。需要审慎的是换模型的时候——如果新模型的输出空间和当前度量不匹配，要在创建 collection 时显式指定对应的度量，或者在模型输出后做归一化拉回同一坐标系。


### 1.3 索引 & 检索策略

**Q9.** 你是不是只做了向量检索？有没有做混合检索（hybrid search）？比如 BM25 + 向量？如果有，怎么融合两个通路的分数的？用的是 RRF（Reciprocal Rank Fusion）还是线性加权？融合参数怎么调的？

我们没有只做向量检索，做的是向量加 BM25 双路混合检索。整个检索链路的入口是先做 query 改写，再走双路检索，最后 RRF 融合。

整个流程是：用户问题进来后，先经过 query 改写步骤。改写器做两件事：一是用 LLM 将用户的口语化表述改写为文档风格的专业表述，比如把"手机收不到短信"改写为"SMS通知渠道未收到告警"；二是通过一个动态映射表，将用户常用的非专业词汇替换为系统内的专业术语，比如"OA"映射为"优化顾问"、"那个监控"映射为"OA监控告警"。映射表存储在动态配置中，可以在运行时直接修改，不需要重启服务或重新部署。映射表的维护来源是线上 bad case 复盘——用户点击"没用"的反馈会被记录下来，包括原始 query、改写后的 query、以及最终检索结果。在项目上线后的前一个月，我们每天都会看这些 bad case 日志，分析是改写步骤出了问题还是检索步骤出了问题。如果改写出了问题，就更新映射表；如果是检索出了问题，就排查是 jieba 分词错误还是 embedding 召回失败。

改写之后，query 并行进入两条检索通路。

向量路：用阿里 text-embedding-v3 对改写后的 query 做 embedding，进 ChromaDB 的 HNSW 索引做余弦相似度检索，返回 top-k 个候选。向量检索擅长语义相似和同义改写，但对精确关键词、专有名词、缩略语的匹配能力弱。

BM25 路：用 jieba 分词 + rank_bm25 库在 Python 内存中构建倒排索引做关键词检索，返回 top-5 个候选。BM25 的评分计算（TF 饱和 + IDF 加权 + 长度归一化）全部在 rank_bm25 内存中完成，不经过 ChromaDB——ChromaDB 不存储稀疏向量、不参与 BM25 检索、也不负责 RRF 融合（融合在 Python 层自己做）。这样分词和检索逻辑完全在自己控制下，自定义词库的热加载不受任何外部组件影响（原理详见 Q17-附）。BM25 擅长精确关键词匹配，正好弥补向量路在专有名词和缩写上的盲区。分词器用的是 jieba，因为我们的文档是中文技术文档，有大量内部术语，默认词库切不准。我们维护了一套自定义词库，包含业务专有名词和缩写，比如"优化顾问"、"region白名单"、"多AZ"、"SMS通知"等。词库同样支持运行时热加载，发现新术语后添加到词库文件，调 reload 接口即刻生效。词库的维护来源和映射表一样，来自线上 bad case 复盘——如果发现是因为分词错误导致 BM25 路失效，就加词库。

  **为什么两路各取 top-5**

  从数据出发。评测集里的综合推理型问题，生成答案平均依赖 2 个多 chunk，需求最多的 case 依赖 4 个 chunk。所以最终给 LLM 至少 4 个，留 1 个余量，取 5。

  从检索流程看，Rerank（cross-encoder 精排）之前候选池必须大于最终输出数——否则 Rerank 退化为直通。两路各取 5、RRF 融合去重后约 8 个候选，压缩比 1.6:1，Rerank 有筛选空间。候选池再小（各取 3）则 Rerank 无筛选空间；再大（各取 10）则 Rerank 耗时翻倍但 Recall@5 已在 0.914，边际收益极低。5 落在两个约束的交点上。

  当前 Recall@5=0.914，加上平均 2 个多 chunk 的需求数据，验证了 5 在现有条件下是够用的。没有跑过 K=3/5/7/10 的严格消融实验——当前配置已有足够的数据支撑，后续文档复杂度上升时可跑一轮 K 值消融找到新的拐点，改参数重跑 100 条评测即可。

  **两路融合**

  两路结果通过 RRF（Reciprocal Rank Fusion）融合成最终候选列表。RRF 只关心每个候选在各自通路中的排序位置，不关心原始分数值——向量路的余弦相似度（0~1）和 BM25 分（0~几十）量纲不同，直接加权会有一路被另一路淹没，RRF 天然规避了这个问题。公式 score = α/(k+rank_vec) + β/(k+rank_bm25)，k=60 是论文经典取值，α=β=0.5 经网格搜索验证——在 100 条 QA pairs 上 α 以 0.1 步长遍历，最优值在 0.5 附近，且偏离时指标变化平缓，两路贡献均衡。
  RRF 之外还有几种融合方法，在当前场景下不适用：

  **分数归一化 + 加权求和**：把两路分数归一化到同一量纲后加权相加。归一化参数（min/max 或 mean/std）从当前候选集实时估算——不同 query 候选集不同、参数不同，排序行为不可控。RRF 不估任何参数，规避了这个不稳定性。

  **Learning to Rank（LTR）**：训练排序模型替代手写规则。需要分级标注（"chunk A 比 B 更相关"而非简单的相关/不相关），当前只有二元标签。且 2000 chunk 规模下 RRF 已够用，训练模型的工程成本远超收益。

  RRF 在当前 5+5 规模下，其排序结果和直接去重后给 reranker 没有可测量的效果差异（同一批 100 条 QA 对比，recall@5 差异 < 1%）。原因在于去重后约 8 个候选，reranker 全算一遍只要 100ms，cross-encoder 的判别力远强于 RRF 的 rank-based 加权——RRF 的预排序被 reranker 覆盖掉了。保留 RRF 的理由不在效果而在于工程规范：成本为零（纯 Python < 1ms）、规避量纲问题是异构检索源融合的标准做法、且候选池未来膨胀时 RRF 的预排序能为 reranker 截断提供基础。

关于要不要加第三路，我评估过 HyDE 和 Small-to-Big。HyDE 的核心思想是用 LLM 生成假设答案，把"问题 vs 答案"的匹配变成"答案 vs 答案"的匹配。经典 HyDE 不适合私有知识场景，因为 LLM 不了解内部文档，凭空生成的假设答案用词对不上。但有一个变体可行：先跑一轮快速向量检索取 top-3，把真实 chunk 给 LLM 让它基于真实内容生成假设答案，再做第二轮检索——这样风格和术语都来自真实文档。我没有实施，因为当前双路效果已满足指标，且我们的改写器已经在做风格对齐的工作。Small-to-Big 是返回时把命中小 chunk 所属的父文档一并返回，不改检索逻辑所以不提升 MRR，但提升答案完整度。没有实施是因为当前未发现因上下文不足导致的生成 bad case。两路到三路有边际收益，但三路以上收益递减明显，双路是当前业务的最优平衡。

评测指标方面，我们的 100 条 QA pairs 评测集按问题类型拆成两组：单答案型（只有一个正确 chunk）用 MRR，综合推理型（需多个 chunk 共同支撑）用 Recall@5。为什么多 chunk 场景不用 NDCG？NDCG 的设计依赖分级相关性——需要标注"这个 chunk 比那个更相关"才能发挥位置加权的作用。我们的标注是二元的（相关/不相关），所有正确答案 chunk 之间没有优先级之分——只要都在 top-5 里就够了，它们之间的相对顺序没有业务意义。Recall@5 直接回答"用户看到了多少相关知识"，简洁、可解释。

**Q10.** 有没有做 query 改写（query rewriting）？有没有做 HyDE（假设文档嵌入）？有没有做 multi-query / query decomposition？如果都没做，复杂问题怎么处理？

Query 改写做了。这个模块同样不是前期设计阶段就规划好的——开发阶段自测时发现，用户常用的口语化表述和文档的正式术语之间存在严重的词汇鸿沟。比如"OA"就是"优化顾问"，"那个监控"就是"OA监控告警"，用户用自己的话搜，检索结果根本对不上文档里的正式术语，系统基础可用性都成问题。这个问题和 header 拼接一样，是在开发自测阶段暴露的，还没走到 QA 评测那一步就必须解决。

我们的方案分两层：第一层是动态映射表，维护了专有名词到标准术语的映射关系，放在配置中心，运行时热加载，用户输入先过一遍映射表做术语替换；第二层是 LLM，对替换后的 query 做口语化去除，把自然语言风格对齐到文档风格。两层串行，先替换再改写。映射表的词条和 LLM 改写的逻辑都不是一次性设计完的——开发阶段自测过程中反复遇到新的术语不匹配 case，发现一个加一个，是持续打磨出来的。

HyDE 没有做，原因分两层说。经典 HyDE 是让 LLM 凭空生成一个假设答案，再用假设答案去做向量检索。这在我们的场景下有明显问题：我们的文档全是内部专有知识，LLM 不了解这些内容，生成的假设答案在术语上大概率出现幻觉——比如它可能会编一个不存在的配置项名称——然后拿着这个错误的答案去做检索，不仅帮不上忙，反而把检索带偏了。改进版的 HyDE 可以规避这个问题：先 rewrite query，跑一轮快速检索取 top-3 真实 chunk，把真实内容给 LLM 让它基于此生成假设答案，再做第二轮检索。这样术语锚定在真实文档上，不会跑偏。但这个方案的代价是链路变成两轮检索，端到端延迟翻倍。在当前 500 文档、日均 100 问的规模下，我们的双路混合检索效果已经够用，改进版 HyDE 的边际收益不足以覆盖延迟代价。后续我们会根据线上用户反馈数据——被踩的答案、漏到人工群的问题——来评估是否需要引入，优先级当前不高。

Multi-query 是指把同一个问题改写成多个不同表述，多路并行检索后合并结果。Query decomposition 是把一个复杂问题拆成多个独立的子问题，各自检索不同信息源，最后汇总。这两个技术本质上和改进版 HyDE 有相同的 tradeoff：检索轮次增加，链路变长，延迟上升。在当前阶段我们都没有采用。

目前复杂问题的处理不靠拆解或多次检索。我们的混合检索本身对多 chunk 召回能力足够——综合推理型 Recall@5 0.892 说明多相关 chunk 的召回质量在线。生成阶段 LLM 拿到 top-k 个 chunk 后自行综合多段信息推理。后续如果复杂问题的比例上升，或者线上 bad case 分析发现「多信息源漏召回」是主要瓶颈，我们会优先试 query decomposition，因为它解决的是信息覆盖面的问题，比 multi-query 的重表述更有针对性。

  补充一句「多信息源漏召回」是什么意思。有些问题看起来是一个问题，但答案需要拼多个不同知识片段。比如"A 服务的告警配置和 B 服务的通知渠道怎么联动"，正确答案依赖 chunk_A（A 服务的告警配置参数）+ chunk_B（B 服务通知渠道的 API 文档）。检索召回了 chunk_A，但 chunk_B 不在 top-5 里——这就是多信息源漏召回。LLM 拿到 chunk_A 只能回答告警配置那一半，联动部分要么说不知道，要么编造。

  针对这个问题，除了检索侧的 query decomposition 方案，前端也加了兜底提示——在输入框下方有一行说明文字："当前仅支持单个问题检索，复杂问题建议拆分后逐一提问"。这不是一个完美的解决方案，但在复杂问题比例很低的当下，给了用户一个明确的预期：系统不会自动拆解你的问题，你得自己拆。

**Q10-附：多问题拆分 —— subagent 并行检索方案**

  当用户一次提问包含多个独立问题时，embedding 会被多个语义方向拉扯导致漏召回。方案分三步：LLM 判断并拆分子问题——各子问题独立并行跑完整链路（改写/检索/RRF/rerank/生成）——LLM 将所有子答案合并为完整回答。不做全局 rerank，因为 cross-encoder 的输入必须是 chunk 对应的那个问题，不同子问题的 chunk 没有统一 query 可以对标。

**Q11.** 检索结果你做重排序（rerank）了吗？用了什么 rerank 模型？是 cross-encoder 还是 bi-encoder？rerank 的延迟增加了多少？值得吗？消融实验数据有吗？

  做了。Rerank 用的是 Qwen3-rerank，cross-encoder 架构，阿里内部私有化部署。

  Cross-encoder 和 bi-encoder 的区别在于是否做跨输入交互。Bi-encoder（检索阶段用的 text-embedding-v3）把 query 和 chunk 各自独立编码成向量，算余弦相似度排序——速度快（3ms 扫 2000 个 chunk），但 query 和 chunk 互相看不到对方，精度有限。Cross-encoder 把 query 和 chunk 拼成一条输入送进 transformer，每层自注意力都在 query 和 chunk 的 token 之间做交互——能捕捉到否定词、条件关系、同词异义这些 bi-encoder 看不到的信号，精度更高，但每对都要实时推理，不能预计算向量。所以两阶段分工：bi-encoder 快速粗筛出 8 个候选，cross-encoder 对这 8 个精排取 top-5。

  延迟方面，rerank 阶段增加约 100ms。

  没有做消融实验。因为不加 rerank 不行——RRF 融合后约 8 个候选里混杂了语义相近但不相关的 chunk（比如多个文档都提到"告警配置"但讲的是不同产品的告警），如果没有 rerank 去噪，这 8 个直接喂给 LLM，噪声会污染生成质量。Rerank 在这里不是锦上添花，是必要环节。

**Q12.** 500个文档，500 * 平均每个文档多少 chunk？你的索引规模有多大？检索延迟是多少？P99 延迟呢？

  500 个文档切分后共约 2000 个 chunk，平均每个文档 4 个 chunk。

  索引分为四部分。向量裸存储：2000 个 chunk 各对应一个 768 维 float32 向量，总大小 2000 × 768 × 4 bytes ≈ 6MB。HNSW 图结构：每个节点最多连接 16 个邻居，每条边 8 字节，总边数约 32000 条，约 0.25MB。BM25 索引：词典约 4000 个 term，doc_freqs 记录约 18 万条，合计约 2MB。ChromaDB 元数据：包括 file_name、chunk_hash、原文 content 等，约 5MB。合计约 13MB，完全在内存中。

  检索延迟方面，HNSW 向量搜索约 15ms（含 ChromaDB Python 层调用开销），BM25 检索约 8ms（rank_bm25 纯 Python 实现），双路并行取 max 约 15ms。Rerank 阶段 8 候选逐对过 cross-encoder 约 100ms。P99 延迟主要波动来自 rerank 阶段 LLM 调用的排队时间。

**Q13.** 整个 RAG 系统的效果怎么评估的？

  评估分三个阶段：检索评估、生成评估、上线后 bad case 维护。

  ---

  **一、离线评估数据集**

  目前 100 条 QA pairs，来自内部用户群的真实提问，筛选有明确答案、可追溯到具体文档的问题。按文档类型和问题热度做分层抽样，高频约占八成，冷门保留一两成。标注时逐个阅读 query 对应的文档，确认哪个 chunk 能正确回答，记录 chunk ID 作为标准答案。这个数据集是三层评估的共享基础，检索和生成评估跑的是同一批数据。

  ---

  **二、检索评估**

  检索链路跑到 Rerank 输出的 top-5 就停下，不接 LLM 生成，纯测检索质量。指标按问题类型拆成两组。

  **单答案型问题 → MRR**。MRR 衡量正确答案在返回列表中的排名，排第一得 1、排第三得 1/3。这里不用 Recall@1——Recall@1 下正确答案排第 2 和第 50 都是 0，MRR 能区分这两者，评测粒度更细。

  **综合推理型问题 → Recall@5**。衡量所有相关 chunk 有多少进了 top-5。这里不用 NDCG——NDCG 的核心价值在于分级相关性，即需要标注了"chunk A 比 chunk B 更相关"时才有意义。我们的标注是二元的（相关/不相关），正确答案间没有优先级，不引入无业务依据的位置折损。K=5 对应 LLM 实际拿 5 个 chunk 做推理，分数直接反映 LLM 拿到的上下文质量。

  ---

  **三、生成评估**

  **RAGAS Faithfulness 的原理**是把 LLM 答案拆成原子化断言（atomic claims），逐条去检索到的上下文中验证这条断言能否被支持。比如答案说了 5 句话，RAGAS 拆成 5 个 claim，逐个判 Yes（上下文支持）或 No（上下文不支持），Faithfulness = Yes 数 / 总 claim 数。裁判 LLM 和生成 LLM 分离，避免同一模型既当运动员又当裁判——我们生成用 DeepSeek V4 Flash，裁判用内部统一 API 的另一个模型实例。

  **我们的做法不做绝对值拦截。** 原因是 RAGAS 的绝对分数和人工判断存在系统性偏差，具体表现为：裁判 LLM 容易把常识性安全建议（如"建议设复杂密码"）判为不忠实，也会把同一件事的不同表述拆成多个 claim 造成重复惩罚。如果设一个 Faithfulness < 0.7 就拦截的规则，大量正确答案会被误杀。学术论文已验证 RAGAS 的绝对分数和人工判断平均偏差达 73.5%，但相对变化方向是可信的——两次评测用同一个裁判 LLM、同一套 prompt、同一批数据，系统性偏差在做减法时抵消了，RAGAS 捕捉到的相对改进量和人工判断高度一致。

  **所以做法是：每次发版跑两遍 100 条 QA，拿新旧两版的逐条 Faithfulness 分数。不看均值、看逐条差异。** 变化幅度超过 0.2 的 case 标记出来（这批 case 通常不到 10 条），人工逐条确认这个差异是真实改进、真实退化还是裁判噪声。改进 → 通过，退化 → 排查根因，噪声 → 忽略。人不需要看全部 100 条，只看标记出的差异 case。

  **RAGAS 的其他指标没有用。** Answer Relevancy 从答案反推 N 个问题算 embedding 相似度——在 RAG 场景下 LLM 被上下文锚定几乎不会跑题，信号太弱，人工一致率约 80%。Answer Correctness 让裁判 LLM 做 TP/FP/FN 分类算 F1——同样有噪声问题，在专业领域的断言拆分和分类判断不可靠。人的判断是最终标准，人已判的 case 直接用结论，不需要再引入有噪声的自动化环节。

  **生成评估有两条数据线并行，最终汇聚到评测集：** 离线线是每次发版的 RAGAS 比对结果经人工确认后回流；在线线是用户点踩和漏到人工群的问题经人工排查后回流。两条线角色不同——离线线是发版门禁，在线线是事后监控和评测集增长机制。

  ---

  **四、端到端基线建立**

  系统第一次部署时，100 条 QA 全量跑一遍完整链路，人工逐条审查建立三条基线：

  - **检索基线**：每条 query 的 MRR/Recall@5，后续发版对比是否有 case 从对变错
  - **忠实度基线**：每条 query 的 RAGAS Faithfulness 分数，后续发版对比是否有退化
  - **答案质量基线**：人工判断每条答案是否正确、有无幻觉、引用是否准确——最硬的一条，因为人了解内部知识库

  这是一次性投入，约一两个小时。基线解决了一个关键问题：RAGAS 只能告诉你 A 和 B 的相对差异，不能告诉你 A 本身好不好——Faithfulness=0.88 没有绝对意义。但如果你知道基线是 0.88、新版是 0.82，你就知道忠实度在退化。

  ---

  **五、上线后维护**

  **日常发版（L1 + L2）。** L1 检索指标全自动跑 10 分钟。L2 RAGAS 跑完后人工看差异 case（<10 条，几分钟）。通过即上线。**


  **重大变更（额外触发 L3 人工验证）。** 四种场景：chunk 策略变更、prompt 大改、模型换代、大量新增文档。检索指标可能正常但答案质量静默退化——30 条分层抽样，人工按六个维度逐条对比：核心结论正确吗、有事实错误吗、有幻觉吗、遗漏了吗、引用准确吗、措辞有误导性吗。约半小时。

  **线上反馈线。** 用户点踩写入 QueryLog，漏到人工群的问题由人工排查根因后标注 chunk ID，加入评测集。

  **评测集分级控制长期成本。** Active ~200 条（最近 6 个月新增 + 历史上修复过的 case）常规必跑；Stable ~100 条（连续多次发版零回归）重大变更时验证；Archived 定期清理。常规发版不会线性增长。

  ---

  **六、模型升级评估流程**

  替换 embedding 或 rerank 模型不能只看检索指标——新模型把 chunk A 排到第一、chunk B 排到第五，MRR 可能一样但 LLM 拿到的上下文变了，最终答案可能不同。

  **五步流程总览：** Step 1 MRR/Recall@5 筛选 → Step 2 RAGAS Faithfulness 对比 → Step 3 人工端到端验证 → Step 4 影子部署答案 diff（见下方详解） → Step 5 切流量观察一周。

  ---

  **Step 4 详解：影子部署答案 diff**

  前面三步跑的都是离线评测集（100 条固定 QA），但离线集覆盖不了线上真实 query 分布。影子部署解决这个问题——把新版放到真实流量中但不暴露给用户，纯比答案内容。

  **部署方式：请求影子复制。** 在 FastAPI 中间件里，主链路返回旧版答案后，异步（`asyncio.create_task`，不阻塞用户响应）把同一 query 发给新版链路。新版答案只写日志不返给用户。影子请求的所有异常必须吞掉——新版挂了不能影响主链路。影子链路另外接一个 ChromaDB collection（`docs_v2`），新模型的 embedding 写在新 collection 里，新旧索引物理隔离。

  **对比方案：三层过滤。**
  - 第一层 exact match + semantic dedup。一模一样或仅表述不同但意思一致（调用 LLM 判语义等价）→ skip，不进入人工。
  - 第二层 RAGAS Faithfulness 差异对比。新旧逐条跑 Faithfulness，delta > 0.2 的标记出来——这批就是答案事实层面有实质差异的 case。
  - 第三层 pairwise LLM 判优劣。对 Faithfulness delta > 0.2 的 case，让裁判 LLM 判"新版更好、旧版更好、持平"。汇总统计：新版优于旧版的占比和旧版优于新版的占比。

  没通过第二层和第三层的 case 都需要人工逐条审查。

  **跑多久：3-5 个工作日。** 目标是覆盖足够多的线上 query 类型，不是跑够样本量就停。如果 3 天内新版已经在各类型 query 上都有覆盖、且没有 major diff，可以提前结束。

  **决策逻辑。** diff_major（答案核心结论不一致）占比 > 5% → 排查新版问题。新版优于旧版的 case 明显多于旧版优于新版 → 可以全量切。两者相当 → 新版不差但不一定更好，决策看其他因素（延迟、维护成本）。

  **当前项目早期无旧 baseline，Step 1 就够用。后续模型升级时走完整五步。**
## 二、在线阶段（推理链路、性能、稳定性、迭代）

### 2.1 Query 理解 & 路由

**Q17.** 用户问题进来之后，整个请求链路是什么样的？从接收请求到返回答案，每一步做了什么？画一下链路你能说清楚吗？

请求链路共 7 步。下面按顺序逐段说。

**第一步：Query 改写（两层串行）**

这个步骤是开发阶段自测时发现词汇鸿沟问题后加入的，不是前期设计阶段就规划好的（详见 Q10）。第一层是动态映射表：放在配置中心、运行时热加载，维护了内部专有名词 → 标准术语的映射（如"OA" → "优化顾问"、"那个监控" → "OA监控告警"），query 先过一遍做术语替换。第二层是 LLM 改写：对替换后的 query 做口语化去除，把用户闲聊式表达对齐到文档风格。两层串行——先替换、再改写——保证专有名词不被 LLM 误改写。

**第二步：Embedding 推理**

改写后的 query 走内部 HTTP API 调用 text-embedding-v3 模型，生成一个 768 维的归一化向量。这一步 P50 约 30ms，P99 约 60ms，是检索延迟的大头。

**第三步：双路并行检索**

Embedding 出来后分两路并行执行，各取 top-5：

- 向量检索：768 维向量在 ChromaDB 的 HNSW 索引上做近似最近邻搜索。HNSW 是分层图结构，从顶层稀疏图快速定位区域，逐层向下精细搜索。ef_search=100，搜索复杂度 O(log N)。返回 top-5 个最相似的 chunk，每个结果带余弦相似度分数。

- BM25 检索：query 过 jieba 分词（加载了内部专有词典），遍历全部 2000 个 chunk 的 doc_freqs 正向扫描，对每个 chunk 查 Counter 是否包含 query term，命中则累加 BM25 分数（IDF × TF_part），返回 top-5 个关键词最匹配的 chunk。

两路并行，总耗时取较慢的那路——P50 约 5ms，P99 约 15ms。

**第四步：RRF 融合去重**

向量 top-5 和 BM25 top-5 通过 RRF（Reciprocal Rank Fusion，k=60）融合。公式是 score(chunk) = 1/(k+rank_vector) + 1/(k+rank_bm25)，按融合分降序排列。两路重合的 chunk 因在两边都有排名而分数叠加、自然排前。去重后得到约 8 个候选 chunk。

**第五步：Rerank 精排**

8 个候选逐个送入 Qwen3-rerank（cross-encoder 架构），每个候选将 query 和 chunk 拼接后做全注意力推理，输出一个精确的相关性分数。8 个候选按分数降序排列，取 top-5 作为最终喂给 LLM 的上下文。这一步增加约 100ms 延迟。

**第六步：LLM 生成**

Rerank 后的 top-5 chunk 拼入 prompt template，连同 system prompt 和原始 query 一起发给 DeepSeek V4 Flash 做生成。Prompt 中每个 chunk 附带来源标注（file_name + 标题路径），方便 LLM 在回答中引用。生成阶段是整个链路延迟最大的部分，取决于输出 token 数。

**第七步：写 QueryLog**

/ask 的每次请求写一条日志到 SQLite（data/queries.db）。日志写入失败不抛异常、只记 warning——不能因为日志挂了影响主链路。设计原则：**不只看"对不对"，还要能定位"哪里不对"**。字段分四组：

**请求标识**
- `request_id`：UUID，链路唯一标识。前端埋点、后端日志、人工群反馈都带这个 ID，用户说"上次那个答案错了"时一秒定位到那条记录
- `user_id`：登录态用户标识（企业内网统一认证），和聊天工具账号一致。人工群反馈回溯时，拿着用户 ID 查 QueryLog 能看到他之前问过的所有问题

**入参和改写**
- `original_question`：用户原始 query
- `rewritten_question`：改写后的 query（LLM 改写 + 映射表替换）。对比这两个字段能发现改写是否合理——如果改写把"OA告警"改成了"告警"，但本该保留"OA"，那就是映射表需要修复

**各步骤延迟（ms，逐阶段记录，定位瓶颈的关键）**
- `embedding_ms`：HTTP 调用 embedding 模型的耗时。如果这个值飙升，说明 embedding 服务在过载
- `vector_search_ms`：ChromaDB HNSW 检索耗时。正常 ~3ms，如果突然>50ms，HNSW 索引可能需要重建
- `bm25_search_ms`：内存 BM25 正向扫描耗时。正常 ~2ms，主要受总 chunk 数影响
- `rerank_ms`：8 个 candidate 逐个过 cross-encoder 的耗时。正常 ~100ms，如果候选数增加或 rerank 服务本身变慢会升高
- `llm_first_token_ms`：LLM TTFT（time to first token）。反映 LLM 服务的排队压力和 prompt 长度。如果这个值大但不是 LLM 本身的问题，那可能是 prompt 里 chunk 太多导致输入过长
- `llm_total_ms`：LLM 完整生成耗时。TTFT + 生成耗时。和输出 token 数直接相关
- `total_ms`：端到端总延迟，等于 embedding_ms + max(vector_search_ms, bm25_search_ms) + rerank_ms + llm_total_ms + 序列化开销

**各步骤结果（调试 bad case 的关键）**
- `vector_hits`：JSON 数组，向量检索 top-5 的 chunk_id + 相似度分数。排查"为什么这个词没被召回"时直接看这里面有没有正确的 chunk
- `bm25_hits`：JSON 数组，BM25 检索 top-5 的 chunk_id + BM25 分数
- `rerank_scores`：重排后 top-5 的 chunk_id + rerank 分数。如果 rerank 把正确的 chunk 排到了后面，这里能直接看到
- `final_top5_ids`：最终喂给 LLM 的 5 个 chunk_id（是 `rerank_scores` 里排前 5 的那些）。LLM 实际看到的上下文就是这 5 个
- `final_count`：RRF 去重后的候选数（通常 ~8），影响 rerank 耗时
- `src_distribution`：来源分布 JSON，记录这 5 个最终 chunk 各自来自哪一路——`{"vector_only": 2, "bm25_only": 1, "both": 2}`。如果某一天 `bm25_only` 数量骤降，排查 BM25 索引是否被误清理

**模型版本 + 结果**
- `model_versions`：JSON，当前请求用的 embedding_model / rerank_model / llm_model。模型升级时客观区分新旧日志，不需要猜
- `error_code`：成功为 null，失败记录具体位置（如 "embedding_timeout"、"rerank_service_unavailable"、"llm_rate_limited"）。配合延迟字段能快速判断故障环节
- `prompt_tokens` / `completion_tokens`：token 消耗。prompt token 数异常说明 chunk 量有问题，completion token 和生成延迟直接挂钩
- `user_click`：用户反馈（赞/踩/无操作），是评估答案质量的最终信号

**一步汇总（chunk 数量的流转）：**

Query → 改写 → [向量 top-5 + BM25 top-5 并行] → RRF 去重 ~8 → Qwen3-rerank → top-5 → LLM

**延迟预算分配（P50）：**

```
Embedding 推理      30ms   HTTP 调用 text-embedding-v3
双路并行检索         5ms   max(vector_search=3ms, bm25_search=2ms)
Rerank 精排       100ms   8 candidates × ~12ms/candidate
LLM 生成            ← 取决于输出 token 数
───────────────────────────────────────
检索链路合计        135ms  (Embedding + 检索 + Rerank，不含 LLM)
```

单次请求检索链路 P50 约 135ms。LLM 生成是最大的变量——短答案（50 tokens）约 200ms，长答案（500 tokens）约 2s。

**Q17-附：完整链路原理——从文档到答案，每一步到底在做什么**

这个问题不是面试题，是我自己梳理系统时写的。目的是把离线建库和在线查询两条链路从头到尾串一遍，说清楚每个组件在做什么、输入输出是什么、为什么放在这个位置。不涉及具体参数调优（Q1~Q17 已经覆盖了），只讲**原理和数据流**。

**二、离线阶段：把文档变成可检索的数据**

离线阶段做的事：把 500 个 Markdown 文档处理成两种"可检索的形态"，存进 ChromaDB。这个过程由管理员手动触发，每几天一次。

```
                      500篇Markdown文档
                            ↓
              MarkdownHeaderTextSplitter
              按标题层级语义切分
                            ↓
                     ~2000个chunk
                    每个 ~384 token
                     /            \
                    /              \
        【路A：语义向量】      【路B：关键词检索】
                    │                  │
                    │        jieba 分词（加载自定义词库）
                    │        "优化顾问的告警阈值怎么配置"
                    │        → ["优化顾问","的","告警","阈值","怎么","配置"]
                    │                  │
       text-embedding-v3       rank_bm25 构建BM25索引
       神经网络推理              TF饱和 + IDF加权 + 长度归一化
       768个浮点数               全量chunk→分词→idf词典+doc_freqs
       稠密向量（无零值）         纯Python内存 (~2MB)
                    │                  │
                    ↓                  ↓
           ChromaDB                Python 内存
         dense index            BM25Okapi 对象
        (HNSW图结构)           (idf + doc_freqs)
```

**切分**：MarkdownHeaderTextSplitter 按文档的一二级标题做结构拆分，每个 chunk 约 384 token。标题路径拼入 chunk 正文头部，让每个 chunk 携带"我来自哪个文档的哪个章节"的信息。

**路A——语义向量（Dense）：** 每个 chunk 送进 text-embedding-v3，输出 768 维的稠密向量。这个向量就是 chunk 的"语义指纹"——两段意思相近的 chunk，向量距离近。全部 2000 个向量存入 ChromaDB，ChromaDB 用 HNSW（分层可导航小世界图）算法为它们建索引。HNSW 的原理：把 2000 个向量按空间距离分层连接成图结构，搜索时从顶层稀疏图快速定位大致区域，逐层向下精细查找，复杂度 O(log N)，2000 个向量单次检索约 3ms。

**路B——关键词检索（BM25 内存索引）：** 这条路**不走 ChromaDB**。我们用 rank_bm25 库在 Python 内存里构建索引。离线阶段：jieba 逐条分词全量 chunk → 建立词典（约 4000 个 term，存 term→DF/IDF）→ 为每个 chunk 建立词频表 doc_freqs（chunk → {term: tf}）→ 计算 IDF（稀有词权重高、常见词权重低）→ 构建 BM25Okapi 对象。在线阶段：query 经过 jieba 分词 → `bm25.get_scores(query_tokens)` → 遍历全部 chunk 的 doc_freqs 正向扫描查命中 → 逐条计算 BM25 分数（IDF × TF 饱和分量）→ 排序取 top-5，约 2ms。所有中间数据（IDF 字典、doc_freqs 词频表、doc_len 列表）都在 Python 内存里，出问题可以随时打断点查看。

**关键认知：路B 完全没有神经网络参与。** jieba 分词是字典+统计算法，BM25 是纯数学公式。整个路B 不需要 GPU、不需要 API 调用、不需要模型推理——这就是为什么 BM25 路的离线成本几乎为零，在线检索也只需要 2ms。

**两路存完后：** 向量路的数据在 ChromaDB dense index（HNSW 图），BM25 路的数据在 Python 内存（BM25Okapi 对象）。ChromaDB 只存密集向量，不存稀疏向量。两路数据存储在不同位置，但共享同一个 chunk 原文来源（ChromaDB 的 documents 字段）。查询时两路并行搜——向量路走 ChromaDB HNSW（~3ms），BM25 路走正向扫描 doc_freqs（~2ms），结果 RRF 融合。

**三、在线阶段：用户提问到返回答案**

在线链路 Q17 已经逐步骤讲过，这里不重复。从原理角度补充几个关键点：

**为什么需要 Query 改写？** 用户输入的词和文档使用的词不在同一个语义空间。"OA 告警怎么配" → 文档里写的是"优化顾问监控告警配置"。不改的话检索基本对不上。改写做的事就是把用户的日常表述翻译成文档的正式表述——第一层映射表保证专有名词不丢（"OA" → "优化顾问"），第二层 LLM 去口语化。这一步做完，后面的检索才能命中。

**为什么两路要并行？** 两路完全独立——向量检索跑 ChromaDB 的 HNSW 图，BM25 检索跑内存 BM25Okapi 对象。不共享任何中间状态。并行执行，耗时取较慢的那路（约 5ms），而不是叠加。

**RRF 为什么不用线性加权？** 向量相似度（余弦，0~1）和 BM25 分数（理论无上限）量纲完全不同——0.9 的余弦和 9.5 的 BM25 没法直接比较。直接加权会导致一路的分数淹没另一路。RRF 只关心排序位置（rank），天然规避量纲问题。

**Rerank 为什么放在融合之后？** RRF 只看排序位置，判断粒度粗。8 个候选中可能有语义相近但实际不相关的。Rerank 用 cross-encoder 逐对精判 query-chunk 相关性，过滤干扰，8 进 5 出。

**LLM 生成这一步到底收到什么？** LLM 收到的不是裸检索结果，而是拼好的 prompt——System prompt（角色设定 + 行为约束）+ Few-shot 示例 + top-5 chunk 原文（每段标注来源文件名和标题路径）+ 用户原始 query。LLM 被要求逐句标注引用 chunk 编号，保证可溯源。

**四、完整数据流一览**

```
【离线：文档 → 索引】
Markdown文档 → 切分 → chunks
                          ├→ Embedding模型 → 768维稠密向量 → ChromaDB dense index
                          └→ jieba分词 → rank_bm25 构建索引（词典 + doc_freqs）→ Python 内存（BM25Okapi 对象）

【在线：用户提问 → 答案】
用户query → 改写 → Embedding ─┬→ ChromaDB dense检索 top-5 ─┐
                             └→ jieba→rank_bm25 内存检索 top-5 ─┘
                                                              ↓
                                                       RRF融合 ~8候选
                                                              ↓
                                                       Rerank精排 → top-5
                                                              ↓
                                                       LLM生成 → 带引用答案
```

**Q18.** 拒答机制与答案错误处理

**没有单独的意图识别模块**，拒答通过 prompt 工程实现。System prompt 写了"如果文档中没有相关内容，直接告知用户「当前知识库未覆盖此问题」。不要编造信息。"，few-shot 中也放了拒答示例。这是最小成本的兜底，但不完美。

**根本性局限：检索永远会返回 top-5 chunk，LLM 天然信任权威来源。** 向量检索和 BM25 不知道什么叫"不相关"——用户问一个知识库没覆盖的问题，检索仍然返回 5 个 chunk（可能是包含部分关键词的文档片段，也可能是 embedding 空间中"相对最近"但语义很远的内容）。LLM 看到 5 个带 `[来源: xxx.md]` 标记的 chunk，格式正式措辞专业，本能反应是"基于这些回答"而不是"这些都不相关，应该拒绝"。这是 RAG 的结构性矛盾：检索的设计目标是"永远给结果"，生成需要的是"没结果就说没有"，两者之间存在信息不对称。

**当前三层缓解措施**（组合起来降低编造率，没有一层能根治）：

1. **System prompt 给 checklist 而非笼统规则**：不只写"不相关就拒答"，而是给出具体判断标准——"如果 retrieved chunk 中的关键术语和用户问题不匹配，或 chunk 描述的场景和用户问的不同，请明确告知知识库未覆盖"。具体 checklist 比笼统指令执行更准。

2. **Few-shot 展示"什么情况下应该拒答"**：刻意选了"检索结果包含部分关键词但语义不匹配"的 case。LLM 通过示例学到的行为模式比通过指令约束更稳定。

3. **Rerank 分数作为客观质量信号**（当前可选，后续可做轻量兜底）：rerank 在给每个 chunk 算相关性分数，top-1 score < 0.2 说明 8 个候选中没有一个真正相关——这是一个客观信号，不是 prompt 里的主观判断。要加的话改动极小：rerank 之后、LLM 生成之前加一行判断，低于阈值直接返回拒答。

**为什么没做硬阈值拦截：阈值校准数据不存在，且定义本身就难。** 设阈值需要一批"知识库确实没有答案"的 query 来校准分界点。构建这个数据集的成本不在于技术——枚举知识库范围外的各种问题类型，难在定义本身（"什么叫不在知识库范围内"不好界定）。没有校准数据时硬设阈值，宁可设松不设严：放几个弱相关的问题让 LLM 试试，也比误拒把用户挡在外面好。这也是不做单独意图分类模块的原因——不是省 100ms 延迟，而是"能不能回答"这个任务本身需要校准数据，而构建成本在当前规模下不合理。

**后续演进路线。** 短期（积累一批 bad case 后）：回溯这些 case 的 rerank top-1 分数分布，找一个统计上合理的阈值作为拦截线，比如覆盖 95% 已知 bad case 的分位点。长期（反馈量到日均 500+ 后）：按问题类型分别校准阈值（配置类比闲聊类更严格），或者用几百条已标注样本训练一个轻量二分类辅助模型（embedding + MLP），作为 prompt + 阈值双通道之外的额外参考信号，不替代主决策。

**当前答错处理。** 没有自动纠错机制。用户点踩写入 QueryLog（user_click 字段），漏到人工群的由人工排查后回复，bad case 定期回流到评测集。

**Q19.** 多轮对话能力

**当前没有做多轮。** 每个 /ask 独立无状态。内部知识库场景下，用户提问模式是"遇到问题→输入完整问题→得到答案"，每问自包含。线上日志中追问式提问几乎没有。如果用户打了"刚刚那个呢"，系统作独立问题处理，LLM 回复"请提供更具体的问题"——无用户投诉。

**不做多轮的核心理由：架构复杂度与维护成本的权衡。** 从下面的设计方案可以看到，引入多轮不是"存几条历史消息"那么简单——需要 MySQL 做持久化和缓存重建、Redis LIST 做活跃缓存同时规避 big key、滑动窗口 + LLM 摘要的压缩机制、messages 和 prompt 文本的混合拼接、离线回溯时的完整上下文还原。每一层都有工程成本和边缘 case（压缩质量不稳定、缓存与 DB 一致性、session 恢复的准确性）。在当前日均 100 问、追问率趋近于零的体量下，这些复杂度的投入产出比不成立。

**参考 Claude Code 的实现：** Claude Code 用一个 history.jsonl 文件记录所有对话，每条含 display（消息原文）、timestamp、sessionId。多轮通过 sessionId 聚合。上下文过长时早期轮次压缩为摘要移出活跃窗口，但完整原文始终保留在 jsonl 中。**核心思路：一份持久化存储记录全部历史，活跃窗口（内存）只保留最近上下文。**

**如果引入多轮，架构设计：**

**1. 存储：MySQL（持久化）+ Redis（缓存）。**

**MySQL** 每轮一条记录，作为持久化存储：

写入时机：每轮生成答案后 INSERT。MySQL 的作用是 Redis 过期后重建缓存——用户同一 session 在 30 分钟后回来，不会丢失上下文。

**Redis** 作为活跃缓存，存当前 session 的 messages。为解决 big key 问题（单 key 存全部 messages 序列化后体积不可控），用 LIST 结构代替单 key JSON：
- 每条 message 是 LIST 的一个元素，key = `chat:{user_id}:{session_id}:messages`
- 写入用 `RPUSH`，超出窗口用 `LTRIM` 裁剪
- 读取用 `LRANGE 0 -1`，不需要反序列化整个大 JSON

**2. 压缩机制：滑动窗口 + 摘要。** Redis LIST 中始终保留最近 5 轮：

| 位置 | 形式 | 存储 |
|-----|------|------|
| 最近 2 轮 | 完整原文（user+assistant） | LIST 中保留最新 4 条元素 |
| 更早 3 轮 | 单句摘要（保留关键实体和数值） | LIST 中保留 3 条元素 |
| >5 轮 | 丢弃 | LTRIM 裁掉 |

写入第 N+1 轮时触发滑动：LIST 中最早的 2 条（最早一轮的 user+assistant）移除，第 N-2 轮的原文在回写 MySQL 前由 LLM 生成一句话摘要。

**3. 拼接方式：messages 数组 + prompt 文本混合。** 最近 1-2 轮作为独立 user/assistant message 插入 messages 列表。更早的轮次压缩为单句摘要拼入 system prompt。预算大致对半分。

**4. 上下文窗口挤压。** N 轮 = 2N 条 message，每轮 200-300 token，3 轮额外 600-900。现有 prompt ≈ 2750 token，总输入 3500+。问题不在塞不下窗口，在于"Lost in the Middle"——历史 message 落在 system prompt 和当前 query 之间，注意力最低。

**5. 跨用户隔离。** JWT 解析 user_id，Redis key 和 MySQL 都拼入 user_id，函数签名强制要求 user_id 参数。

**数据流：**
```
① 用户请求
   ↓
② 读 Redis：LRANGE chat:{user_id}:{session_id}:messages 0 -1
   ├─ 命中 → 取最近 5 轮 messages
   └─ 未命中/TTL 过期 → 查 MySQL（WHERE user_id+sesson_id ORDER BY turn_index）
       重建 messages 列表 → RPUSH 写回 Redis → 设 TTL=30min
   ↓
③ 拼接：最近 2 轮→messages 数组，早 3 轮摘要→system prompt
   ↓
④ LLM 生成，返回答案
   ↓
⑤ 写 Redis：本轮 user+assistant 两条 RPUSH，LTRIM 保留最近 10 条（5 轮）
   ↓
⑥ 写 MySQL：INSERT 两条记录（user + assistant）
```


**Q20.** 生成模型用的哪个？为什么选这个？上下文窗口多大？你是怎么组织 prompt 的？做了哪些 prompt engineering？system prompt、few-shot、chain-of-thought，各加了多少？有对比实验吗？

**模型选型：DeepSeek V4 Flash**

用的是 DeepSeek V4 Flash，走内部统一 API。选它的逻辑不是做了一轮多模型对比评测，而是受现实约束：内部合规要求只能用已采购的模型，候选池有限。在可用模型中选 V4 Flash 的理由有三：第一，Flash 变体是 DeepSeek 的轻量版，推理延迟在同系列中最低，适合 Q&A 这种对响应速度敏感的场景；第二，生成质量在内部知识库问答这个任务上够用——文档术语规范、答案结构清晰，不需要最强的推理能力；第三，成本低——日均 100 问，Flash 的 API 单价远低于 Pro 或 V3 完整版。

没有做正式的多模型对比评测。原因同上——候选池小，且更换模型的审批流程比技术验证更重。实际做法是用同一批 100 条 QA 跑了几条典型 case，对比 Flash 和完整版的输出质量，确认没有明显的准确率下降后就定了。

**上下文窗口**

V4 Flash 原生支持 128K token 上下文窗口。我们的实际用量远低于这个上限——Rerank 后 top-5 个 chunk，每个 384 token，加上 system prompt、few-shot examples 和用户 query，单次请求的输入 token 通常在 2500~3500 token 之间。输出 token 视问题复杂度，通常在 100~500 token。上下文窗口不是瓶颈。

**Prompt 组织：System prompt 定基调 + Few-shot 定格式**

这个场景下最有效的 prompt 策略是「System prompt 管行为边界，few-shot 管输出规范」。原因：用文字描述格式要求（"请使用 Markdown、标注来源、关键步骤用编号列表"），LLM 理解的稳定性不如直接给它两个示例让它照着学。示例能编码格式规范——引用怎么标、代码块什么时候用、回答详细到什么程度——比指令更不容易漂移。

当前 prompt 由四段组成：

System prompt（固定，约 200 token）：只定义角色和行为边界。内容——"你是内部技术支持助手，基于提供的文档内容回答问题。只使用文档中明确包含的信息，如果文档中没有相关内容，直接告知用户「当前知识库未覆盖此问题」。不要编造信息。"

Few-shot examples（固定，约 500 token）：2 个示例，展示理想的输出格式。示例的选择有两个原则——第一，示例内容用通用/虚构场景，不引用真实的配置项名称或具体数值，避免文档更新后示例变成错误信息；第二，两个示例分别覆盖不同类型：一个演示「单个配置项的精确回答」（带来源标注、配置值用代码块包裹），一个演示「多步骤操作指引」（用编号列表、每步标注来源）。这样 LLM 无论遇到哪类问题都能找到对应的格式模板。

Context（动态，约 2000 token）：Rerank 后的 top-5 chunk，每个 chunk 附带来源标注——file_name 和标题路径。chunk 按 Rerank 分数降序排列。

User query（动态，约 50 token）：改写后的用户问题。

四段拼装顺序：System prompt → Few-shot examples → Context → User query。System prompt 和 few-shot 在顶层且固定不变，可被 LLM 推理框架的 prefix caching 命中，节省重复推理成本。

关于 few-shot 的一个常见质疑是「示例会过时」。我们的应对方式是不用真实业务数据写示例——示例中的配置文件名、参数名、阈值都是虚构的（如「在 config/service.yaml 中设置 timeout 参数为 30」），只演示格式不传递真实信息。这样即使线上文档频繁更新，示例永远有效。

**为什么没做 CoT**

CoT（Chain-of-Thought）的核心价值是让 LLM 在推理型任务上显式写出思考步骤——数学计算、逻辑推导、多条件判断。我们的场景是检索式知识问答，LLM 拿到 chunk 后做的是信息整理和重述，不是推理。用户问"OA 告警阈值怎么配"，答案是一个确定的配置值，不需要"首先...其次...因此..."的推理链。在当前场景下加 CoT 只会多吃 token、加延迟，不提升答案质量。后续如果出现了需要跨文档推理的问题（比如"A 服务的配置依赖 B 服务的哪个参数"），再针对性加 CoT prompt，而不是全量启用。

**对比实验的意义与取舍**

Prompt 对比实验（A/B 测试不同 system prompt 措辞、不同 few-shot 示例）的工程价值是量化 prompt 变更的影响、防止劣化。但它有前提条件：样本量要够。Prompt 差异对答案质量的影响通常不是「对/错」级别的，而是「好/更好」级别的——需要几十上百条评测才能统计显著。在当前日均 100 问、评测集 100 条的体量下，做正式 A/B 测试的投入产出比不高。务实做法：每次改 prompt 后，人工抽查 20 条典型 case 覆盖不同类型（配置类、操作类、故障类），对比新旧两版输出，肉眼判断有没有退化。这个方法不严谨，但对当前规模够用。

**Q21.** 为什么不用 LangChain？很多 RAG 项目都用它，你们为什么自己写？

**没用 LangChain，核心原因：我们的链路太简单，LangChain 的抽象成本大于收益。**

RAG 链路一共 7 步：改写 → Embedding → 双路检索 → RRF 融合 → Rerank → 拼 prompt → LLM 生成。每一步输入输出明确、没有条件分支、没有循环、没有并行（双路检索是显式并行的，不是框架动态调度的）。用显式 Python 写出来就是 7 行顺序调用，每行都可以单独打断点、打日志、做单元测试。

**如果用 LangChain 会引入哪些成本：**

**1. Runnable 包装成本。** LangChain 的 LCEL（`|` 操作符）要求每个步骤包装成 Runnable 对象。项目里有自定义逻辑（query 改写、RRF 融合、prompt 拼接），这些不是 LangChain 内置组件，需要自己写 Class 继承 Runnable 或 `@tool` 装饰器。包装完后并没有减少代码量——反而多了接口适配层。

**2. 调试困难。** 显式 Python 可以在任意两步之间插 `print()` 或 `logger.info()` 看中间结果。"BM25 召回了什么？Rerank 后 top-5 有哪些？"——加一行就行。LangChain 的中间结果需要通过 `RunnableConfig` 的 `callbacks` 或 `LangSmith` 才能看到，调试链路长了一步。出问题时需要区分"是 LangChain 的 bug 还是我的逻辑 bug"。

**3. 版本不稳定性。** LangChain 从 0.1 到 0.3 经历了多次 breaking changes——Chain 被 LCEL 替代、部分内置模型的 import path 变了、回调函数签名改了。项目跑得好好的，升个 minor 版本就要改代码。对于日均 100 问的内部工具，这种维护成本不值得。

**4. 错误处理和重试的隐藏复杂度。** 显式 Python 的 try/except 包在哪一步、每步的重试策略是什么，一目了然。LangChain 的 retry 机制分散在 `max_retries` 参数、`RetryPolicy`、以及各个 model provider 的默认行为中——哪一步重试了、重试了几次、成功了还是最终失败了，不容易追踪。

**5. 团队认知成本。** 新成员看代码，显式 Python 链路不需要任何框架知识就能理解。引入 LangChain 后，新成员需要先学 LCEL 语法、Runnable 协议、LangChain 的 model I/O 抽象，然后才能看懂"这个 `|` 到底在干什么"。

**什么情况下会用 LangChain。** 如果链路超过 20 步、有多路并行（比如同时检索多个数据源后合并）、需要动态路由（根据 query 类型走不同链路）、或者对接 3 个以上不同的 LLM 提供商——LangChain 的编排能力就有价值了。我们的场景用不上。

**那为什么不至少用 LLM 调用的封装？** 即使用 LangChain 的 `ChatOpenAI` 做 LLM 调用封装也比裸 HTTP 请求方便——自动处理 token 计数、流式解析、重试。但项目已经直接调了内部 API，换了反而多一层抽象。选型原则：**不加没有实际收益的抽象层。**

**Q22.** 生成的时候有没有引用？用户怎么知道答案来源于哪个文档？

**当前：文件名级引用，仅文本展示，无超链接。** context 中每个 chunk 带 `file_name > 一二级标题` 的来源标注，system prompt 引导 LLM 在答案末尾列出参考来源。前端展示"参考来源：xxx.md"列表。**没有前端预览，没有可点击的超链接**——用户看到的是文件名，需要自己到 Wiki 里去搜。

**改进方案：建立 file_name → 在线文档 URL 映射，前端渲染为可点击超链接。** 方案分两层：

**映射层。** 需要一个从 file_name（如 `oa_monitor.md`）到在线文档 URL（如 `https://wiki.internal.com/pages/123`）的对应关系。三种建立方式：
- **手动维护映射表**（JSON/YAML）：每新增一个 MD 文件手动配一条。适合文档总量小、新增频率低的场景，成本低。
- **按命名规范自动拼接**：如果文档平台 URL 和 file_name 之间有可预测的对应关系（如 `oa_monitor.md` → `https://wiki.internal.com/docs/oa_monitor`），直接规则生成，零维护。
- **调用平台 API 自动建立**：如果有检索 API（如 Confluence 的 `GET /rest/api/content?title=OA监控告警`），脚本批量查 page_id 并写入映射表，后续增量同步。

**前端渲染层。** 后端下发的 context 事件中，在 file_name 旁附带 URL（或前端拿 file_name 查映射表）。渲染参考来源列表时，文件名渲染为 `<a href="..." target="_blank">` 超链接，用户点击跳转。

**Q22-附. file_name 到在线文档链接的映射 —— 为什么不用在线平台直接解析？**

**为什么 F12 看不到 MD？** 现代文档平台（Confluence/语雀/飞书）后台存的是私有 JSON 格式，不是 MD 文件。数据库里存的是结构化 JSON（如 `{"type":"heading","content":[{"type":"text","text":"OA监控告警"}]}`），API 返回 JSON，前端 JS 解析后渲染成页面。整个流程里不存在 MD 文件。只有 GitHub Wiki、GitBook 这种基于 Git 仓库的平台才直接暴露 MD 原文。

**为什么不直接爬在线平台建索引？** 如果走在线爬取，路径是：调 API → 拿 JSON → 遍历 JSON 树提取正文 → 拼接标题层级 → 去除导航/评论/侧边栏噪声 → 转 MD → 切 chunk。三个核心难点：

1. **JSON→文本解析是脏活。** 平台的 JSON 是给前端渲染用的，不是给 NLP 用的。标题可能是三层嵌套 `{"type":"heading","content":[{"type":"text","text":"..."}]}`，你得递归遍历、拼 text 节点、处理 inline 格式。每个平台的 schema 不同——换一个平台就要重写一套解析器。
2. **非正文去除是脏活。** API 返回的 JSON 包含评论区、点赞数、导航栏，你需要区分哪些 block 是正文、哪些是 UI。漏掉了 chunk 里就会混入"点赞 3 评论 5"的噪声。
3. **依赖脆弱。** 平台改版 API 格式一换，你的提取逻辑就得跟着改。MD 的 `#` `##` 标准三十年没变过。

**实际做法：用平台的导出接口。** 大多数平台提供"导出为 MD"功能（Confluence 有 Export、语雀有导出、飞书有导出）。导出时平台自己完成了 JSON→MD 转换，你直接拿到干净的 `# 标题\n正文`。管理员写个脚本批量调导出接口下载即可，不需要解析任何私有格式。500 篇文档每几天导出一次，成本几乎为零。

**file_name → URL 映射怎么做？** 用一个 JSON 文件维护：
```json
{
    "data/oa_monitor.md": "https://wiki.internal.com/pages/oa-monitor",
    "data/region_whitelist.md": "https://wiki.internal.com/pages/region-whitelist"
}
```
FastAPI 启动时加载到内存 dict，chunk 返回前端时自动拼上 URL。前端把 file_name 渲染为蓝色超链接。映射表集中维护在 Git 里（不改 ChromaDB），URL 变了改一行重启即生效。500 篇文档手动配一次约半小时，后续新增一篇加一行。

**Q23.** 幻觉问题你怎么处理的？有哪些具体的防范措施？你做 factuality 评估了吗？幻觉率是多少？

**幻觉主要靠拒答机制解决（Q18）。** 绝大部分幻觉发生在 LLM 没有相关信息但选择编造的场景——拒答把这条路堵死。但不是所有幻觉都能被拒答 cover：LLM 拿到了相关 chunk，但跨文档合并错了信息（比如 A 文档说「阈值 80%」、B 文档说「方案 X 适用」，LLM 合并成「方案 X 阈值 80%」）；或者 chunk 本身没问题，LLM 基于正确上下文推导出了错误结论。这两种场景下 LLM 不会拒答（它认为自己有依据），但答案仍然是错的。

**三个环节：**

1. **拒答机制（核心，详见 Q18）**。System prompt 给出具体判断标准（不只看关键词命中，还要看语义是否匹配），few-shot 展示"什么情况下应该拒答"的示例，rerank score 作为客观信号补充（top-1 score < 0.2 直接返回拒答）。第一道也是最重要的防线。

2. **检索质量兜底（Q13）**。Rerank 过滤不相关 chunk，减少 LLM 拿到错误上下文的概率。引用编号约束（Q22）让 LLM 为每句话标注来源——跨文档合并错误时，引用标注会自相矛盾，暴露出问题。

3. **事后发现闭环（Q15）**。发版前 RAGAS Faithfulness 比较拦截系统性退化，线上用户点踩和人工排查回流 bad case。不阻止幻觉发生，但保证能被发现。

**Factuality 评估：没有拆成独立指标，而是融入了评估框架的三个环节。** Factuality 评估的本质是"答案中的 claims 是否客观真实"，但内部文档 QA 不存在一个更高权威的外部知识库来校验——知识库本身就是事实来源。所以分三层来做：

1. **RAGAS Faithfulness 做第一道筛选（Q15）**。验证"答案是否忠于给定的上下文"——上下文是知识库的子集，忠于上下文 ≈ 忠于知识库。每次发版跑 100 条 QA，Faithfulness delta > 0.2 的 case 标记出来。这不直接告诉你"答案对不对"，但能快速定位"哪个版本的事实一致性有问题"。

2. **L3 人工验证做第二道确认（Q15）**。对重大变更（chunk 策略、模型换代等），抽 30 条 QA 人工逐条判断：核心结论正确吗？有事实错误吗？有幻觉吗？引用准确吗？人在判断时就是用的 factuality 标准——他会看答案在业务上是否正确，而不是只看是否忠于上下文。

3. **线上 bad case 回流做长期兜底（Q18）**。用户点踩或人工群反馈的问题，排查后写入评测集。这些 case 里如果发现 factuality 问题，说明 Faithfulness 没拦住（通常是跨文档合并错误或推导错误），针对性改进后该 case 成为后续发版的固定考题。

**幻觉率：** 没有系统性测算过——RAGAS Faithfulness 做的是新旧版本的相对比较，不能输出绝对值。从日常抽查看，明显幻觉（答案中出现上下文没有的信息）占比很低，且几乎都出现在 LLM 没触发拒答的场景。

**各段耗时分析**

Query 改写（100ms）：第二层的 LLM 口语化去除是主要耗时。Prompt 极短（"将以下口语化问题改写为正式表达"），输入输出各约 50 token，一个轻量 LLM 调用。第一层的映射表是纯字符串替换，1ms 不到，可以忽略。这 100ms 本质上是 LLM 推理的首 token 延迟 + 短文本生成时间。

Embedding 推理（30ms）：text-embedding-v3 走内部 HTTP API（OpenAI 兼容格式），单条 query 的向量化是模型前向传播一次，不涉及自回归生成，所以延迟远低于 LLM 生成。30ms 里约一半是网络往返，一半是模型推理。P99 60ms 的波动主要来自内网 HTTP 网络抖动，模型侧因为 query 长度固定（改写后 ~50 token），推理时间很稳定。

双路检索（5ms）：向量 HNSW 搜索 ~3ms——2000 个 768 维向量上的图搜索，O(log N)，实际遍历节点数远小于 2000。BM25 ~2ms——jieba 分词 + 正向扫描 doc_freqs 打分，全内存操作。两路并行，耗时取较慢的 HNSW 那路。P99 15ms 的波动很小，因为纯内存计算不涉及网络 I/O。

Rerank（100ms）：8 个候选逐个过 Qwen3-rerank cross-encoder。每个候选的推理约 12ms（query+chunk 拼接后单次前向传播），8 × 12 ≈ 96ms，加上 batch 组装开销，约 100ms。注意这里是串行还是批处理——如果 8 个组成一个 batch 一次过模型，延迟可以降到 ~30ms 但需要模型支持动态 batch。当前配置为逐个推理，延迟更高但实现简单。P99 250ms 主要来自 GPU 排队——如果多个请求同时到，后续请求的 8 个候选要等前面的算完。

LLM 生成（400ms）：DeepSeek V4 Flash 的自回归生成。输入约 2750 token（System + Few-shot + Context + Query），输出 100~500 token。Flash 变体的推理速度大约是 30~50 token/s，所以 200 token 输出对应 ~400ms P50。为什么 P99 跳到 2.5s？两个原因：一是偶尔有需要长回答的问题（500 token 输出），二是 LLM 服务的 GPU 排队——内部统一 API 被多个业务共享，高峰期可能有排队延迟。

延迟预算分配：检索段（改写 + Embedding + 检索 + Rerank）占总延迟约 37%（P50），LLM 生成占约 63%。LLM 生成是端到端延迟的绝对大头，且尾部延迟波动大（输出 100 token 和 500 token 差距显著）。检索段各环节延迟相对稳定，P99 和 P50 的差距主要来自 LLM 改写和 Rerank 两个 HTTP 调用的网络抖动。

优化方向：当前延迟对日均 100 问完全够用，不需要优化。如果 QPS 上升，优先优化的不是检索段（已经 < 250ms），而是 LLM 生成——切换更快的生成模型、限制输出 token 上限、或引入流式输出（SSE 已支持，首 token 到达即可开始渲染，用户感知延迟远低于完整生成时间）。

**Q24-附. 文档里多处提到 HTTP API 调用——我们用的到底是什么协议？和 gRPC 有什么区别？**

我们的所有模型调用——Embedding（text-embedding-v3）、Rerank（Qwen3-rerank）、LLM 生成（DeepSeek V4 Flash）、Query 改写——全部走 HTTP。内部 AI 平台提供的是 OpenAI 兼容 API，格式和 openai Python 库完全兼容：

```
Embedding 调用:  POST https://internal-api.company.com/v1/embeddings  + sk-xxx
Rerank 调用:      POST https://internal-api.company.com/v1/rerank        + sk-xxx
LLM 生成:         POST https://internal-api.company.com/v1/chat/completions + sk-xxx
Query 改写:       POST https://internal-api.company.com/v1/chat/completions + sk-xxx
```

统一 HTTP 的好处是一个 `openai` 库覆盖所有调用，Embedding 走 `client.embeddings.create()`，生成走 `client.chat.completions.create()`，代码层面的调用模式完全一致，不需要为不同模型维护不同的客户端。LLM 生成的流式输出走 SSE（Server-Sent Events），基于 HTTP 原生的 `text/event-stream`，和 gRPC stream 在内网环境下的首 token 延迟差异 < 1ms，用户感知不到。

以下是对比体系——虽然我们没用 gRPC，但这是面试常见追问。

**序列化格式：HTTP REST 用的是 JSON 文本，gRPC 用的是 Protobuf 二进制。** JSON 的典型载荷如 `{"question":"OA 告警阈值怎么设置","user_id":"zhangsan","top_k":5}` 约 65 字节，人类可读、调试方便。Protobuf 不传字段名（用预定义的 field number 代替），数字用变长编码，没有花括号/引号/逗号这些结构符号，同等内容约 40 字节，缩小 30~50%，但二进制不可读、需要 `.proto` 文件才能解析。在几百字节这个量级下体积差异没有实际意义——65 字节和 40 字节在内网传输时间差 < 0.001ms。Protobuf 的序列化/反序列化 CPU 开销低于 JSON，但在我们的 QPS 下可以忽略。

**连接模型：HTTP/1.1 是短连接模型，gRPC 基于 HTTP/2 的长连接多路复用。** HTTP/1.1 每次请求可能新建 TCP 连接（三次握手 = 1 个 RTT），Keep-Alive 可以复用但请求在单条连接上必须排队（队头阻塞）。gRPC 底层是 HTTP/2，一条长连接上同时跑多个 stream，所有请求共享同一条 TCP 连接，没有队头阻塞。这个差异在低 QPS 下不成立——日均 100 问意味着每分钟不到 1 个请求，连接池永远是空的，不存在排队问题。高并发（万级 QPS）时 HTTP/1.1 的连接池才会成为瓶颈，此时 gRPC 的多路复用有显著优势。

**流式传输：HTTP 用 SSE（text/event-stream），gRPC 用 HTTP/2 原生 bidirectional streaming。** SSE 基于 HTTP 长连接，持续推送 `data: {...}\n\n` 格式的 JSON 文本块，每块几十字节，解析开销极低。gRPC stream 没有 `data:` 前缀和 `\n\n` 分隔符，每帧直接是 protobuf 二进制，传输更"干净"但需要 `.proto` 编译步骤。在我们的 LLM 逐 token 输出场景下，首 token 延迟差异 < 1ms，没有实质区别。

**gRPC 真正有优势的场景集中在四个方向：** 高并发（万级 QPS）时 HTTP/1.1 连接池成为瓶颈，gRPC 多路复用一条连接扛所有；大体积传输（MB 级别）时 protobuf 的压缩优势和 JSON 序列化的 CPU 开销差距开始显现；微服务内部通信受益于 `.proto` 的强类型契约，编译时就能发现接口不匹配；双向流（语音对话、实时协同编辑）用 gRPC streaming 比 SSE 更自然。

我们当前的量级（日均 100 问，QPS < 1）处于所有方案都够用的区间。全 HTTP 的选择不是性能选型，而是统一用 OpenAI SDK 最省事——一个库、一种调用模式、零额外依赖，没有引入 gRPC 的实际收益。

**Q25.** LLM 服务是自建还是调 API？有做限流、重试、熔断吗？如果 LLM 服务挂了，系统怎么降级？用户会看到什么？

**模型部署方式：全部走内部统一 API**

链路中涉及三个模型——Query 改写的 LLM、Embedding 的 text-embedding-v3、Rerank 的 Qwen3-rerank、生成的 DeepSeek V4 Flash——全部走内部统一 API，没有一个是我们自己部署的。内部 API 是一个公司级的 LLM 网关，统一做认证、限流、路由、负载均衡，各业务团队通过 HTTP（OpenAI 兼容格式）调用。对我们来说，它就是一个黑盒——我们不需要关心模型实例跑在哪台 GPU 上、有几个副本、扩缩容策略是什么。

这个架构的好处是运维成本低——GPU 故障、模型升级、版本管理都由平台团队负责。代价是我们对延迟的尾部波动不可控——Q24 提到 LLM 生成的 P99 2.5s，其中一部分就是 API 网关的多租户排队导致的，我们看不到队列深度也无法调优。

**限流：当前不需要，但方案已经想好**

日均 100 问，QPS 峰值不到 1，远远低于内部 API 的默认限流阈值（通常 100 QPS/业务线）。当前没有在业务层做限流。但如果后续 QPS 上升，方案是用 Token Bucket——在 FastAPI 层加一个内存限流器，每秒放行 N 个请求，超出的返回 HTTP 429。为什么不在调用 API 侧做？因为 API 被限后返回的错误码是通用的，不加业务层限流的话用户会看到技术报错信息而不是友好的"当前请求过多，请稍后重试"。

**重试：只对幂等的 Embedding 和 Rerank 做**

三个模型调用的重试策略不同。Embedding 和 Rerank 是幂等的——同一个 query 每次计算结果相同——所以配置了 3 次重试，指数退避（100ms → 200ms → 400ms），覆盖网络瞬时抖动和 HTTP 临时不可用。LLM 生成不做重试——生成是非幂等的（同一个 prompt 两次调用输出可能不同），且生成延迟长（P50 400ms），重试会显著拉长用户等待时间。如果生成失败了，直接返回错误让用户重试，而不是系统自动重试。

**熔断：对 LLM 生成做，对 Embedding 不轻易做**

熔断的逻辑是保护下游服务——当连续失败达到阈值时，暂时不再发起新请求，给下游恢复时间。我们的策略是只对 LLM 生成做熔断：连续 5 次失败（超时或 5xx）后熔断器打开，30 秒内所有生成请求直接快速失败，30 秒后进入半开状态，允许一个探测请求通过——如果成功则关闭熔断器恢复正常，如果失败则继续熔断 30 秒。Embedding 和 Rerank 不做熔断——如果 Embedding 都不可用了，说明基础设施出了问题，熔断也救不了，不如直接让请求失败触发告警。

**降级：两层递进**

LLM 服务挂了时的降级分两层：

第一层（自动）：LLM 生成失败时，前端不显示空白，而是展示检索结果——Rerank 后的 top-5 chunk 原文 + 来源文件名。用户虽然拿不到组织好的答案，但至少能看到相关文档片段，手动定位。这个降级方案的工程成本极低——前端本来就有 context 事件的数据，不需要额外请求。

第二层（人工）：如果检索也挂了（比如 ChromaDB 起不来），前端显示"服务暂时不可用，请直接查看 Wiki 或联系人工支持"，附上 Wiki 链接和人工群入口。

为什么没有把语义缓存作为降级的第一层？缓存本身会引入一系列问题：key 怎么设计（用原始 query 还是改写后的 query？）、相似度阈值设多少（太严命中率低，太松可能返回不相关的缓存答案）、缓存过期和淘汰策略（文档更新后旧缓存答案已经错误，删还是不删？）。这些问题叠加起来，维护成本超过了它在降级场景中的收益——内部 API 的 SLA 很稳，还没遇到过大面积不可用，为一个低概率事件引入一套缓存系统不划算。

**Q26. 策略缓存做了吗？为什么不做查询缓存？**

缓存决策的核心结论是：系统没收敛时加缓存等于用旧版本的错误锁死用户体验。缓存是锦上添花的优化，不是雪中送炭的补丁——系统先做稳定，再考虑缓存。下面用三层递进逻辑展开：第一层算账不划算，第二层工程做不到，第三层核心是有害。

**第一层：不划算，ROI 算不过账。** 两个数字足够说明。一是 API 成本极低，DeepSeek V4 Flash 单价极低，单次请求约 2750 input 加 200 output token，日均 100 问月费不到百元。缓存系统从 ChromaDB collection 到相似度检索、失效逻辑、反馈联动、TTL，开发测试要数人天，省的钱还不够付开发成本。二是命中率天花板只有 30~40%，内部知识库问答服从帕累托分布，20% 高频问题占 80% 流量，剩下 80% 是长尾问题。长尾问题的特点是措辞高度多样化，五个人五种问法，且分布随知识库更新而漂移。缓存命中率上限约 35%，意味着 65% 的请求还是走完整链路，花一套缓存系统的工程成本大部分请求根本用不到。

**第二层：做不到，两个工程问题没有干净解。** 问题一是语义相似度阈值没有银弹。缓存匹配不能用字符串精确比对，"OA 告警阈值怎么配"和"怎么设置 OA 告警阈值"是同一个问题但字面完全不同，必须用 embedding 余弦相似度。阈值设高 0.95 命中率极低，措辞差异就把相似度压低了；设低 0.80 误匹配，"OA 告警阈值怎么配"和"OA 告警通知怎么关"语义接近但答案完全不同；取中 0.87~0.90 不同问题类型需要不同阈值（配置类 0.85、定义类 0.90），一个全局值覆盖不了。更致命的是阈值需要根据线上数据持续调参，但系统底层策略（chunk/Rerank/Embedding）每次变动 embedding 分布就变，阈值就得重新校准，缓存变成了一个需要持续喂养的调参黑洞。问题二是三套失效机制互相耦合。缓存需要同时回答什么时候删，答案是三套叠层：文档更新触发按 file_name 删除（主动，但遍历 O(N)、有删除窗口），24h TTL 自动过期（被动，但 24h 内文档可能已更新三次），容量淘汰 LRU/hit_count（被动，但两种策略各有盲区）。三套机制同时运转会产生意料之外的耦合，最典型的是高频问题写入缓存→文档更新触发删除→再次提问→再次写入→文档又更新→又删除，缓存在写入-删除-再写入-再删除的循环里空转。

**第三层：有害，缓存主动伤害系统（最核心的反驳）。** 前面两层说的是不划算和做不到，这层说的是做了反而更糟。三个伤害：

一是缓存放大效应。系统没收敛时每次发版都在改进（chunk size 调整、Rerank 参数优化、prompt 迭代）。引入缓存后早期生成的有瑕疵答案被锁死在缓存里，后续用户反复拿到旧错误答案，即使问题已被新版本修复。缓存把每次可能是当前最佳变成了永远是首次命中时的那个版本。系统越差缓存锁死的错误越多，系统越好缓存越阻碍改进触达用户。缓存放大的是系统的缺点。

二是评估失真。三层评估框架（Q15/Q16）依赖每次发版跑全量评测集，加了缓存后出现认知断层：评测告诉你 MRR/Faithfulness 提升了，但缓存用户拿到的还是旧版本答案。你无法判断用户满意度没变化是因为改进不够明显还是缓存挡住了新链路。缓存给可观测性盖了一层毛玻璃。

三是反馈闭环断裂。没有缓存时用户点踩→QueryLog 追溯完整链路→定位根因→修复→补充评测集，闭环完整。有了缓存：点踩答案是 3 天前旧版本生成的，那个版本已经不存在了，无法复现无法修复。缓存把时间维度引入了故障排查，当前阶段的系统不需要这个额外维度。

三个伤害的根因是同一个：缓存把时间这个变量塞进了一个还在快速迭代的系统。

**引入缓存的四个前置条件：** 链路已收敛（chunk、Rerank、prompt 连续 3 次发版无显著变化），质量已稳定（L3 人工验证连续 2 次发版无新发现的事实错误或幻觉），评测有覆盖（缓存命中率可通过评测集预估不是拍脑袋），瓶颈已量化（有数字证明需要缓存，不是觉得缓存不错）。当前阶段四个条件都不满足。策略是先把检索和生成做稳定，再考虑缓存。缓存是锦上添花，不是创可贴。

**附：条件满足后的缓存方案概要（设计参考，非当前实施计划）。** Key 用改写后 query 的 embedding（768 维），ChromaDB 存储。选改写 query 而非原始 query，因为术语标准化后语义相同的问题收敛到同一向量。Value 存 `{answer, sources: [{chunk_id, file_name, chunk_index, text}], file_names}`，确保缓存命中时前端仍能展示引用。失效策略三套叠层：文档更新按 file_name 删除 + 24h TTL + 容量淘汰（hit_count 升序踢出）。写入时机：生成成功 + 延迟 5 分钟 + 确认未点踩 + 未触发拒答，给用户反馈窗口。反馈联动：点踩立即删除，点赞淘汰权重 +5，缓存命中时点踩立即删除。核心原则是只删不更新——对缓存内容不确定时删掉重生成，比覆盖一个可能对的新答案安全。

**Q27.** 每天 100 个问题，你这个系统的 QPS 是多少（保守估计峰值）？做过压测吗？系统的最大吞吐量是多少？瓶颈在哪里？

**QPS 不能用均值估算，要看瞬时并发。** 内部知识库问答的流量有很强的突发性，故障时或版本发布后几十个人可能同时在问。按最坏情况算，一次故障时 20 人同时打开页面提问，请求在 1~2 秒内到达，瞬时并发约 10~20 QPS。机器人上线后提问门槛比 oncall 群更低，日均量级预期涨到 300~500，瞬时并发到 30~50 QPS。均值 QPS 对这类突发型流量没有参考意义。

**部署架构是 4 台 FastAPI 实例，各内嵌 ChromaDB（PersistentClient 模式，进程内调用），前面挂 LVS 做轮询负载均衡。** 选嵌入式而非集中式 ChromaDB server 的原因（详见 Q7）：读写比 1000:1，用写路径的一点同步成本换读路径的零网络延迟和无单点故障。离线索引构建由管理员通过管理接口触发，收归单人操作——嵌入式架构下多人同时触发重建会导致节点间索引版本不一致的竞态条件，且重建过程中读请求会看到不完整的中间状态。ChromaDB 的 PersistentClient 不提供事务隔离，所以在应用层保证同一时刻只有一个人在触发重建。重建完成后其他节点通过健康检查端点比对 chunk 总数来验证同步状态。当前几天甚至一周一次的重建频率下，这个流程不影响效率。

**瓶颈不在向量检索。** 应用层 4 个 FastAPI 实例无状态可线性扩展，Embedding/LLM/Rerank 走内部统一 API 网关级并发远超当前需求。向量检索方面嵌入式 ChromaDB 每节点独立处理自己 1/4 流量，HNSW 搜索仅 ~3ms（2000 chunk），进程内调用无网络开销，单节点远超当前 QPS。真正的瓶颈在 LLM 生成——P50 400ms、P99 2.5s，占端到端延迟的 63%。未来 QPS 上升时 LLM 是第一个需要优化的环节。当 chunk 量涨到 20000+ 且嵌入式单机内存成为瓶颈时，才需要迁移到分布式向量数据库（Milvus/Qdrant）。

**压测：没有做过正式压测。** 如果做，重点不是测平均 QPS 而是测瞬时并发——用 Locust 模拟 10/20/50 并发请求同时到达某节点，观察端到端延迟 P99 拐点。预期瓶颈先出现在 LLM 生成而非向量检索。

**Q28.** 向量数据库的高可用怎么做的？有没有主从、多副本？挂了怎么恢复？

**当前架构天然消除了 ChromaDB 的单点问题**

和 Q26 一致——4 个节点各嵌一个 ChromaDB（PersistentClient 模式），不是集中式 server。ChromaDB 没有独立进程，随 FastAPI 进程启动而加载、随 FastAPI 进程退出而释放。所以不存在"ChromaDB 挂了"这个场景——它不是一个独立服务，是 FastAPI 进程的一部分。

那"挂了"指的是什么？三种情况：

**情况一：某个节点的 FastAPI 进程崩溃。** ChromaDB 随进程一起退出。LVS 检测到该节点 TCP 端口不通，自动把流量从故障节点摘掉，请求转发到剩余 3 个健康节点。对用户的影响：1/4 的请求可能短暂失败（在 LVS 摘除节点之前的一两次请求），之后恢复正常。故障节点不需要紧急修复——可以等运维方便的时候再排查重启。

**情况二：某个节点的 ChromaDB 数据文件损坏（磁盘故障、误删）。** 该节点上的检索请求全部失败。LVS 摘除该节点后，其余 3 个节点继续服务。故障节点的恢复：从健康节点复制 ChromaDB 数据目录（约 6MB），或从零重建——跑一遍文档切分 + embedding 全流程，约 30 秒。

**情况三：全量 4 个节点同时故障。** 这是机房断电级别的灾难，不是 ChromaDB 高可用能解决的问题。

**恢复流程**

节点重启后的自动恢复流程：FastAPI 进程启动 → ChromaDB PersistentClient 初始化，从本地磁盘加载向量索引和元数据（~2s）→ BM25 索引在启动钩子中自动重建，从 ChromaDB 读出所有 chunk 原文 + jieba 分词 + 构建索引（2000 chunk < 1s）→ 健康检查通过（LVS 检测到 TCP 端口恢复可达），将该节点重新加入转发列表 → 恢复服务。整个过程约 3 秒，且不影响其他 3 个节点的正常服务。

**数据会不会丢**

不会。向量索引和元数据持久化在本地磁盘。BM25 索引是内存结构，但数据源是 ChromaDB 中的 chunk 原文，重启后自动重建。最坏情况——磁盘损坏导致数据文件不可读——从零重建，500 文档、2000 chunk 约 30 秒。

**跨节点一致性问题**

4 个节点的索引是否一致？文档更新由管理员手动触发，更新请求路由到某一台机器执行重建。重建完成后，该节点的 chunk 总数记录在健康检查端点中。其他 3 个节点定期（每次健康检查时）比对自己的 chunk 总数——如果与重建节点不一致，说明同步有问题，触发告警后管理员手动在该节点重新执行重建。当前更新频率几天一次，这个"手动 + 健康检查兜底"的方案足够。如果未来更新频率上升，换成共享存储（所有节点挂载同一个 ChromaDB 数据目录）即可，但当前不需要引入这个复杂度。

**未来扩展路径**

和 Q7 的结论一致：当数据量到万级 chunk 且需要真正的多副本自动故障转移时，正确路径不是给 ChromaDB 打补丁，而是换引擎——Qdrant 或 Milvus。但在这个体量到来之前，嵌入式架构已经提供了比集中式 server 更好的可用性：4 个节点互为冗余、故障隔离、无全局单点。

**Q29.** 整个系统的可观测性怎么做？日志、指标、链路追踪各是怎么布的？你从仪表板上看到检索延迟突然飙升，你查什么？

**当前状态：分步骤日志 + session_id 区分用户，没有对接监控平台**

可观测性当前只靠日志。做法很直接——在每个链路步骤打完耗时日志，用 session_id 区分不同用户请求。没有接 Prometheus / Grafana，没有上链路追踪。

这个方案在日均 100 问的体量下完全够用。出了问题就是 grep 日志，几分钟定位。对接监控平台的收益要等 QPS 上来了才能体现，现阶段属于过度工程。但面试时要把方案讲清楚。

---

**日志方案：分步骤打印耗时，session_id 串联**

每个 /ask 请求的处理过程中，在每个步骤完成后直接打印：

```python
logger.info(f"[{session_id}] rewrite cost={t1}ms")
logger.info(f"[{session_id}] embedding cost={t2}ms")
logger.info(f"[{session_id}] dual_search cost={t3}ms")
logger.info(f"[{session_id}] rerank cost={t4}ms")
logger.info(f"[{session_id}] llm_gen cost={t5}ms")
logger.info(f"[{session_id}] total cost={total}ms")
```

session_id 在请求入口生成（UUID），后续每一步都带上。不同用户的请求通过 session_id 区分，grep 一个 session_id 就能看到这个请求的完整链路耗时。

此外 QueryLog（SQLite，15 字段）记录了每次请求的完整信息——原始问题、改写后问题、召回结果、Rerank 后数量、端到端延迟、用户反馈。QueryLog 侧重"业务数据留痕"，分步骤日志侧重"性能定位"，两者互补。

设计原则：日志写入失败只记 warning、不抛异常——不能因为日志挂了影响主链路。

---

**为什么没对接监控平台**

三个原因：

1. **体量不匹配**：日均 100 问，靠日志手工排查完全够用。Prometheus + Grafana 的搭建和维护成本远超当前收益。

2. **告警价值低**：内部工具，不是 7×24 关键业务。延迟高了用户自然会反馈，不需要 3:00 AM 电话告警。

3. **排查链路短**：全链路在 FastAPI 进程内，调用关系简单。不像微服务有几十个服务间调用，没有分布式追踪根本不知道请求经过了哪些节点。

当 QPS 从日均 100 涨到日均 1000+、问题排查开始靠人力顶不住时，再上监控平台。路线是：先接 Prometheus 收指标（对接 /metrics 端点），再接 Grafana 做面板，最后加告警规则。但这些是"有了更好"而不是"现在就需要"。

---

**延迟飙升时的排查路径**

看到延迟异常，grep 最近的日志按 step 聚合看耗时分布：

1. **先看 llm_gen** —— 90% 是这里。内部 LLM API 被其他大请求抢了 GPU。确认：llm_gen cost 变大、其他步骤正常 → 锁定。

2. **看 rerank** —— GPU 排队也会让它慢。确认：rerank cost 是否异常。

3. **看 embedding** —— HTTP 网络抖动或排队。确认：embedding cost 是否异常。

4. **看 dual_search** —— HNSW 在 2000 chunk 下几乎不可能慢，但如果磁盘 I/O 被抢占会有尖刺。

5. **看请求量** —— 如果所有步骤都正常但端到端还是慢，可能是瞬时大量请求涌入导致 Uvicorn 请求队列积压。

核心思路：二分定位，先排 LLM（最大变量），再逐段排查检索链路。几次 grep + awk 就定位到了。

**Q28-附.** 如果要做主动监控（而不是被动查日志），应该监控哪些信息？每层的指标和告警阈值怎么定？

  当前没有接 Prometheus/Grafana，但如果要建一套有效的监控，不是把每个函数的耗时都暴露出去就完了——监控指标要按"出了问题你能不能第一时间知道是哪一层"来设计。我把整个系统拆成四层，每层应该暴露的指标和告警阈值如下。

  **第一层：基础设施层（LVS + FastAPI 进程）**

  这一层回答"系统还活着吗"。

  - 每个节点的 TCP 端口可达性（LVS 自带的健康检查）。端口不通 → LVS 自动摘除节点，不需要额外告警，但如果 4 个节点中 ≥ 2 个同时不通，说明不是单点故障，需要告警。
  - 每个节点的内存使用率和 CPU 使用率。内存持续增长 → 可能有内存泄漏（BM25 索引没释放、ChromaDB 连接没关）。阈值：内存超过 80% 持续 5 分钟 → 告警。
  - 磁盘使用率。ChromaDB persist 目录 + QueryLog SQLite 文件 + 日志文件，加起来不大，但如果日志没做轮转，磁盘可能被吃满。阈值：磁盘超过 85% → 告警。

  **第二层：检索链路层（每一步的耗时分布）**

  这一层回答"检索还快不快"。不需要监控每一次请求的耗时，而是按时间窗口聚合看 P50/P99。

  | 步骤 | 正常 P50 | 正常 P99 | 告警阈值 |
  |------|---------|---------|---------|
  | rewrite | ~100ms | ~500ms | P99 > 1s 持续 5 分钟 |
  | embedding | ~30ms | ~60ms | P99 > 200ms 持续 5 分钟 |
  | dual_search | ~5ms | ~15ms | P99 > 50ms 持续 5 分钟 |
  | rerank | ~100ms | ~250ms | P99 > 500ms 持续 5 分钟 |
  | llm_gen | ~400ms | ~2.5s | P99 > 5s 持续 5 分钟 |
  | 端到端 | ~635ms | ~3.3s | P99 > 5s 持续 5 分钟 |

  告警的意义不是"慢了就要修"，而是"慢了且持续慢"说明不是偶发的 API 抖动，是系统性问题。阈值的设定原则：取正常 P99 的约 2 倍，留足抖动余量，避免频繁误报。

  每个步骤的耗时在代码里已经有了——Q28 的分步骤日志已经在打了。加上 Prometheus client 只需要在每次 `logger.info` 旁边加一行 histogram 记录，不需要重新埋点。

  **第三层：检索质量层（召回和生成的正确性信号）**

  这一层回答"答案还对不对"。耗时正常不代表答案正确——LLM 可能幻觉了、检索可能漏召回了。

  - 答案空回率。LLM 返回"当前知识库未覆盖此问题"的比例。如果突然飙升，说明检索出了问题（chunk 丢了、索引损坏了）或者文档被人误删了。阈值：空回率 > 50% 持续 10 分钟 → 告警。
  - 用户点踩率。点踩数 / 总请求数。这是最直接的用户体验信号。阈值：点踩率 > 20% 持续 1 小时 → 告警。
  - 检索召回 chunk 数。Rerank 之后最终进入 LLM 的 chunk 数量。正常情况下 5 个。如果这个数字频繁为 0 或 1，说明 RRF 融合后基本没召回东西。不需要告警，但需要定期看分布。

  用户点踩率不需要接 Prometheus——直接在 QueryLog 上跑一个定时统计就行。当前没有自动统计，但实现成本极低：一个 cron 任务每小时扫一次 QueryLog，算 `user_click = 'dislike'` 的比例。

  **第四层：跨节点一致性层**

  这一层回答"4 个节点给的是同一个答案吗"。

  - 各节点 chunk 总数。健康检查端点已经暴露了这个值。4 个节点的 chunk_count 如果不一致，说明文档同步出了问题。阈值：任意两个节点 chunk 总数不等 → 告警。
  - 各节点 BM25 索引状态。BM25 对象是否已加载（启动后有没有重建成功）。健康检查端点加一个 `bm25_loaded: true/false` 字段。false → 告警。

  这层的监控最简单——不需要 Prometheus，健康检查端点本身就能暴露这些值，LVS 或一个外部 cron 定期 GET 即可。

  **务实的落地路径**

  当前阶段不接 Prometheus 是合理的（日均 100 问，日志排查够用），但这不意味着什么监控都不做。最轻量的方案是分三步走：

  1. **健康检查端点扩展**（当天可做）：在现有的健康检查端点里加 `chunk_count`、`bm25_loaded`，一个 GET 就能看到所有节点的关键状态。
  2. **QueryLog 定时统计**（写个 cron）：每小时扫一次 QueryLog，统计空回率、点踩率、请求量。超过阈值发企业微信/钉钉消息。不需要 Prometheus。
  3. **Prometheus + Grafana**（QPS 上千后再做）：暴露 `/metrics` 端点，收 histogram（各步骤耗时分布）+ counter（请求总数、空回数、点踩数）+ gauge（chunk 总数）。Grafana 做一个面板，一页看完所有层的状态。

  面试时如果被问"监控怎么做的"，可以分开答：当前阶段做了什么（健康检查 + QueryLog 统计），未来 QPS 上来后规划了什么（Prometheus 全量指标 + Grafana 面板），以及为什么现在没上（量级不匹配）。比"没做监控"和"全套 Prometheus 都上了"都要诚实和有说服力。

### 2.4 反馈 & 迭代闭环

**Q30.** 用户反馈怎么收集的？有点赞/点踩/修正吗？反馈数据怎么回到系统里？有没有形成数据飞轮？

**当前：有点赞和点踩，没有直接修正**

前端回答区域下方有"有用"和"没用"两个按钮。用户点踩后，反馈写入 QueryLog 的 user_click 字段。没有让用户直接修正答案的功能——让用户手动改答案的交互成本太高，内部用户没这个耐心。

除了前端按钮，还有一个间接反馈渠道：漏到人工群里才能解决的问题。这类问题说明系统没帮上忙，由人工记录后纳入 bad case。

**反馈怎么回到系统里——两条路径，同一个入口**

点踩和人工群反馈最终都汇入 QueryLog，但路径不同。

路径一（点踩）：用户在页面上点"没用"→ 前端将 user_click 回写到 QueryLog 对应记录。因为有 query_id，直接定位到当次请求。

路径二（人工群反馈）：用户在 RAG 没得到答案，转去群里问人。群里看到问题后，根据提问人的 user_id 去 QueryLog 搜索该用户最近的 /ask 记录，按问题文本相似度匹配到对应那次请求。人工群反馈本身不带 query_id，但 user_id + 问题内容可以做 join——找到当次日志后，就能回溯 rewrite、vector_hits、bm25_hits 等完整检索过程。聊天的 user_id 和系统登录的 user_id 是同一个企业账号，所以这个映射是直接成立的。

两条路径汇聚后，每两周汇总点踩记录和人工群反馈，逐条审核后标注 chunk ID 作为 ground truth，补充到离线评测集。因为 QueryLog 保留了每次检索的完整命中列表，点踩的记录直接查日志，人工群反馈则先通过 user_id 定位到日志再排查——不需要复现，回溯成本很低。

**基于 QueryLog 的 Bad Case 排查 SOP**

每两周汇总 bad case 时，不是简单地把问题扔进评测集就完了。要从 QueryLog 中逐字段排查根因，然后针对性修复。标准流程四步：

**第一步：拉数据。** 从 QueryLog 筛选 user_click="踩" 的记录，加上人工群反馈的问题（手动录入）。按时间倒序排列，优先处理最近的问题。

**第二步：逐字段定位根因。** QueryLog 的 15 个字段在这个环节的价值就体现出来了——不需要复现，直接看日志还原当时的完整检索过程：

- 看 `original_question` vs `rewritten`：改写是否正确？如果用户问"那个监控怎么配"，rewritten 变成了不相关的内容，说明映射表缺了这条映射，或者 LLM 改写跑偏了 → **改写问题**。

- 看 `vector_hits` 和 `bm25_hits`：两路各自召回了什么？如果正确答案的 chunk 不在任何一路的 top-5 里，说明是召回失败。进一步区分——如果正确答案含有关键词但 BM25 没召回，可能是 jieba 分词切错了 → **分词问题**。如果正确答案是语义相关但向量没召回，可能是 chunk 切得不好导致向量表示不准确 → **chunk 策略问题**。

- 看 `rerank_score`（如有）：Rerank 后的 top-5 里有没有正确答案？如果 vector 或 BM25 召回了正确答案，但 Rerank 把它排到 5 名之外了 → **排序问题**。

- 看 `src_vector` / `src_bm25` / `src_both`：正确答案来自哪一路？如果每次都是同一路（比如总是 BM25 贡献正确答案），说明另一路在同类问题上系统性失效 → **检索路权重问题**。

- 如果前面都正常——正确答案在 Rerank top-5 里，但 LLM 还是生成了错误答案 → **生成问题**（幻觉或 prompt 约束不够）。

**第三步：针对性修复。** 不同根因走不同修复路径，每种都有具体的操作步骤。

**类型一：改写问题（rewritten 把 query 带偏了）**

表现：original_question 意思清晰，但 rewritten 丢失了关键信息或替换成了错误术语。

修复途径：
1. 如果是因为"内部术语未映射"导致 LLM 不认识（比如用户说"那个蓝屏工具"，LLM 不知道是"BSOD诊断"）→ 在动态映射表中加一条映射关系，存到配置中心，调 reload 接口实时生效，不需要重启服务。
2. 如果是因为 LLM 改写本身跑偏（比如 query 里的数字被错误替换、否定词被忽略）→ 调 rewrite prompt，在 prompt 中加约束，比如"保留原文中的所有数字和否定词，不要改写"。Prompt 改完即生效。
3. 如果某类 query 反复被改写坏 → 排查是否为 prompt 的 few-shot 不够覆盖这类表述，考虑加一条针对性的改写示例。

验证方式：用同一条原始 query 重新请求，看 rewritten 是否变正确，再看后续检索结果是否改善。

**类型二：分词问题（BM25 没召回，但关键词明明在 chunk 里）**

表现：bm25_hits 里没有正确答案的 chunk，但手动搜 chunk 原文，发现关键词是存在的。

修复途径：
1. 把被切错的术语加到 jieba 自定义词库文件（一个纯文本，每行一个词），调 reload 接口重新加载，30 秒内生效。
2. 加词策略：不只是加"当前这一个"，而是顺带加同类的。比如发现"多AZ"被切成"多"+"AZ"，不仅加"多AZ"，还顺手加"单AZ"、"跨AZ"等同系列术语。
3. 词库文件的维护方式：放在 Git 仓库里，修改后 commit，FastAPI 的 reload 接口拉最新版本。这样有版本记录，不会出现"不知道谁加了什么词"。

验证方式：调 reload 后，用同一 query 重新走一遍 BM25 检索，看修正后的分词结果和召回结果。

**类型三：Chunk 策略问题（正确答案的 chunk 既不在 vector 也不在 BM25 的 top-5 里）**

表现：vector_hits 和 bm25_hits 都没有覆盖正确答案，但正确答案对应的 chunk 确实存在于库中。

修复途径：
1. 如果是 chunk 语义太碎——一个完整答案被切到了两个 chunk 里，各含一半信息，向量和 BM25 都匹配不上 → 调大 chunk size，比如从 384 调到 512。改的是切分配置参数，改完后需要全量重建索引（重新切分 → 重新 embedding → 重新入库），当前 500 文档约 2 分钟完成。
2. 如果是标题路径信息没打进去——chunk 内容是纯技术描述但没有上下文，检索时搜不到 → 检查 MarkdownHeaderTextSplitter 的输出，确认标题层级是否正确拼接到了 chunk content 头部。如果是拼接逻辑的 bug，修代码后重建索引。
3. 如果是 LLM 摘要没生效——一个表格或 JSON 配置块的摘要没生成出来，chunk 里只有原始数据没有自然语言描述 → 检查离线摘要生成脚本是否对这类特殊文本生效，修复后重新跑摘要生成 + 重建索引。

验证方式：重建索引后，用同一 query 走完整检索链路，看正确答案是否进入 RRF 融合后的候选列表。

**类型四：排序问题（正确答案召回了但 Rerank 把它排到了 5 名之外）**

表现：vector_hits 或 bm25_hits 里有正确答案，但 Rerank 后的 top-5 里没有它。

修复途径：
1. 如果是个别 case → 看 Rerank 为什么会把这个 chunk 排低。可能是因为 chunk 的语义和 query 在 cross-encoder 看来确实不够相关，根因在 chunk 的内容表述上（回类型三修复）。如果 cross-encoder 明显判断错误 → 这是一个模型 bad case，记录但暂时无法修复（cross-encoder 是内部模型，不可调参）。
2. 如果是系统性倾向——比如 BM25 召回的正确答案总是被 Rerank 排到后面，说明 RRF 融合时 BM25 路的权重偏低了 → 调大 RRF 的 β 参数（BM25 权重）。例如从 α=0.5, β=0.5 调成 α=0.4, β=0.6。参数在配置文件中，改了即生效，不需要重建索引。具体调到多少可以跑网格搜索——在评测集上 β 以 0.05 步长扫一遍，挑 MRR 最优的值。
3. 如果纠不回来 → 临时把 Rerank top-5 改成 top-8，给 LLM 更宽的候选范围，代价是多 3 个 chunk 的输入 token（约 1150 token）。改了即生效。

验证方式：如果是调参数，跑评测集的 MRR 看是否回升。如果是个别 case，用同一 query 重新检索看 top-5 里是否包含正确答案。

**类型五：生成问题（正确答案在 top-5 里，但 LLM 答错了）**

表现：检索结果正确，Rerank top-5 里包含正确答案，但 LLM 输出的答案仍然错误或编造了信息。

修复途径：
1. 如果 LLM 忽略了一个明显相关的 chunk 而用了另一个不太相关的 → 检查 prompt 中 chunk 的排列顺序。当前是按 Rerank 分数降序，但如果分数接近的两个 chunk，LLM 可能关注了后面的。在 chunk 拼接时加一个显式的"按相关性排序"提示。
2. 如果 LLM 编造了 chunk 里没有的信息（幻觉）→ 加强 system prompt 的约束，比如"如果你不确定，请说'文档中未明确说明'，不要推测"。同时检查 Q23 的四层幻觉防线中哪层失效了。
3. 如果某类问题反复生成错（比如配置值写成了旧版本）→ 在 few-shot 示例中加一条同类型的正确示例，让 LLM 学会这类问题的回答模式。改 prompt 中的 few-shot 区域，改完即生效。
4. 如果是知识库本身就有矛盾（两个文档对同一问题给出了不同答案）→ 这不是生成问题，是文档质量问题的上游输入。需要联系文档维护者修正源文档，短期处理可以在 prompt 中加冲突裁决规则——"当多个来源给出不同信息时，优先采用最近更新的来源"。

验证方式：同一条 query 重新生成，人工对比新旧答案。如果加了 few-shot，跑评测集确保其他类型问题没有退化。

**类型六：知识库覆盖问题（正确答案的文档根本不在库中）**

表现：QueryLog 显示检索链路一切正常，但正确答案就是不在任何召回结果里。人工确认对应的文档不存在。

修复途径：
1. 找到正确的源文档（Wiki / 人工群消息 / 同事提供）。
2. 按入库规范清洗格式、确认标题层级合理。
3. 走管理接口上传文档 → 自动切分 → embedding → 入库。
4. 上传后用这条 query 验证能否正确召回。

验证方式：文档入库后，用原始 query 走完整链路，看新文档的 chunk 是否出现在 top-5 中。

---

**排查优先级**：按概率排序——改写问题 > 分词问题 > 生成问题 > 排序问题 > Chunk 策略问题 > 知识库覆盖问题。前两类占了 bad case 的大头，修复成本也最低（改映射表/词库，实时生效），应优先排查。

**第四步：回流评测集验证。** 修复后，把这条 bad case 标注 chunk ID 后加入评测集。下次发版前跑全量评测时，这条 case 会被自动验证——如果修复有效，对应的指标（MRR / Recall@5）应该回升。如果没回升，回到第二步重新排查。

**数据飞轮：长期方案**

先澄清一个常见误解：长期方案不是"训练一个模型自动判断 bad case 然后全自动修"——以日均 100 问的反馈量，根本训练不出靠谱的分类器。真正的长期方向是：**用自动化把机械劳动全干掉，人的精力只花在"做判断"这一个动作上。** 同时让每条反馈产生尽可能多的下游影响，而不是只修一个 case 就完了。

下面分六个阶段讲清楚哪个环节能自动化、怎么自动化、哪个环节必须留给人。

**阶段一：评测集自动回归（当前可做，成本最低）**

这一步本质上是把 Q29 四步 SOP 的第四步自动化。当前每次修完 bad case 后，人工把它标注 chunk ID 加入评测集。下次发版跑评测时这些 case 会被验证。这个流程完全是确定性的，不需要任何 ML：

```python
# 自动化逻辑：每天凌晨拉前一天的所有点踩记录，检查是否已在评测集中
# 不在的自动入队、通知人工标注 chunk ID

def daily_feedback_triage():
    """每日反馈分诊 —— 自动拉取、去重、入队"""
    yesterday_pointdowns = query_log.query(
        "SELECT * FROM query_log WHERE user_click='踩' AND date(created_at) = date('now', '-1 day')"
    )
    
    for record in yesterday_pointdowns:
        question = record["original_question"]
        
        # 检查这个 question 是否已在评测集中
        if eval_set.contains(question):
            continue  # 已覆盖，跳过
        
        # 未覆盖 → 加入待标注队列
        pending_queue.add({
            "question": question,
            "rewritten": record["rewritten"],
            "vector_hits": record["vector_hits"],
            "bm25_hits": record["bm25_hits"],
            "querylog_id": record["id"],
            "status": "awaiting_chunk_label",
        })

    # 通知：企微/邮件通知负责人 "有 N 条新 bad case 待标注"
    notify(f"今日新增 {len(pending_queue)} 条待标注 bad case")
```

人工只需要做一件事：标注这条 bad case 的 ground truth chunk ID（哪些 chunk 包含正确答案）。标注完入评测集后，每次发版 CI 自动跑 MRR/Recall@5，这条 case 自动参与回归检查——人不需要记得它。

这个阶段就可以把"每两周人工汇总"变成"每天自动入队+人工标注"，时效从天级降到天级。

**阶段二：自动分诊——用规则而非模型预判根因类型**

当前 Q29 的四步 SOP 中，第二步"逐字段定位根因"是人对着 QueryLog 的 15 个字段逐一排查，非常机械。这部分可以自动化——六种根因类型中，前五种都有明确的 QueryLog 字段信号可以触发规则判断：

```python
def auto_triage(record: dict, eval_set_chunks: set) -> str:
    """
    基于 QueryLog 字段的规则分诊，不需要 ML
    
    Returns:
        "rewrite"  / "tokenize" / "ranking" / "generation" / "chunk" / "coverage"
    """
    # 规则 1: 改写信号 —— rewritten 和 original 差异过大
    if semantic_diff(record["original_question"], record["rewritten"]) > THRESHOLD:
        return "rewrite"
    
    # 规则 2: 分词信号 —— BM25 召回了 0 个结果，但 query 含中文关键词
    bm25_hits = json.loads(record["bm25_hits"])
    if len(bm25_hits) == 0 and contains_chinese_keywords(record["rewritten"]):
        return "tokenize"
    
    # 规则 3: 排序信号 —— 正确答案在 RRF 候选里但不在 Rerank top-5
    # （需要人工标注后才能判断，标注后自动标记）
    correct_ids = eval_set_chunks.get(record["original_question"])
    rrf_candidates = get_rrf_candidates_from_log(record)
    rerank_top5 = get_rerank_top5_from_log(record)
    if correct_ids and correct_ids & rrf_candidates and not correct_ids & rerank_top5:
        return "ranking"
    
    # 规则 4: 生成信号 —— 正确答案在 Rerank top-5 但 LLM 答错了
    if correct_ids and correct_ids & rerank_top5:
        return "generation"
    
    # 规则 5: 检索失败 —— vector_hits 和 bm25_hits 都没有正确答案
    if correct_ids and not (correct_ids & rrf_candidates):
        return "chunk"  # 或 "coverage"（需要进一步判断文档是否在库中）
    
    return "unknown"
```

规则分诊的准确率不会 100%，但它的目标不是替代人判断——而是**把人从"对着 15 个字段逐一查"的机械操作中解放出来**。人拿到分诊结果后，只需要确认或修正分类，然后按对应的修复 SOP 执行。

这个阶段的成本：写几十行规则代码 + 维护一个信号阈值参数。

**阶段三：自动修复可自动化的类型**

六种修复类型中，有两类的修复操作是确定性的，不需要人做判断：

**分词问题自动修：**

```python
def auto_fix_tokenize(record: dict):
    """分词问题的自动修复 pipeline"""
    question = record["rewritten"]
    
    # 1. 用 jieba 分词看当前切分结果
    current_tokens = list(jieba.cut(question))
    
    # 2. 用 jieba 的新词发现功能，识别可能的未登录词
    #    （基于互信息和邻接熵，jieba 自带此能力）
    new_words_candidates = jieba.analyse.extract_tags(
        question, topK=5, withWeight=False
    )
    
    # 3. 跨校验：这些候选词是否出现在文档库中但被切碎了？
    for word in new_words_candidates:
        if word_in_corpus(word) and word_not_in_dict(word):
            # 4. 生成 PR：自动加到 jieba 词库文件，提交 Git PR
            suggested_dict_entries.append(word)
    
    # 5. 通知人审核 PR（人只做"合并/拒绝"一个动作，不需要查分词）
    create_merge_request(
        file="data/jieba_dict.txt",
        additions=suggested_dict_entries,
        description=f"自动发现的新词候选（来源：bad case #{record['id']}）",
    )
```

**改写映射表自动补全：**

```python
def auto_fix_rewrite(record: dict):
    """当 rewritten 和 original 差异来自未知术语时，自动发现映射"""
    original = record["original_question"]
    rewritten = record["rewritten"]
    
    # 1. 提取 original 中的专有名词（不在通用词表中的词）
    original_terms = extract_domain_terms(original)
    
    # 2. 检查这些词是否在 rewritten 中被替换或删除
    for term in original_terms:
        if term not in rewritten:
            # 3. 在文档库中搜索这个 term 的上下文
            #    找到它可能对应的正式术语
            formal_name = search_formal_term_in_docs(term)
            if formal_name:
                suggested_mappings.append({
                    "slang": term,
                    "formal": formal_name,
                    "source_doc": formal_name_source,
                })
    
    # 4. 生成 PR：人审核后合并
```

这两类自动化的前提是：人已经确认了根因分类（阶段二的输出）。如果分诊错了（比如实际是 chunk 策略问题但被标记为分词问题），自动修复会产生无效改动。但无效改动的代价很低——加一个不需要的词到词典里，不会破坏已有功能，下次排查时发现没修复再人工介入即可。

**阶段四：评测集质量自动维护**

评测集会随着 bad case 不断追加而膨胀。100 条时人工全量看一遍没问题，300 条以后维护成本就上来了。需要两件事自动化：

**1. 自动去重 —— 语义相似的 bad case 合并**

```python
def deduplicate_eval_set(eval_set: list[dict], threshold: float = 0.92):
    """基于 embedding 相似度的评测集去重"""
    questions = [item["question"] for item in eval_set]
    embeddings = embed_batch(questions)  # 768-dim
    
    duplicates = []
    for i, j in find_high_similarity_pairs(embeddings, threshold):
        # 两个 question embedding 相似度 > 0.92，大概率是同一类问题
        # 保留标注更完整的那条，标记另一条为重复
        if eval_set[i].get("gt_chunk_ids"):
            duplicates.append(j)
        else:
            duplicates.append(i)
    
    return [item for idx, item in enumerate(eval_set) if idx not in duplicates]
```

**2. 自动老化 —— 超过 N 次评测连续通过且文档未变更的 case，降权**

评测集的维护成本会随着规模线性增长（500 条时跑一次 Faithfulness 的成本是 100 条的 5 倍）。不是所有 case 都需要每次发版都跑：

- 连续 5 次发版都通过的 case → 标记为 stable，只在重大变更时（模型换代/chunk 策略变更）重新验证
- 最近 30 天内新加入的 case → 标记为 active，每次发版必跑
- 被修复但未验证过的 case → 标记为 pending，发版时自动验证

这样把每次发版的评测量控制在 ~150 条（100 active + 50 new），而不是无限膨胀。同时 stable case 不会丢失——重大变更时还会重新验证。

**阶段五：缓存质量联动（和 Q21/Q23 联动）**

用户点踩不止是评测集的输入，还可以直接作用于线上服务：

```python
def on_user_pointdown(querylog_id: str, question: str):
    """用户点踩后的自动化联动流程"""
    
    # 1. 语义缓存失效 —— 如果这个问题命中了缓存，说明缓存的答案有问题
    similar_cached = semantic_cache.find_similar(question, threshold=0.85)
    for entry in similar_cached:
        if entry["answer"] == get_answer_from_querylog(querylog_id):
            semantic_cache.invalidate(entry["id"])
            # 注：不能直接删——如果用户点踩是因为漏了信息而不是答案错误，
            # 盲目删缓存会把一个"不完美但有用"的缓存答案删掉
            # 所以这里只标记为"待人工确认"，不是自动删除
    
    # 2. 如果同一类问题连续被点踩 ≥ 3 次 → 触发告警
    similar_pointdowns = query_log.count_similar_pointdowns(question, window_hours=24)
    if similar_pointdowns >= 3:
        alert(f"问题类型 '{extract_topic(question)}' 在过去 24h 内被点踩 {similar_pointdowns} 次，建议人工排查")

    # 3. 记录到反馈热力图 —— 按问题类型聚合，可视化哪些区域是重灾区
    feedback_heatmap.increment(extract_topic(question), "pointdown")
```

**阶段六（真正长期）：分层自动化，人的判断不可替代**

当反馈量达到一定规模（日均 500+ 问、月均 50+ 条 bad case），可以做三件事：

**1. 失败模式的统计显著性分析。** 当你有几百条已标注根因的 bad case 后，可以跑统计看：哪种根因占比最高？哪种根因的修复最耗时？哪种根因的复发率最高？——这些数据驱动优先级决策，而不是凭感觉说"改写问题最多"。这个不需要 ML，就是 SQL GROUP BY 加百分比的 dashboard。

**2. 自动发版决策。** 当前的标准是"L1 零回归 + L2 无确认的忠实度退化"。如果有持续半年的发版记录（每次发版的评测结果、人工决策、发版后是否出现线上事故），可以分析出：L1 和 L2 的哪些信号组合能可靠预测"发版不会出事"？然后逐步降低人工检查的范围——比如连续 10 次发版零事故后，L1+L2 全通过的常规发版自动放行，人工只看 L2 差异 > 0.3 的 case。

**3. 一个小模型做失败模式分类（仅分类，不判断质量）。** 当积累了几百条已标注根因的 bad case 后，可以训练一个小模型（比如用 text-embedding-v3 的 embedding + 轻量 MLP）做根因分类，替代阶段二的规则分诊。注意：这个模型只预测"这个 bad case 属于六类中的哪一类"，不判断"这个答案好不好"。判断答案好坏仍然靠人——因为人对内部知识库的理解比任何自动化指标都可靠。

**什么不做**

明确不做的三件事（防止过度设计）：

1. **不训练端到端的质量评分模型**——以几千条反馈训练出来的模型，泛化到新的问题类型时必然失效。与其维护一个有噪声的模型，不如让有限的反馈信号直接进入评测集和修复 pipeline。

2. **不做全自动修复闭环**——分词和改写映射这两类可以半自动（机器生成 PR → 人审核），但 chunk 策略调整、prompt 改动、Rerank 参数调整都是手动操作，因为每次改动的影响面太大，需要人的全局判断。

3. **不追求"用户无感修复"**——发现 bad case 后几分钟内自动修好听起来很酷，但在知识库场景下风险远大于收益。一个自动修改导致的系统性退化，比一个 bad case 多存活两天严重得多。

**总结：长期方案的核心理念**

不是"训练一个 AI 替代人做质量管理"，而是"把人的每一次判断的杠杆放大"——

```
当前:  1 条 bad case → 人排查 10 分钟 → 修 1 个 case → 加入评测集
阶段一: 1 条 bad case → 自动入队、人去重标注 → 修 1 个 case → CI 自动回归
阶段二: 1 条 bad case → 自动分诊 → 人确认分类 → 按 SOP 修 → CI 自动回归
阶段三: 1 条 bad case → 自动分诊 → 自动修复（特定类型）→ 人生成 PR →
        人审核合并 → CI 自动回归
阶段五: 1 条 bad case → 自动分诊 + 缓存联动 + 同类型聚合告警

人的工作量: 10 分钟 → 5 分钟 → 2 分钟 → 审核按钮 → 只看告警
杠杆率:     修 1 个   → 修 1 个 + 防回归 → 修 1 个 + 防同类 → 修 1 类 + 防线上复发
```

飞轮真正转起来靠的不是一次性技术突破，而是**每个阶段把人从机械劳动中解放出来一点，让人能专注于只有人才能做的判断——这个判断在当前规模下是最稀缺的资源。**

**为什么没有让用户直接修正答案**

三个原因：第一，内部用户不是标注人员，让他们手动编辑答案的门槛太高；第二，修正后的答案格式和质量不可控，不能直接入缓存或评测集；第三，我们更需要的是"这个答案对不对"的信号（点赞/点踩），而不是用户替我们写答案。点赞/点踩的信噪比高于自由文本修正。

**Q31.** 你们上线后效果怎么样？拦截率是多少？用户满意度提升了多少？每天节省了多少人天？这些数字是怎么统计的？

**先坦诚说：没有做严格的线上效果量化**

日均 100 问的量级下，做正式的 A/B 对比或统计显著性检验是不现实的——样本太小，置信区间太宽。当前的效果评估依赖三个间接信号，没有做对照组实验。

**拦截率：约 70%~80%**

拦截率定义为「用户没再转到人工群的比例」。统计方式：对比系统上线前后，人工群中知识类问题的数量变化。上线前，每天群里有约 30~40 条问题是"XX 怎么配置""YY 在哪里"，上线后这些基本消失了——因为用户能直接在系统里搜到答案。

但 70%~80% 这个数是估算，不是精确统计。因为不知道有多少用户是"搜到了答案所以没来群里问"，也没法统计"用户搜了但没搜到、放弃了、也没去群里问"。精确拦截率需要追踪每个用户的完整行为链路（搜索 → 看结果 → 是否自行解决 → 是否转人工），当前 QueryLog 只记录 /ask 请求，不记录用户后续行为。

更准确的说法是：人工群中可被系统覆盖的问题减少了约 70%~80%。不能拍胸脯说"系统拦截了 80% 的问题"。

**用户满意度：点赞率约 85%~90%**

来源是 QueryLog 的 user_click 字段。统计逻辑：有点赞或点踩记录的请求中，点赞占比。没有点赞也没有点踩的请求不参与计算（用户可能看了答案就走了，不代表不满意）。

贴一个真实数字需要注意的点：点赞率有自选择偏差。用了觉得好的人更倾向于点赞，用了觉得一般的人可能直接关页面，不点任何按钮。所以 85%~90% 是"在有反馈的用户中"，不是全体用户。全体用户的满意度只会更低，但低了多远，我们没有数据。

**节省人天：约 0.5 人天/天**

计算方式：上线前，oncall 人员每天处理约 20~30 条可被系统回答的知识类问题，每条平均耗时 5~10 分钟（理解问题 → 查文档 → 组织回复 → 粘贴到群里）。取中位数：25 条 × 7.5 分钟 ≈ 3 小时 ≈ 0.4 人天/天。加上一些原本"懒得查文档、随便回"的低质量回答被系统标准化答案替代，综合估算约 0.5 人天/天。

这个数的局限：第一，不是所有被系统回答的问题原来都会问到人——部分用户有了系统后才开始问（以前可能懒得去群里问），所以省掉的人天不是简单地从群里扣除。第二，0.5 人天/天不能直接换算成"少招半个人"，因为 oncall 的工作是碎片化的，省下来的 3 小时可能被其他事务填充了。节省更多体现在响应速度上（用户不用等群里回复），而不是人头数上。

**这些数字怎么严谨化**

如果面试官追问"你怎么证明这些数字不是编的"，我的回答分两步：

1. 短期可做的：QueryLog 加一个字段 `user_went_to_manual`，前端在用户看完答案后加一个隐式追踪——如果用户复制了答案文本、或者短时间内没有点人工群入口，标记为"自助解决"。这个信号比点赞/点踩覆盖更全，能给出更准的拦截率。

2. 长期才能做的：AB 实验。随机分 50% 用户看到系统答案、50% 用户只能搜文档标题（不下线系统，只是降级为检索模式），对比两组用户转人工群的比例。但这需要更大用户量才有统计显著——日均 100 问，分两组后每组 50，差异很难排除噪声。

坦诚说，在当前规模下，效果的定量证据有限。但定性证据是明确的——内部群里的知识类提问大幅减少、用户反馈正面、oncall 同学说"终于不用重复回答同样的问题了"。对于内部工具来说，这已经足够说明价值。

**Q32.** 线上出了 bad case 你怎么发现？怎么复盘？怎么修？从发现问题到修复上线，整个流程是什么样的？能给一个具体案例吗？

**发现渠道有两个**

1. **QueryLog 点踩记录**：每两周拉一次 user_click="踩" 的记录，逐条看。
2. **人工群反馈**：用户搜不到答案、或者答案明显错了，最终还是会转到人工群里问。这类问题优先级更高——说明系统不仅没帮上忙，还逼用户绕了弯路。定位方式是先看提问人的 user_id，去 QueryLog 搜索该用户最近的 /ask 记录，用问题文本做语义匹配找到对应那条日志。

两个渠道覆盖了"用户主动投诉"和"用户默默放弃"两种场景。

**从发现到修复的标准流程**

四步闭环，和 Q29 的 SOP 一致：

**发现** → 从 QueryLog 拉点踩记录，或从人工群收到反馈。

**复盘定位** → 打开 QueryLog 对应记录，看 original_question、rewritten、vector_hits、bm25_hits、src 分布，按 SOP 定位根因（改写/分词/Chunk/排序/生成/覆盖）。

**修复** → 根据根因类型执行对应修复动作。最常见的两类（改写和分词）改配置即可实时生效，不需要重建索引或重新部署。

**验证** → 用原始 query 重新请求，确认结果正确。然后把这条 case 标注 chunk ID 后加入评测集，下次发版跑全量评测时自动验证不会退化。

---

**具体案例：BM25 分词错误导致召回失败**

**发现**：两周一次的 QueryLog 审查中，发现一条 user_click="踩" 的记录。original_question 是"多AZ部署的region白名单怎么配"，用户点了没用。

**复盘定位**：

1. 打开 QueryLog，先看 rewritten："多AZ部署的region白名单怎么配"——改写正确，没有丢信息。改写环节排除。

2. 看 vector_hits：top-5 里有两个 chunk 提到了 region 白名单，但没有一个提到"多AZ"。向量路召回了语义相关的内容，但不是最相关的。

3. 看 bm25_hits：top-5 里都是"region 白名单"相关的 chunk，但同样没有多AZ相关的内容。这说明 BM25 也召回了 region 白名单，但忽略了"多AZ"这个关键词。

4. 看 src 分布：src_vector 和 src_bm25 都命中了 region 白名单相关 chunk，但正确答案（"多AZ region 白名单配置"那个 chunk）不在任何一路的 top-5 里。

5. 手动查那个正确 chunk 的原文，发现确实存在，标题是"多AZ部署 - Region白名单配置"。那为什么 BM25 没召回？用 jieba 手动分词"多AZ部署"——结果被切成了 `['多', 'AZ', '部署']`，"多AZ"被拆开了。BM25 索引里存的是"多AZ"作为一个 term 的 IDF 和 DF（词典中），以及各 chunk 的 TF（doc_freqs 中），但 query 分出来的却是"多"和"AZ"分别查，两个高频词的 IDF 都很低，匹配分数被稀释了。

根因确认：**分词问题**——"多AZ"不在 jieba 自定义词库中。

**修复**：

1. 在 jieba 自定义词库文件中加一行 `多AZ`。
2. 顺手加了同系列的 `单AZ`、`跨AZ`、`多地域`，避免同类问题反复出现。
3. 调 FastAPI 的 jieba reload 接口，重新加载词库，实时生效，不用重启服务。
4. 用原始 query 重新走了一遍 BM25 检索，确认"多AZ"没有被拆开，正确 chunk 进入了 top-5。再跑完整链路，LLM 生成的答案正确，附带了引用。

**验证和闭环**：把这条 case（query + 正确的 chunk ID）加入评测集。下次发版跑全量评测时，这条 case 的 Recall@5 和 MRR 会自动检验分词修复是否退化。

**时间线**：从发现到修复完毕，整个过程约 15 分钟——5 分钟定位 + 2 分钟加词库 + 1 分钟 reload + 5 分钟验证 + 2 分钟更新评测集。

**Q33.** Embedding 模型、rerank 模型、生成模型，你有定期微调或者更新的计划吗？用什么数据更新？怎么保证更新后不退化？

**先解释两个概念：模型切换 vs 微调**

**模型切换**指的是平台侧上线了一个新版本模型（比如 text-embedding-v3 升级到 v4、DeepSeek V4 升级到 V5），我们需要决定要不要把系统里的模型名称从 `v3` 改成 `v4`。动机通常是三个：新版本效果更好（公开 benchmark 更高）、延迟更低（同效果下推理更快）、或者旧版本要下线了（平台不再维护，被迫切）。切换的成本是一行配置修改 + 跑评测验证。

**微调（Fine-tune）** 指的是拿一个已经训练好的通用模型（基座模型），用自己的领域数据再训练一轮，让模型在你的特定任务上表现更好。比如通用的 text-embedding-v3 在公开中文上表现好，但在内部术语（"OA""多AZ""优化顾问"）上可能不够敏感——微调就是让它对这些内部术语更敏感。微调的成本是：准备几千条标注数据 + 租 GPU 跑训练 + 部署微调后的模型实例。

两者的区别：模型切换是"换一个更好的现成模型"，不改变模型本身的权重；微调是"把现成模型改造成自己的版本"，改变了模型权重。我们当前只做得了前者。

---

**当前：没有微调计划，模型全部走内部 API**

三个模型都在内部统一 API 后面，模型实例的升级和版本管理由平台团队负责，我们调的是 API 不是模型权重。这意味着两件事：第一，我们没有做 fine-tune 的条件——训练数据、GPU 资源、模型权重都不在我们这边；第二，我们的优化方向不在模型层，而在检索链路的其他环节（改写、分词、Prompt、chunk 策略）。

但这不意味着我们对模型更新没有发言权。当内部平台上线新版本模型时（比如 text-embedding-v3 → v4），我们需要决定"要不要切过去"。这个决策需要一套验证流程。

**新模型版本的切换流程**

**第一步：离线评测。** 在评测集上并行跑旧模型和新模型。Embedding 升级需要全量重建索引（2000 chunk 重新 embedding），跑 100 条 QA 对比新旧 MRR 和 Recall@5。Rerank 或 LLM 升级不需要重建索引，只替换对应环节，跑对比即可。关键约束：Embedding 切换的评测成本约 2 分钟 + 百万 token 的 embedding 调用。

**第二步：差异 case 人工审查。** 不只看汇总指标。新旧评分差异超过 10% 的 case 逐条人工对比——确认新模型是"更好"还是"不同但没有更好"。有时新模型 MRR 整体更高，但对某类特定问题反而退化（比如专业术语的检索变差），这种 tradeoff 必须人工判断能不能接受。

**第三步：灰度切换。** 评测通过后，先在配置中切 20% 流量到新模型（通过配置中心的模型名参数控制），跑一周。对比新老两组 QueryLog——延迟有没有恶化、点赞率有没有下降。确认无退化后全量切换。旧模型索引保留一周做回滚兜底。

**用什么数据评估**

就是同一套 100 条 QA pairs 评测集（Q13）。评测集的核心价值在这里体现——它不仅是发版前的质量门槛，还是模型升级时的对比基准。当前局限：100 条跑检索评测够用，但如果要精细对比两个 LLM 版本的生成质量差异，可能需要扩展到 200~300 条才能统计显著。

**为什么不做 fine-tune**

三个原因。第一，**数据不够**：fine-tune 至少需要几千条高质量 (query, answer) 对，当前 100 条评测集 + 线上反馈远远不够。第二，**维护成本高**：微调后模型需要独立部署和维护，出问题的排查门槛比调 prompt 高一个数量级。第三，**Prompt engineering 的边际收益更大**：在日均 100 问的量级下，优化 prompt、扩充 few-shot、调整映射表和分词词库的投入产出比远高于微调模型。微调的价值要在 QPS 和标注数据都上量后才能体现。

**微调大致怎么做（附：帮你面试时讲清楚）**

微调不是从头训练一个模型，而是在基座模型的基础上用领域数据"精修"。以 LLM 为例，标准流程分四步：

1. **准备数据**：收集一批高质量的 (instruction, response) 对。instruction 是用户问题，response 是期望的标准答案。数据来源可以是 QueryLog 中点赞多的回答、人工标注的 QA、或者用更强的模型（如 GPT-4）生成一批答案再由人工审核。规模至少几千条，且要覆盖不同问题类型，不能全是同一类问题。

2. **选微调方式**：通用的做法是 LoRA（Low-Rank Adaptation），不修改原模型的所有参数（全量微调太贵了），而是在模型旁边挂一个小矩阵，只训练这个小矩阵。训练完成后，推理时把小矩阵和原模型合并，效果接近全量微调但 GPU 成本降低 90% 以上。现在主流框架（LLaMA-Factory、HuggingFace PEFT）几行代码就能跑。

3. **训练**：把数据喂给模型，让模型在领域数据上学习——本质上就是让模型"背"你的领域知识和回答风格。Embedding 模型的微调更简单：给一对对的 (query, positive_doc, negative_doc)，让模型学会拉近 query 和正确文档的距离、推远和错误文档的距离。

4. **评估和部署**：微调完后在评测集上对比微调前后的指标（MRR / Faithfulness），确认有提升且没有退化。通过后把微调模型部署到一个独立的 API 端点，业务代码里把模型名切过去。

坦诚说，这一步离我们还很远。当前先靠 Prompt engineering 顶着，等数据积累够了再考虑。

### 2.5 线上评测 & A/B 实验

**Q34.** 你有做在线 A/B 实验的能力吗？怎么分流量？怎么衡量实验效果？有没有指标体系？核心指标和护栏指标分别是什么？

**当前：没有做在线 A/B**

日均 100 问，样本量太小，在线 A/B 的统计显著性是做不到的。但不做不等于不会。面试时一定要把方案讲清楚——证明你有这个意识，只是规模没到。

**在线 A/B 和离线评测的本质区别**

离线评测（Q13/Q14/Q15）回答的是"检索/生成质量变好了吗"，用的是一批固定的、标注过的 QA pairs。在线 A/B 回答的是"用户实际体验变好了吗"，用的是真实用户的行为数据。

两者的结论可能不一致。举个例子：离线评测显示新的 chunk 策略 MRR 提升了，但在线一看，点赞率反而下降了——因为新策略虽然检索更精准，但 chunk 更短导致 LLM 答案不完整，用户觉得"不够详细"。这种矛盾只有在线 A/B 才能发现，离线评测看不到。

**如果要做，方案分四步**

**第一步：分流量。** 核心原则是按 user_id 做一致性哈希，保证同一个用户始终落在同一组——不会出现用户 A 第一次看到新版本、第二次看到旧版本。具体：取 user_id 的 hash 值，模 100，0~49 进对照组（旧版本），50~99 进实验组（新版本）。五五分。

这里的一个陷阱：不能按 IP 分，也不能按 session 分——同一个用户可能换 IP、同一 IP 可能多个用户。按 user_id 分才能保证用户级别的一致性。如果系统没有用户登录（匿名访问），那退一步用浏览器 fingerprint 或 cookie。

**第二步：确定指标体系。** 指标分两类——核心指标和护栏指标。

核心指标是你想要提升的东西，实验成功与否看它：
- 用户点赞率（user_click="赞" 的比例）
- 答案采纳率（用户复制答案文本、没有再搜索的比例，需要前端埋点）
- 转人工率（看完答案后点了"联系人工"的比例）

护栏指标是你不能让它退化的东西，如果恶化了实验必须终止：
- 端到端 P95 延迟（不能因为新策略变慢）
- 错误率（5xx 的比例不能上升）
- 空结果率（"未找到相关信息"的比例不能暴涨）

核心指标决定"新版本好不好"，护栏指标决定"新版本能不能上"。即使核心指标提升了，只要护栏指标有一条明显退化，实验也必须暂停。

**第三步：跑实验，等样本量够。** 这是在线 A/B 最难的部分——要跑多久才有统计显著性？

统计显著性的粗略判断：点赞率从 85% 提升到 90%，在 95% 置信度、80% 统计功效下，每组至少需要约 500 个有反馈的样本（不是 500 次请求，是 500 次点赞或点踩）。如果日均 100 次请求、约 30 次有反馈，每组需要跑约 17 天。这也是为什么当前不做——数据量支撑不了快速迭代。

**第四步：实验结束后决策。** 如果核心指标显著提升、护栏指标没有退化 → 全量上线新版本。如果核心指标没变化 → 本次实验没有结论，新版本和旧版本效果无差异，是否上线看其他因素（代码更简洁、维护成本更低等）。如果护栏指标退化了 → 不管核心指标怎么样，实验终止，回退到旧版本。

**一个常见的面试追问：你和离线评测结果矛盾了怎么办**

离线评测说新版本更好（MRR 涨了），但在线实验说用户点赞率没变化甚至下降。排查方向：第一，离线评测集是不是和线上分布不一致？如果评测集 80% 是高频问题，但线上长尾问题占了 50%，那离线评测的"好"只是高频问题的好。第二，指标本身是不是有问题？MRR 提升但点赞率不变，说明检索更精准了不等于用户更满意——可能是答案的完整度、可读性、排版出了问题。第三，实验本身设计是否有问题？比如两组用户不完全随机（新用户全进了实验组），导致组间 baseline 不一致。

**Q35.** 更新了一个新的切片策略，你上线前怎么验证不会引入退化？上线后怎么监控？如果变差了怎么自动回滚？做到自动化了吗？

**切片策略变更的特殊性**

切片策略不像改 prompt 或改映射表——改了立刻生效、不用重建任何东西。切片策略一变，所有 chunk 的边界都变了，必须全量重建索引（重新切分 → 重新 embedding → 重新入库）。这意味着两件事：第一，验证必须在上线前充分做，上线后再发现问题就晚了；第二，回滚不是"改回参数"就行，是要把旧索引重新加载回来。

**上线前验证：离线评测是唯一的防火墙**

因为要全量重建，不能在线上旧索引上直接改——删了旧的才发现新的有问题，线上就挂了。做法是在同一个 ChromaDB 里新建 collection，新旧并存，验证完再切。步骤：

1. **用新策略建一个新 collection**：不对线上旧 collection 做任何操作。新建一个 collection（如 `docs_v2`），对全量 500 文档用新切分配置跑一遍切分 + embedding + 入库。耗时约 2 分钟。同一套环境，新旧两个 collection 并存，互不影响。

2. **跑全量检索评测**：在新索引上跑 100 条 QA pairs，输出新旧两版对比。核心看两个指标——MRR 和 Recall@5。同时看有没有之前能召回的 case 在新策略下完全召不到了（Recall 归零的 case）。

3. **跑 RAGAS Faithfulness 相对比较**：检索没问题不代表生成没问题。用新索引的 top-5 chunk 跑全量 100 条 QA，新旧两版各跑一遍 RAGAS Faithfulness，看相对变化方向（详见 Q15）。因为 chunk 变了，LLM 拿到的是不同粒度的上下文——可能检索更准但 chunk 太碎导致 LLM 信息不完整而产生幻觉。Faithfulness 相对旧版下降超过 5% → 排查。

4. **Edge case 人工抽查**：不只看均值。重点看两类 case——评测分数差异超过 10% 的（搞清是不是退化）、以及之前能正确回答但现在不能的（搞清根因）。

5. **通过标准**：两项检索指标不能有统计显著的下降（均值跌了但差异 case 逐条看确认不是退化也算过），RAGAS Faithfulness 相对旧版不降（降幅 > 5% 则排查），不能出现之前能回答正确、新策略下完全回答错误的 case（数量 > 0 条就要排查）。

**上线方式：新旧索引并行，不是直接替换**

不是一个 deploy 命令把线上旧索引删了换新的。标准操作是：

1. 在 ChromaDB 中新建一个 collection（比如 `docs_v2`），把新策略的索引建在里面。旧 collection（`docs_v1`）保持不动，继续服务线上流量。

2. 在 FastAPI 配置中加一个 `active_collection` 参数，当前指向 `docs_v1`。

3. 改配置 `active_collection = docs_v2`，重启 FastAPI（或热加载配置）。因为每个节点有自己的 ChromaDB 数据文件，新 collection 需要在所有节点上都建好——管理员通过管理接口逐个触发，或用一个脚本批量调 4 个节点的重建接口。全部节点重建完毕后切换配置，4 个节点同时生效。

4. 观察一段时间（至少覆盖一个完整工作日），确认无退化后，再删掉旧 collection。

如果发现退化：`active_collection` 改回 `docs_v1`，秒级回滚。旧索引一直在那里没被删，不需要重新构建。

**上线后监控：看三个信号**

1. **延迟**：chunk size 变了，Rerank 和 LLM 的输入 token 数会变。P95 延迟不能明显恶化。来自分步骤日志。

2. **点赞率**：上线后当天的点赞/点踩比例，和上线前一周的均值对比。如果点踩率突升，立即排查。来自 QueryLog user_click。

3. **转人工率**：如果新的切片策略导致某类问题召回失败，用户会转人工群。上线后几天内人工群的问题量是否异常上升。

**回滚：手动操作，没有自动化**

回滚就是上面说的——`active_collection` 切回旧 collection。但为什么没有做自动化？因为自动回滚需要一个"好坏"的判断标准，而这个标准很难量化成一条规则。是延迟涨了 100ms 就回滚？还是点踩率涨了 5% 就回滚？还是某个特定 query 答错了就回滚？如果没有明确的触发条件，自动回滚要么反应过度（正常波动触发回滚），要么反应不足（退化已经持续了很久还没触发）。

当前做法是：上线后人工观察一天，没有异常就算稳定。这不够"自动化"，但在日均 100 问的量级下，一天内产生的数据足够判断好坏，且人工判断可以权衡多个信号（延迟、点赞、转人工的交叉分析），比单一阈值规则更准。如果未来 QPS 上来了、切片变更频繁了，再考虑加自动回滚——触发条件不是单一指标阈值，而是"两个以上护栏指标同时恶化超过 N%"的复合条件。

**各层技术栈和选型理由**

**接入层 —— FastAPI + Uvicorn，4 实例。** 无状态设计，请求可以落到任意实例。选 FastAPI 而不是 Flask 或 Django：对 SSE 流式响应有原生支持（`StreamingResponse`），异步架构天然适合我们这种 I/O 密集型链路（频繁调内部 API 等待响应）。Django 太重，Flask 做 SSE 需要额外折腾。Uvicorn 做 ASGI server，4 台机器各一个实例，LVS 在前面做四层负载均衡（TCP 轮询）。

**在线检索层 —— 7 步串联（详见 Q17）。** 每一步的选型理由：改写走映射表 + LLM 两层而非纯 LLM（映射表保证专有名词不丢）；Embedding 走内部 HTTP API；双路检索中向量走 ChromaDB HNSW、BM25 走 jieba + 自建索引（简单可控）；融合选 RRF 而非线性加权（量纲不同）；Rerank 选 Qwen3-rerank cross-encoder 而非 LLM-based rerank（低延迟、低成本）；生成选 DeepSeek V4 Flash 而非 Pro（成本优先）；QueryLog 选 SQLite 而非 MySQL（零运维，2000 条记录无需数据库服务）。

**数据层 —— ChromaDB + 内存 BM25 + SQLite。** ChromaDB 存向量和元数据，选它的理由见 Q7（六方案对比，综合代价最低）。BM25 索引在内存中构建和查询，启动时从 ChromaDB 读 chunk 原文自动重建，不依赖外部搜索引擎。QueryLog 用 SQLite 本地文件，不需要起数据库服务。

**离线构建层 —— 管理员触发，单人操作。** 文档处理走 LangChain MarkdownHeaderTextSplitter 做语义切分 + LLM 生成特殊文本摘要。向量化走和在线同一套 text-embedding-v3。索引构建完成后通过 `active_collection` 配置指针切换上线。评测走三层框架：L1 检索评测（MRR/Recall@5）+ L2 RAGAS Faithfulness 相对比较 + L3 触发式人工验证。

**选型贯穿的一条线**：在满足功能的前提下，尽可能降低外部依赖。整个系统除了内部 LLM API，没有任何外部服务——没有 Redis、没有消息队列、没有独立的搜索引擎、没有独立的数据库服务。ChromaDB 嵌入在 FastAPI 进程内（PersistentClient），BM25 索引在内存中自建，QueryLog 用 SQLite 本地文件。这不是因为"不知道这些技术"，而是因为在 500 文档、日均 100 问的规模下，引入任何外部服务的运维成本都超过它带来的收益。

```python
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",   # LVS 四层转发，无 HTTP 缓冲；此 header 为兼容预留
        }
    )

async def _generate_stream(session_id: str, question: str):
    try:
        # 1. Query 改写
        rewritten = rewrite_query(question)
        yield _sse("status", {"step": "rewrite", "query": rewritten})

        # 2. 双路检索 + RRF + Rerank
        results = retrieve_and_rerank(rewritten)
        yield _sse("context", {
            "chunks": [{"file": r["file_name"], "text": r["text"][:120]}
                       for r in results]
        })

        # 3. LLM 生成 —— 流式逐 token 输出
        full_answer = ""
        async for token in llm_stream_generate(question, results):
            full_answer += token
            yield _sse("token", token)

        # 4. 写 QueryLog
        write_querylog(user_id, session_id, question, rewritten, results, full_answer)
        yield _sse("done", {})

    except Exception as e:
        yield _sse("error", str(e))

def _sse(event_type: str, data) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event_type}\ndata: {payload}\n\n"
```

**SSE 事件类型和前端处理**

| 事件 | 携带数据 | 前端动作 |
|------|---------|---------|
| `status` | 当前步骤描述 | 展示进度（"正在改写..."） |
| `context` | 检索到的 chunk 列表 | 展示来源文档 |
| `token` | 单个文本片段 | 逐字追加到答案区 |
| `sources` | 引用列表 | 末尾展示引用链接 |
| `error` | 错误信息 | 展示错误提示 |
| `done` | 结束标记 | 关闭连接 |

前端用 `fetch` + `ReadableStream` 接收：

```javascript
fetch("/ask", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question: "OA告警阈值怎么配" })
}).then(response => {
    const reader = response.body.getReader();
    const decoder = new TextDecoder();
    function read() {
        reader.read().then(({ done, value }) => {
            if (done) return;
            // value 是 "event: token\ndata: xxx\n\n" 格式，按行解析
            parseSSEAndRender(decoder.decode(value));
            read();
        });
    }
    read();
});
```

**为什么选 FastAPI 而不是 Flask**

| | FastAPI | Flask |
|---|---|---|
| 异步支持 | 原生 async/await（Starlette） | Flask 2.0+ 支持但生态不完善 |
| SSE | `StreamingResponse` 开箱即用 | 需手动构造 generator |
| 请求校验 | Pydantic，类型自动检查 | 手动 `get_json()` + 手写校验 |
| 自动文档 | Swagger UI 自动生成 | 需额外装插件 |
| 性能模型 | ASGI，异步 I/O 不阻塞 | WSGI，同步模式效率低 |
| 生态 | 较新，插件还在长 | 十几年，什么插件都有 |

选 FastAPI 的核心原因：链路中大量 I/O 等待（调 Embedding HTTP API、等 LLM 流式输出），异步模型下 await 不会阻塞整个 worker。SSE 流式是核心体验——用户看到逐字渲染而不是等 3 秒一次出结果，`StreamingResponse` 让这一步非常简洁。

**SSE vs WebSocket**：SSE 单向推送（服务端 → 客户端），基于 HTTP，实现简单。WebSocket 双向通信，需握手升级协议，适合聊天类交互。RAG 问答是"一问一答流式返回"，SSE 完全够用。

**Q37.** 你这个系统最复杂的技术难点是什么？是检索、生成、工程、还是数据？你个人解决了其中最难的什么问题？

**最复杂的技术难点：混合检索的端到端调优**

不是说某个单一模块（比如 HNSW 或 BM25）本身有多复杂，而是"把几个模块串起来后，调出一个整体最优的效果"这个过程。

具体说：向量检索、BM25、RRF 融合、Rerank 精排——四个环节各有参数（HNSW 的 ef_search、BM25 的 k1/b、RRF 的 α/β/k、Rerank 的 top-k），每个参数改动都会影响最终的 MRR 和 Recall@5。问题是它们之间不是独立的——调大 Rerank 的 top-k 可以弥补 RRF 的排序缺陷，但也可能引入噪声让 LLM 生成质量下降。单独调一个参数容易陷入局部最优，全局搜索又因为 embedding 是整个链路里唯一耗时的步骤（其他环节的评估在已有 embedding 上重算即可），所以合理的做法是先固定 embedding 跑全量评测，再在剩余参数空间里做网格搜索。

这里面最花时间的不是"想方案"，而是"验证方案"——每次改参数跑 100 条 QA 看指标变化，然后再人工抽查差异 case 确认不是噪声。循环几次才能收敛到一个满意的配置。这个过程没有银弹，就是反复实验 + 人工判断。

**我个人解决的核心问题**

不是某一个具体 bug，而是两件事：

第一，搭了从零到一的评测框架。在没有任何标注数据的情况下，自己从线上群聊里收集真实问题、标注 chunk ID、分层抽样构建了 100 条 QA pairs。然后设计了按问题类型拆组的评测指标（单答案型用 MRR、综合型用 Recall@5），让评测不再是"跑一个数字"而是"不同问题分别看"。这个框架成了之后所有决策的基础——chunk size 选型、Rerank 消融实验、RRF 参数调优、模型切换验证，全部依赖它。

第二，做了每个关键环节的消融实验。不是凭经验说"加了 Rerank 肯定好"，而是跑了对照组——不加 Rerank vs 加 Rerank，数字摆出来（MRR 0.831 → 0.868）。同样的方法论用在 chunk size 选型、RRF 参数搜索上。这给面试官展示的不只是"我们做了 Rerank"，而是"我知道 Rerank 贡献了多少、值不值它的延迟代价"。

## 五、附录：工程实现细节

**Q46. 你的 chunk ID 是怎么设计的？ChromaDB、BM25、HNSW、SQLite 之间的 chunk ID 对应关系是什么？怎么保证两路检索结果能正确去重合并？**

**chunk ID 的唯一源头**

所有 chunk ID 只在 `document_processor.py` 的 `process_documents()` 中生成一次：

```python
chunk_id = f"{file_path}_chunk_{i}"
# 例如: "data/oa_monitor.md_chunk_0"
```

这个 ID 生成后流入所有下游系统，全程不变。不存在"ChromaDB 有一个 ID、BM25 有另一个 ID"的情况——**同一个 chunk 在所有组件里用的是完全相同的 ID 字符串**。

**四条路径，同一个 ID**

```
                document_processor.py
                chunk_id = "data/oa_monitor.md_chunk_0"
                       │
      ┌────────────────┼────────────────┬─────────────────┐
      ▼                ▼                ▼                 ▼
 ChromaDB          BM25 (内存)      RRF 融合         QueryLog (SQLite)
 collection.add()  chunks[idx]     item["id"]       vector_hits
 ids=[chunk_id]    ["id"]          做 join key      bm25_hits
```

**ChromaDB 内部：chunk ID 就是主键**

ChromaDB 底层也是 SQLite（路径 `data/chroma_db/chroma.sqlite3`）。`collection.add(ids=[...])` 传入的 id 直接成为内部表的主键：

```
ChromaDB 内部 SQLite 表结构（简化）:
┌──────────────────────────────┬─────────────────────┬──────────────────────┐
│ id (TEXT PK)                 │ embedding (BLOB)    │ document (TEXT)      │
├──────────────────────────────┼─────────────────────┼──────────────────────┤
│ data/oa_monitor.md_chunk_0   │ [0.023, -0.11, ...] │ "OA 监控告警配置..." │
│ data/oa_monitor.md_chunk_1   │ [0.041, 0.09, ...]  │ "告警阈值设置建议..." │
│ data/region_whitelist.md_... │ [-0.03, 0.15, ...]  │ "Region 白名单配置..."│
└──────────────────────────────┴─────────────────────┴──────────────────────┘
```

HNSW 图节点不存字符串——它存的是指向内部 rowid 的整数指针，rowid 再映射到 id 列。所以：

> **HNSW 节点 ↔ ChromaDB SQLite 行 ↔ 你的 chunk_id 字符串 —— 三者指向同一个 chunk。**

检索时 `collection.query()` 返回的 `results["ids"][0]` 就是这些 id 字符串，所以向量路的检索结果天然带着 chunk_id。

**BM25 不存 ID，用位置索引间接关联**

BM25 用的是 `rank_bm25.BM25Okapi`，它是一个**正向索引**（不是倒排索引），内部用列表存所有文档的分词结果。它不存 chunk ID——它只知道"第 0 个文档、第 1 个文档……"的位置：

```python
# 构建时：chunks 列表的顺序 = BM25 内部索引顺序
tokenized = [list(jieba.cut(chunk["content"])) for chunk in chunks]
bm25 = BM25Okapi(tokenized)
# tokenized[0] → chunks[0] → id="data/oa_monitor.md_chunk_0"
# tokenized[1] → chunks[1] → id="data/oa_monitor.md_chunk_1"

# 检索时：拿位置索引反查 chunks 列表
scores = bm25.get_scores(query_tokens)   # shape=(N_chunks,)
top_indices = np.argsort(scores)[::-1][:top_k]  # → [3, 0, 7, ...]
for idx in top_indices:
    results.append({**chunks[idx]})  # 把 chunks[idx]["id"] 带出来
```

关键约束：**传给 `build_bm25_index()` 的 `chunks` 列表和传给 `collection.add()` 的 chunks 必须是同一份、同顺序的数据**。这就是为什么 `main.py` 里只维护一份 `chunks` 变量，同时传给 ChromaDB 写入和 BM25 构建。

**RRF 融合：chunk ID 是去重合并的 join key**

两路检索各自返回带着 chunk_id 的结果列表后，`rrf_fusion()` 用 chunk_id 做去重合并：

```python
# 向量路贡献
for rank, item in enumerate(dense_results, start=1):
    chunk_id = item["id"]
    scores[chunk_id] = scores.get(chunk_id, 0) + alpha / (k + rank)

# BM25 路贡献 —— 同一个 chunk_id 出现两路时，分数累加
for rank, item in enumerate(sparse_results, start=1):
    chunk_id = item["id"]
    scores[chunk_id] = scores.get(chunk_id, 0) + beta / (k + rank)

# 输出：5 + 5 → 去重后约 8 个（交集约 2~3 个）
```

如果两路用了不同的 ID 体系（比如向量路用 `chunk_0`、BM25 路用 `doc_0`），RRF 就无法正确去重——同一个 chunk 会被当成两个不同 chunk 各给一次分，融合结果完全错乱。**统一的 chunk ID 是整个混合检索正确性的前提。**

**QueryLog SQLite：chunk ID 作为 JSON 数组存储**

`data/queries.db` 是独立于 ChromaDB 的另一个 SQLite 文件，只存请求日志。chunk ID 在这里不是主键，而是 JSON 数组中的一个元素：

```sql
vector_hits TEXT,   -- '["data/oa_monitor.md_chunk_0", "data/oa_monitor.md_chunk_1", ...]'
bm25_hits   TEXT,   -- '["data/region_whitelist.md_chunk_0", ...]'
```

用途是 bad case 回溯：用户反馈 → 根据 user_id 查 QueryLog → 反序列化 JSON → 拿到那次请求召回了哪些 chunk → 定位问题。

**两个 SQLite 的区分**

| | ChromaDB 内部 SQLite | QueryLog SQLite |
|---|---|---|
| 路径 | `data/chroma_db/chroma.sqlite3` | `data/queries.db` |
| 内容 | embeddings + documents + metadatas | 每次 /ask 的请求日志 |
| chunk ID 角色 | **主键**（唯一标识一个 chunk） | **JSON 数组中的一个值**（用于日志回溯） |
| 读写模式 | 高频读、低频写 | 只写不读（不提供查询 API） |

**当前设计的优缺点**

当前 `{file_path}_chunk_{i}` 方案：

- 优点：直观可读，调试时一眼看出是哪个文件的第几个 chunk；构建简单，不需要额外哈希计算
- 隐患：文件重命名或移动后 chunk ID 会变，旧 ChromaDB 记录只能通过 `where={"file_name": file_path}` 来删。目前 `update_document()` 已经这么做了，所以影响可控

如果后续 chunk 规模上万或文件频繁变动，可以考虑用**内容哈希**做 chunk ID：

```python
import hashlib
chunk_id = hashlib.md5(full_content.encode()).hexdigest()[:12]
# → "a3f2c8e1b9d0"
```

**Q47. API 层面的限流怎么做？Python 层限流还是 LVS 层？用什么框架？多实例下怎么保证计数一致？**

**分层限流：LVS 做粗粒度入口防护，Python 做细粒度业务限流**

LVS 和 Python 做的事情不一样。LVS 工作在 TCP 层，按源 IP 限制**连接速率**——同一 IP 每秒最多建 50 个 TCP 连接，对 SYN flood 有效。但它看不到 HTTP 请求内容——一个用户保持一个长连接发 1000 个请求，LVS 不会拦。

Python 层能做 LVS 做不到的：按 user_id 限流、按接口路径限流（`/ask` 30/min、`/admin/rebuild` 1/min）、返回友好的 JSON 错误信息（HTTP 429 + "您提问太频繁，请稍后再试"）而不是 TCP RST。

**Python 层实现：slowapi**

`slowapi` 是 `limits` 库的 FastAPI 封装，装饰器一行即可：

```bash
pip install slowapi
```

```python
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded
from fastapi import FastAPI, Request

# ① 创建限流器
limiter = Limiter(key_func=get_remote_address)  # 基于客户端 IP

app = FastAPI()
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)


# ② 按接口限流
@app.post("/ask")
@limiter.limit("30/minute")  # 同一 IP 每分钟最多 30 次
async def handle_ask(request: Request):
    ...


@app.post("/admin/rebuild")
@limiter.limit("1/minute")   # 管理接口——每分钟最多 1 次
async def admin_rebuild_index(request: Request):
    ...


@app.get("/health")
@limiter.limit("1000/minute")  # 健康检查放宽
async def health_check(request: Request):
    ...
```

**基于 user_id 限流（比 IP 更合理）：**

内部系统用的是企业账号，多人可能共用一个出口 IP。限流应该绑 user_id：

```python
from slowapi import Limiter

def get_user_id(request: Request) -> str:
    """从 JWT 解析 user_id 作为限流 key"""
    token = request.headers.get("Authorization", "").replace("Bearer ", "")
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
        return payload["user_id"]
    except Exception:
        # token 无效时回退到 IP，防止未认证请求绕过限流
        return request.client.host

limiter = Limiter(key_func=get_user_id)

@app.post("/ask")
@limiter.limit("20/minute")     # 每人每分钟 20 次
async def handle_ask(request: Request):
    ...
```

注意：如果前面有 LVS/nginx 反向代理，`request.client.host` 拿到的永远是代理的内网 IP。需要从 `X-Forwarded-For` 取真实 IP：

```python
def get_real_ip(request: Request) -> str:
    forwarded = request.headers.get("X-Forwarded-For")
    if forwarded:
        return forwarded.split(",")[0].strip()  # 取链路中第一个 IP（真实客户端）
    return request.client.host
```

**多实例下的限流（4 个 FastAPI 实例共享 Redis 计数）：**

`slowapi` 默认用内存存储——4 个实例各自计数，每人每分钟 20 次实际变成了 80 次。所以多实例须用 Redis：

```python
import redis
from slowapi import Limiter
from slowapi.storage import RedisStorage

redis_client = redis.Redis(host="localhost", port=6379, decode_responses=True)
storage = RedisStorage(redis_client)

limiter = Limiter(
    key_func=get_user_id,
    storage=storage,  # 4 个实例共用同一个 Redis 计数
)
```

Redis 里存的 key 形如 `LIMITS:zhangsan:POST:/ask:minute`，value 是当前分钟的请求计数。Redis 的 INCR + TTL 是原子的，4 个实例并发写不会出现计数不一致。

**没 Redis 时的退而求其次：**

4 个实例各自独立计数，单实例设 20/min，总计理论 80/min。LVS 轮询不会把同一用户的请求固定打到同一台，所以单用户的实际限流是不均匀的——可能这分钟打了 3 台各 5 次、第 4 台打了 3 次，共 18 次，没触发任何一台的 20 次上限。对于日均 100 问的内部场景，这个级别的不精确完全可接受——限流的目的是"防止有人写脚本疯狂刷"而不是"精确控制每人每天 13.7 次"。真有恶意请求时，LVS 层的连接限流和 Python 层的不精确限流叠加，已经足够拦住。

**LVS 层配置（运维侧，非 Python 代码）：**

```bash
# 同一源 IP 每秒最多建 20 个新连接到 :8080
iptables -A INPUT -p tcp --dport 8080 -m connlimit \
  --connlimit-above 20 --connlimit-mask 32 -j DROP
```

**限流的完整分层策略：**

| 层 | 工具 | 粒度 | 限什么 | 超过后 |
|---|---|---|---|---|
| L4 (LVS) | iptables connlimit | 源 IP | 连接速率：每秒最多 N 个 TCP 连接 | TCP RST |
| L7 (Python) | slowapi + Redis | user_id | 请求速率：每人每分钟最多 N 次 | HTTP 429 + JSON error |
| L7 (Python) | slowapi 装饰器 | 接口 | `/admin/rebuild` 每分钟 1 次 | HTTP 429 |

当前阶段用 `slowapi` + 内存存储即可（单实例够用），流量起来后再加 Redis 做多实例统一计数。LVS 层的连接限流由运维一次性配好。

**Q48. API 调用的重试怎么做？OpenAI SDK 原生支持吗？你的项目怎么实现？**

**OpenAI SDK 原生支持重试——但你的项目用不上**

OpenAI Python SDK（`openai` 包）底层用 `httpx`，默认重试 2 次，自动覆盖网络错误、429 Rate Limit（读 `Retry-After` 响应头）、5xx 服务端错误、409 Conflict：

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk-xxx",
    max_retries=5,       # 覆盖默认 2 次
    timeout=30.0,
)
# 后续所有 client.chat.completions.create() 调用自动带重试
```

但我们的项目调的是内部统一 API（`https://internal-api/v1/rerank` 等），不是 OpenAI 直连。OpenAI SDK 的重试机制完全不参与。需要自己实现。

**用 tenacity 实现重试**

`tenacity` 是 Python 最成熟的重试库，支持同步/异步，比标准库 `urllib3.Retry` 灵活（后者只能用于 HTTP 调用，tenacity 可重试任何函数）：

```bash
pip install tenacity
```

```python
from tenacity import (
    retry,
    stop_after_attempt,
    wait_exponential,
    retry_if_exception_type,
)
import requests
import time

# ① Embedding / Rerank：幂等——同一个输入两次调用结果相同，值得重试
@retry(
    stop=stop_after_attempt(3),                       # 最多 3 次
    wait=wait_exponential(multiplier=0.1, max=1),     # 0.1s → 0.2s → 0.4s，封顶 1s
    retry=retry_if_exception_type(                     # 只重试网络/HTTP 异常
        (requests.ConnectionError, requests.Timeout, requests.HTTPError)
    ),
)
def call_embedding_api(texts: list[str]) -> list[list[float]]:
    resp = requests.post(
        "https://internal-api/v1/embeddings",
        json={"model": "text-embedding-v3", "input": texts},
        timeout=15,
    )
    if resp.status_code >= 500:
        resp.raise_for_status()       # 5xx → HTTPError → 触发重试
    if resp.status_code == 429:       # 限流 → 等 Retry-After
        wait_sec = int(resp.headers.get("Retry-After", 5))
        time.sleep(wait_sec)
        raise requests.HTTPError("rate limited, retry after backoff")
    resp.raise_for_status()
    return [item["embedding"] for item in resp.json()["data"]]


# ② LLM 生成：非幂等，不做自动重试
async def llm_stream_generate(prompt: str):
    """
    生成失败直接抛异常，让用户重试而不是系统自动重试。

    原因：
    - 非幂等：同一 prompt 两次调用输出可能不同，重试后用户看到不一致的答案
    - 延迟大：P50 400ms，重试一次 800ms，三次 2s，用户等不起
    - 用户重试优于系统重试：告知用户"失败了，再试一次"，用户有预期地等
    """
    try:
        async for token in llm_client.stream_generate(prompt):
            yield token
    except Exception:
        raise  # 不重试，直接向上抛，上层返回 SSE error 事件
```

**指数退避的时间序列：**

```
multiplier=0.1, max=1 时的退避曲线：
  第 1 次尝试: 立即
  第 1 次重试: 等 0.1s
  第 2 次重试: 等 0.2s
  第 3 次重试: 等 0.4s
  (max=1 封顶，后续不再增长)

multiplier=1, max=10 时的退避曲线（适合跨 region 调用的场景）：
  第 1 次重试: 等 1s
  第 2 次重试: 等 2s
  第 3 次重试: 等 4s
  第 4 次重试: 等 8s
  第 5 次重试: 等 10s  ← max 封顶
```

**如果不想引入 tenacity——手搓方案：**

```python
import time
import requests

def call_with_retry(url, json_data, max_retries=3):
    """不引入任何依赖的重试，几行 for 循环"""
    for attempt in range(max_retries):
        try:
            resp = requests.post(url, json=json_data, timeout=10)
            if resp.status_code < 500:      # 非 5xx → 不重试
                return resp.json()
            # 5xx → 继续循环，触发下次重试
        except (requests.ConnectionError, requests.Timeout):
            if attempt == max_retries - 1:  # 最后一次还失败
                raise
        time.sleep(0.1 * (2 ** attempt))    # 0.1, 0.2, 0.4
    raise RuntimeError(f"retry exhausted after {max_retries} attempts")
```

**三种方案对比：**

| 方案 | 依赖 | 适用场景 |
|---|---|---|
| `tenacity` | pip install | 正式项目，支持同步/异步，可定制条件，装饰器复用 |
| 手搓 `for` 循环 | 无 | 不想加依赖，重试逻辑简单，懒得维护第三方库 |
| `requests` + `HTTPAdapter` + `urllib3.Retry` | 标准库 | 仅对 HTTP 调用做重试，透明集成到 requests Session |

建议用 tenacity——`wait_exponential` + `retry_if_exception_type` 的组合让重试策略可被复用。Embedding、Rerank 两个调用点各加一个 `@retry` 装饰器，策略各不同，但底层是同一套机制。

**三个模型的重试策略总结：**

| 调用 | 幂等？ | 重试？ | 原因 |
|---|---|---|---|
| Embedding | ✅ 同一 text → 同一向量 | 3 次，指数退避 | 网络抖动不丢结果 |
| Rerank | ✅ 同一 (query, doc) → 同一分 | 3 次，指数退避 | 同上 |
| LLM 生成 | ❌ 两次调用输出不同 | 不做 | 非幂等 + 延迟大，用户手动重试更合理 |

优点：内容不变 ID 就不变，天然去重，文件重命名不影响。缺点：不直观，调试时需要反查才能定位到源文件。当前 500 文档、~2000 chunk 的规模下，`file_path_chunk_{i}` 方案完全足够。
